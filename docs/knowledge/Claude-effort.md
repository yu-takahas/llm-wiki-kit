# Claude-effort

Anthropic の API で、モデルが応答に費やすトークン量を制御するパラメータ。
`output_config.effort` に `low` / `medium` / `high` / `xhigh` / `max` のいずれかを渡す。
既定は `high` で、`high` の明示は省略時と等価。

呼び出し側から触れる調整つまみとしては、廃止された [[Temperature]] の後を占める位置にある。
ただし動かすものが違う。
Temperature が出力分布の鋭さを変えるのに対し、effort は思考・ツール呼び出し・応答テキストを含めた消費量そのものを動かす。

## 何を制御して、何を制御しないか

effort が効くのは応答に含まれる全トークンで、思考だけではない。

- テキスト応答と説明
- ツール呼び出しとその引数
- 思考（有効な場合）

思考を有効にしなくても効くこと、ツール呼び出しの回数まで動かせることの 2 点が、拡張思考の `budget_tokens` にはなかった性質。
低い effort ではツール呼び出しが少なくなり、複数の操作が 1 回にまとまり、前置きなしで実行に移り、完了報告が短くなる。

制御しないのは目に見える応答の長さ。
effort を下げると思考量は減るが、ユーザーに見える応答が確実に短くなるわけではない。
応答の分量を変えたいならプロンプトで明示的に指示する（[[Claude-Code-Skillの書き方]]「出力量を制御する」セクション）。

## 水準の選び方

既定の `high` から始めて、自分の評価データで上下に振るのが基本形。
以前のモデルから設定を引き継いでいる場合は、そのまま使わずスイープをやり直す。

5 水準が揃うのは Fable 5 / Opus 5 / Opus 4.7〜4.8 / Sonnet 5。
Opus 4.6 と Opus 4.5 は `xhigh` を持たず、Sonnet 4.5 と Haiku 4.5 は effort 自体を受け付けない。

| 水準     | 位置づけ                                            |
| -------- | --------------------------------------------------- |
| `max`    | 制約なしの最大能力。深い推論が要る場面に限る        |
| `xhigh`  | 長時間のエージェント作業・要求の厳しいコーディング  |
| `high`   | 既定。複雑な推論、難しいコーディング                |
| `medium` | 速度・コスト・性能の釣り合いを取る                  |
| `low`    | 短く区切られたタスク、レイテンシ重視、[[Sub-Agent]] |

Opus 5 では `low` と `medium` が、わずかなトークンとレイテンシで高い品質を出す。
品質が保たれる範囲では、この 2 つがコストと応答時間の主要な制御手段になる。

コードレビューでは、指摘の精度（誤検知の少なさ）が低い水準でも維持される。
網羅性の方は水準に依存するので、速い低水準パスと徹底的な高水準パスを分ける設計が成り立つ。

## 思考との関係

`thinking` は思考ブロックを出すかどうかを決め、effort は応答全体にかける仕事量を決める。

適応的思考（`thinking: {type: "adaptive"}`）は、いつどれだけ思考するかをモデルが動的に決める方式で、4.6 世代以降はこちらが主になっている。
このモードでは effort が「どれくらいの頻度でどれだけ深く思考するか」まで含めて動かす。

これに先立つ拡張思考の手動バジェット（`budget_tokens`）は Opus 4.6 / Sonnet 4.6 で非推奨になり、Opus 4.7 以降のモデルでは指定すると 400 エラーになる。
思考のコストに上限を掛けたい場合は effort を下げるか、`max_tokens` を厳格な上限として使う。

高い水準ではほとんどの要求で思考し、低い水準では簡単な問題で思考を省くことがある。

Opus 5 には制約が 1 つある。
思考の無効化は effort が `high` 以下の場合に限られ、`xhigh` / `max` と `thinking: {type: "disabled"}` を組み合わせると 400 エラーになる。
思考を無効にすると内部 XML タグの漏れとツール呼び出しのテキスト化が起きるので、コストを下げたいなら思考を有効にしたまま effort を下げる方が結果がよい（[[Chain-of-Thought]]「思考が既定のモデルでの扱い」セクション）。

## 過剰な探索を抑える手段として使う

Opus 4.6 世代で、高い effort での事前の探索が以前より増えた。
以前のモデル向けに「徹底的に」と促していたプロンプトは、そのままだと過剰になる。

対処は 3 段階で、プロンプト側から順に試す。

1. 包括的な既定を的を絞った指示に置き換える（「既定で使う」→「理解を深める場合に使う」）
2. 過剰なトリガーを招く指示を削る（「迷ったら使う」の型）
3. それでも積極的すぎるなら effort を下げる

順序が逆になると、プロンプトの問題を効率の設定で覆い隠すことになる。

## prompt cache との相性

effort はリクエスト単位の設定で、レンダリングされたプロンプトの形を変える。
そのため会話の途中で値を変えると、それ以前のキャッシュ済み接頭辞が効かなくなる。

長いセッションで prompt cache に依存しているなら、開始時に水準を決めて最後まで動かさない。
水準を変えたいときは、会話の中ではなくワークロードの単位で分ける。
