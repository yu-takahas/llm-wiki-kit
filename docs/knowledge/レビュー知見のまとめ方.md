# レビュー知見のまとめ方

レビューで得た知見を蓄積して再利用するための、1 件ごとのエントリの構造化ガイド。
lessons learned テンプレート・ポストモーテムテンプレート・コードレビューチェックリストの 3 領域を横断調査し、共通パターンを抽出した。

核心: **再利用されるエントリは「何が起きたか」ではなく「次にどう使うか」が書いてある**。

## 必須 5 フィールド

3 領域のテンプレートに共通して現れる、再利用に耐えるエントリの最小構造。

| フィールド | 役割                                                     |
| ---------- | -------------------------------------------------------- |
| タイトル   | 1 行で知見を言い切る。検索・一覧時にスキャンできる粒度   |
| 状況       | 事実ベースで何が起きたかを記述する。意見や評価を混ぜない |
| 影響       | なぜ問題なのか。放置するとどうなるか                     |
| 対策       | 次にどうすればいいか。具体的・検証可能な行動として書く   |
| 分類       | 検索・フィルタ用。どの領域の知見か                       |

対策は**動詞で始める**（add / remove / change）。
「気をつける」「意識する」は知見ではなくスローガン。

## 再利用率を上げる補助フィールド

必須ではないが、蓄積が増えたときに効く。

| フィールド      | 効果                                                               |
| --------------- | ------------------------------------------------------------------ |
| 早期警戒信号    | 「この兆候が見えたらこの知見を思い出せ」。レビュー時の検出トリガー |
| 関連            | 根拠となる規約・設計書・過去の事例へのリンク                       |
| 発見日 / 発見元 | 知見の鮮度判定用。古い知見が現状と合うか検証する際に必要           |

優先度 / 影響スコアは少量のうちは不要（全件読めるため）。
蓄積が 10 件を超えたあたりで検討する。

## 再利用されないエントリのアンチパターン

| パターン     | 問題                                                                                        |
| ------------ | ------------------------------------------------------------------------------------------- |
| スローガン型 | 「もっと気をつける」「コミュニケーションを取る」→ 次のアクションが不明                      |
| 長文型       | 経緯を詳述しすぎて再利用時にスキャンできない。タイトルで 1 行に言い切れない知見は分割が必要 |
| 属人型       | 「A さんが B をした」→ 人ではなくプロセスやシステムの改善点を書く                           |
| 分類なし型   | フラットに並べるだけ → 蓄積が 10 件を超えると埋もれる                                       |

## 領域別の構造パターン

### Lessons Learned（プロジェクト振り返り）

8 フィールド構成が主流（Plane / monday.com / Asana 共通）。
5 フィールドに加えて根本原因・早期警戒信号・アクション項目（担当者 + 期限 + 追跡番号）を持つ。
推奨改善は「コミュニケーション向上」ではなく「隔週デモを実施」のように具体化する。

### ポストモーテム（インシデント振り返り）

7 フィールド構成。
タイムライン（UTC タイムスタンプ付き）と Contributing Factors（非難なし）が特徴的。
**完了条件にランブック更新を含める**パターンが最も示唆的: 知見を書いて終わりではなく、運用手順への反映を完了条件に組み込むことで、知見が次のアクションに埋め込まれる。

### コードレビューチェックリスト

3 列構成: What to look for / Why / Ideal。
1 項目 = 1 行で完結する簡潔さ。
8 カテゴリ（プロジェクト構成 / 可読性 / 設計 / 言語使用 / テスト / ドキュメント / セキュリティ / ツール）で分類。

## 蓄積を回す設計原則

知見を書く仕組みだけでは蓄積は回らない。
ポストモーテムのランブック連携パターンから導かれる 2 つの原則:

1. **追記の導線をワークフローに組み込む**: 知見が生まれるタイミング（レビュー反映完了後等）に追記ステップを埋め込む。意識や努力に頼る蓄積は回らない
2. **完了条件に蓄積を含める**: 「知見を書いたか？」のチェックをワークフローの完了条件にする。書かなくても完了できる設計では書かれない
