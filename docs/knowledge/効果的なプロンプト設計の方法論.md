# 効果的なプロンプト設計の方法論

プロンプトを LLM から狙った出力を引き出すための「指示書」と捉え、3 層で整理する。
訓練データに寄せて書く（[[赤ずきんの原則]]）/ 構造化フレームワークで型に乗せる（[[CO-STAR]] 等）/ 推論プロセスを引き出す科学的テクニック（[[Chain-of-Thought]] / [[Tree-of-Thoughts]] / [[ReAct]] / [[Self-Refine]]）の 3 層。
2026 年は Claude Opus 4.7 / GPT-5 / Gemini 2.5 Pro いずれも構造化プロンプトに強く反応する流れ、関心は static prompt から Context Engineering へ移っている。

llm-wiki 内応用は [[プロンプト設計原則]] に分離。

## 3 層整理

### 層 1: 訓練データ寄りに書く

[[赤ずきんの原則]] が核心。LLM が訓練で見た形式・トーン・構造の「道」から外れるほどハルシネーションが増える。schema / 構造化テンプレートで道を示す。

関連原則:

- [[チェーホフの銃の誤謬]] — プロンプトに含めた要素は伏線扱いされる、不要情報を入れない
- データ形式の一貫性 — 改行・インデント・区切りを見慣れた形に揃える
- Lost in the Middle — 長プロンプトの中盤情報は忘却されやすい（詳細は [[Claude-Codeのメモリ階層]]）
- サンドイッチ戦略 — 重要情報はプロンプトの最初と最後に配置

### 層 2: 構造化フレームワーク

要素を列挙したテンプレート。標準は [[CO-STAR]]（Singapore GovTech 発、Anthropic / OpenAI コミュニティでも参照）。
2026 年時点の主要 9 種:

| フレームワーク | 構成要素                                                           | 適合タスク                              |
| -------------- | ------------------------------------------------------------------ | --------------------------------------- |
| RTF            | Role / Task / Format                                               | 一発指示、最小限の構造                  |
| TAG            | Task / Action / Goal                                               | オペレーショナル自動化                  |
| TASS           | Task / Audience / Style / Structure                                | 読み手で出力が変わるタスク              |
| [[CO-STAR]]    | Context / Objective / Style / Tone / Audience / Response           | 業務標準化（標準）                      |
| CRISP / CRISPE | Context / Role / Instruction / Specifics / Prohibit (+ Experiment) | 禁止条件の明示                          |
| BAB            | Before / After / Bridge                                            | ケーススタディ・提案書                  |
| CARE           | Context / Action / Result / Example                                | Few-shot を内包                         |
| CREATE         | Character / Request / Examples / Additions / Type / Extras         | 最も包括的、negative instruction も含む |
| COAST          | Context / Objective / Actions / Scenario / Task                    | 仮説シナリオシミュレーション            |

使い分けの目安:

- 業務標準化 / チーム展開 → [[CO-STAR]]
- 汎用的な一発指示 → 深津式
- 日常タスク → CRISPE
- 創造的タスク（ケース提案）→ BAB / CREATE
- 戦略立案 → COAST

### 層 3: 科学的テクニック（推論を引き出す）

LLM の思考プロセスに介入する手法。

- [[Chain-of-Thought]] — 推論を段階的に説明させる、複雑タスクで精度向上
- [[Tree-of-Thoughts]] — 推論枝の生成 / 評価 / 選択を再帰、Game of 24 で 4% → 74%
- [[ReAct]] — Reasoning と Acting を交互、agentic workflow の基礎
- [[Self-Refine]] — 生成 → 自己批判 → 修正ループ、~20% 改善

モデル種別による最適化:

| モデル種別                                    | 推奨                                    |
| --------------------------------------------- | --------------------------------------- |
| 通常モデル（GPT-4o / Claude Sonnet 等）       | Few-shot 例を含める、CoT 明示指示       |
| 推論モデル（GPT-5 / Claude Opus 4.7 / o1 系） | zero-shot から始め、必要時のみ Few-shot |

## 5 つの基本原則

OpenAI / Anthropic / Google ベストプラクティスで共通している項目。

1. 役割（ペルソナ）を明示する
2. 背景・目的を明確に伝える
3. 出力形式を指定する
4. やってほしくないことも明示する（negative instruction）
5. 質問でなく命令文で書く

変数化できる部分（プロンプト内の差し替え可能箇所）をテンプレ化しておくと再利用性が上がる。

## 2026 年動向: Context Engineering

「プロンプトを書く」から「LLM が見る環境全体を設計する」へ拡張している。
Context Engineering survey（arxiv:2507.13334, 2025-07）が 6 要素（`c_instr` / `c_know` / `c_tools` / `c_mem` / `c_state` / `c_query`）で形式化。
詳細は [[Chat-AIのプロンプト階層と用語体系]]「Context Engineering」セクション参照。

| 要素            | 説明                                                               |
| --------------- | ------------------------------------------------------------------ |
| Static prompt   | システムプロンプト・ロール定義（従来のプロンプトエンジニアリング） |
| Dynamic context | 実行時に注入する RAG 検索結果 / tool 使用履歴 / 会話履歴           |
| RAG             | 質問と類似のドキュメントを検索して context に挿入                  |
| DSPy            | プロンプトをプログラム的に最適化（コンパイル型 prompt）            |
| Multi-agent     | 複数 LLM agent の協調設計                                          |

2026 年時点で重心は「最適なプロンプトの詰め方」からエージェントシステムのランタイム状態管理へ移行。
命令優先度の階層化（Instruction Hierarchy という考え方）もプロンプトインジェクション対策として活発に研究されている。

効いていた技法 / 廃れた技法（2026 年）:

- 効く: 構造化プロンプト全般、CoT、Few-shot（通常モデル）、Self-Refine、RAG
- 死んだ: 「prompt injection 回避のための長文 disclaimer」（モデル側で対策済み）、「明示的に honest であれと書く」
- 逆効果: 推論モデルへの過剰な Few-shot、創造性を要求する形容詞の連発（[[赤ずきんの原則]] 違反）

## 実践チェックリスト

事前確認:

1. 役割（ペルソナ）を最初に明示したか
2. context / objective が冒頭で分かるか
3. 出力形式を具体的に指定したか
4. やってほしくないこと（negative instruction）を 1-3 個書いたか
5. 命令文として書いたか（質問でなく）

赤ずきんチェック: 詳細は [[赤ずきんの原則]] 「7 つの実践ガイドライン」セクション

技法選択:

1. 推論モデルなら zero-shot CoT、通常モデルなら Few-shot を試したか
2. 重要情報をプロンプト最初と最後に配置したか（サンドイッチ、詳細は [[Lost-in-the-Middle]]）
3. 不要情報を削ったか（[[チェーホフの銃の誤謬]]）
4. 自己改善が必要なら [[Self-Refine]] ループを末尾に追加したか
