# エージェントループの運用手法

マルチエージェントの長時間ループで、状態管理・ログ・進捗追跡・停止条件・リカバリを具体的にどう実装するかの実践手法集。
[[Agent-Teams運用パターン]] が「何をするか」を扱うのに対し、本ページは「具体的にどういうファイル形式・手順でやるか」に焦点を当てる。

## 状態ファイルの 3 パターン

ループの状態をコンテキスト外に永続化する手法。目的と形式で 3 つに分かれる。

### PROGRESS.md（チェックリスト型）

最も軽量。Claude Code の `/loop` で広く使われている。

```markdown
## Module 1: App Shell
- [x] FastAPI scaffolding
- [x] Vite frontend setup
- [-] LangSmith integration  ← 進行中

## Module 2: Retrieval
- [ ] pgvector setup
- [ ] manual history management
```

状態シンボル: `[ ]` 未開始 / `[-]` 進行中 / `[x]` 完了（検証済み）。
セッション開始時に読み込んで現在位置を把握し、タスク完了時に更新する。

### feature_list.json（構造化 JSON 型）

Anthropic の長時間エージェントハーネスで採用。JSON は LLM が不適切に書き換えにくいという理由で選ばれた。

```json
{
  "category": "functional",
  "description": "New chat button creates a fresh conversation",
  "steps": [
    "Navigate to main interface",
    "Click the 'New Chat' button",
    "Verify a new conversation is created"
  ],
  "passes": false
}
```

エージェントは `passes` フィールドのみ更新可能。テスト項目の削除・編集は厳禁。

### CHANGELOG.md（研究ノート型）

Anthropic の科学計算での長時間実行で採用。lab notes として機能する。

記録内容: 完了タスク / 失敗したアプローチとその理由 / 精度テーブル / 既知の制限事項。
PROGRESS.md が「何が終わったか」を追跡するのに対し、CHANGELOG.md は「何を試して何がダメだったか」を記録する。

### 使い分け

| パターン          | 向いている場面                                       |
| ----------------- | ---------------------------------------------------- |
| PROGRESS.md       | タスクの進捗追跡。完了/未完了が明確な場合            |
| feature_list.json | テスト駆動。合格/不合格の二値判定が本質の場合        |
| CHANGELOG.md      | 試行錯誤の記録。失敗アプローチの蓄積が価値になる場合 |

## セッション間のハンドオフ

### initializer + coding agent の分離

Anthropic のハーネス設計では、初回セッション専用の initializer agent と、2 回目以降の coding agent を使い分ける。
システムプロンプトやツールセットは同一で、初期ユーザープロンプトのみが異なる。

initializer agent の責務: 機能仕様から `feature_list.json` を生成 / `init.sh` スクリプトを作成 / 初期 git commit / `progress.txt` を初期化。

coding agent のセッション開始ルーチン:

1. `pwd` で作業ディレクトリ確認
2. git ログと progress files から最近の作業を確認
3. features list から最優先・未完了機能を選択

セッション終了時: git commit（説明的なメッセージ付き）+ progress file に進捗概要を記載。

### CLAUDE.md のコンパクター指示

CLAUDE.md に「コンテキスト圧縮時に保持すべき情報」を明示する手法:

- 現在のタスク目標と受入基準
- 読み込み済み・変更済みのファイルパス
- テスト結果とエラーメッセージ
- 行った判断とその理由

## 停止条件の設計

ループの暴走を防ぐ 3 つのハード停止: 最大反復回数 / 無進捗検出（N 回連続で変化なし）/ コスト上限（トークン数 or ドル）。

良い停止条件は検証可能な形で書く。「完了に見えたら止める」ではなく「`npm test` が exit 0」「10 回連続で全テスト通過」「$5 を超えたら停止」。

## maker / checker 分離

作業するエージェントと検証するエージェントを分ける。自己採点を防ぐのが目的。

単純な分離: `/loop` で実装 → テスト・型チェック・lint 実行 → 失敗を次の指示にフィードバック → 全通過で停止。

複数モデルでの検証: 実装後に別モデルで仕様との差分をレビューし、最大 5 ラウンド反復。両モデルが合意した場合のみ合格。

Anthropic のアプリ開発ハーネスでは generator と evaluator を分離し、スプリント契約ファイルで事前合意してから実装に入る。evaluator は 27 項目のテスト基準で各スプリントを検証し、1 つでも未達なら詳細フィードバック付きで差し戻す。

## Agent Teams の調整の実際

### shared task list

各タスクは JSON ファイルとして保存される。ステータスは `pending` → `in_progress` → `completed` で遷移し、ファイルロックで重複請負を防止する。

teammate の調整フロー: `TaskList()` で利用可能なタスクを確認 → `TaskUpdate()` で請負 → 作業実行 → `SendMessage()` で報告。teammate 間は直接メッセージングで通信可能で、lead を経由しなくてよい。

既知の問題: teammate が `TaskUpdate` を忘れることがある。lead が定期的に `TaskList()` で確認し、手動で補正する。

## リカバリの具体的手法

### git ベースのリカバリ

最も実践的。「意味のある作業単位ごとにコミット」を指示し、コミット履歴を復旧ポイントにする。

### init.sh による環境リセット

セッション開始時に実行し、開発サーバー起動 + 基本テスト実施でアプリの破損状態を素早く判定する。破損が検知されたら前のコミットまで巻き戻す。

### Ralph Loop パターン

完了宣言を鵜呑みにせず、条件を満たすまで繰り返す:

```bash
while ! grep -q "ALL TASKS DONE" STATUS.md; do
  claude -p "Read PLAN.md and STATUS.md..."
done
```

## HPC / 長時間実行の運用

SLURM + tmux で非同期管理する手法。ジョブスクリプトで tmux セッション内に Claude Code を起動し、`detach` / `attach` で非同期に監視する。コミット履歴が「速くて字面通りのポスドクの実験ノート」として機能する。
