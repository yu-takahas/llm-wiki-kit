# llm-wiki-kit で活かすプロンプト設計原則

プロンプトエンジニアリングの主要原則・手法を、llm-wiki-kit 内のどの decision の根拠として参照すべきかを整理する synthesis。
原本データの説明は [[効果的なプロンプト設計の方法論]] を参照。
本ページは「llm-wiki-kit 内応用」だけに集中する。

## TL;DR

- SKILL.md / rules の書き方は [[赤ずきんの原則]] と [[チェーホフの銃の誤謬]] に従う（構造化テンプレ + 不要記述削除）
- 出力量は上限側も規定する。常時ロード層と skill の実行手順の両方に置かないと打ち消される
- 1 メッセージの中でも探索ステップと活用ステップを別セクションに分ける（[[探索・活用ジレンマ]]、混ぜると活用の慣性で探索が空振り）
- skill の Process 設計は [[Chain-of-Thought]] のスキャフォールディング
- 複数案の trade-off 評価は [[Tree-of-Thoughts]] のメタファー
- Agent ツール / lw-cmux-teams の lead / teammate 構造は [[ReAct]] の派生
- レビュー → 修正フローの自動化は [[Self-Refine]] の延長
- 外部規約（`log.md` / `index.md` の更新）の消化はターン終了前に確認する。自己検証の重複指示とは切り分ける
- ツール呼び出しの引数と調査結果は、実物を開いてから書く
- wiki page の書き方は [[CO-STAR]] の Audience / Tone 設計

## SKILL.md / rules の書き方

[[赤ずきんの原則]]:

- 構造化テンプレート（YAML frontmatter / 番号付き Process / 表形式の数値閾値）を使う
- 停止条件を明示（「停止条件 / 提案条件」のような視覚分離、[[lw-kit-スキル設計-lw-render]]「事前条件」セクション）
- 禁止行為を明示（NEVER overwrite、`unless` 条件付き）
- skill が想定外の入力を受けたら停止 + lead 確認、創造的に推論しない

[[チェーホフの銃の誤謬]]:

- 不要な記述を入れない（wiki.md「中途半端な英単語混じり禁止」と同根の思想）
- SKILL.md は起動時に全文 context に積まれるので、毎情報に「Claude はこれを知っているか?」を問う
- 概念詳細は wiki page に委ね、SKILL.md は手順だけに集中

## 出力量の上限を規定する

kit の規約と skill は「書かないモデル」への対策として書かれてきた。
「凝縮しない」「必ず一巡問う」「暗黙完了しない」といった下限側の防御が各所にあり、上限側の規定がない。
モデルの既定の出力が長くなった結果、下限側の指示だけが効いて出力量に歯止めがかからない。

置き場は 2 層に分ける。

- 常時ロード層（CLAUDE.md か `paths` なしの rule）— 応答とナレーションの既定
- skill の実行手順 — その skill が出す成果物と報告の分量

片方だけでは効かない。
skill の実行手順が「該当なしでも報告する」のように個別報告を命じていると、起動中はそちらが勝つ。
常時ロード層に「簡潔に」と書いても打ち消される。

減らし方には区別が要る。
報告義務は走査を駆動する装置でもあるので、消すと探索が silent に崩れる。
量を減らすときは報告そのものを残し、個別報告を集約報告に畳む。

規定する 3 種類（応答 / ナレーション / 成果物）の具体は [[Claude-Code-Skillの書き方]]「出力量を制御する」セクション。

## 1 メッセージ内でも探索と活用を分ける

[[探索・活用ジレンマ]] / [[Temperature]]:

LLM はデフォルトで greedy（活用）に倒れる非対称性が、1 メッセージ（プロンプト / レスポンス）内の構造分割の判定基準として効く。
探索の所作（候補列挙 / 比較 / 棚卸し）と活用の所作（決め打ち / 実行 / 結論）を同じ段落で混ぜると、活用側の慣性で探索が空振りする。

判定: 1 メッセージの中でも探索ステップと活用ステップを別セクションに分ける。

- 1 セクション = 1 モードに絞る。指示プロンプト側でも返答レスポンス側でも同じ
- 探索強制の具体形: モード宣言（[[Temperature]] を上げる比喩で「いまは探索」と明示） / 領域別走査（カテゴリを並べて「該当なし」を許さない仕掛け）
- 例外: 探索と活用が両方発火するタスクに限る。1 問 1 答型に強制すると構造化コスト > 効果で noise になるので非適用

## Process 設計はスキャフォールディング

[[Chain-of-Thought]]:

- 複雑タスクは小タスクの連結に分解
- render skill の Process 9 ステップ（書く 4-6 / 検査する 7-8 / 引き継ぐ 9 の 3 フェーズ）はこの応用
- raw 完読 → index 読み込み → 議論ステップ → source page → entity 更新 → 矛盾保持 → バックリンク → 影響範囲 → 引き継ぎ、と各ステップが独立して評価可能

## 複数案 trade-off 評価

[[Tree-of-Thoughts]]:

- 設計判断で複数案を出す習慣（CLAUDE.md 改訂時の案 A/B/C、render skill 名選定の 3 候補、cleanup vs 維持の選択肢提示）
- 単一案に最初から収束しない、評価軸を明示する
- AskUserQuestion で 2-4 案を提示するパターンも ToT の極小版

## Agent ツール / lw-cmux-teams

[[ReAct]]:

- lead が思考・判断、teammate が行動（実装・調査）、結果を lead に返す
- Agent ツールの tool use loop も Reasoning と Acting の交互実行
- 議論ステップ（書く前に lead 提示）は Reasoning phase、Process 4-9 は Acting phase の連続

## レビュー → 修正フローの自動化

[[Self-Refine]]:

- lw-doc-review skill → reviewer 出力 → lead が lw-fix-review で反映、というフローは [[Self-Refine]] の人間ループ版
- レビューと反映を別 skill に分けているので、同一プロンプト内の自己批判にはならない。[[Self-Refine]]「現行モデルでの扱い」セクションが効く形として挙げているのがこの型
- ループの停止条件（「ほどほどで OK」）はユーザー判断で残す

## 外部規約の消化をターン終了前に確認する

リポジトリ固有の規約（`log.md` 更新、`index.md` 追従）は、モデルの内部基準に無い。
自己検証の重複指示とは扱いが違うので、公式のプロンプティング指針が削除対象に挙げた再チェック指示とは分けて考える。

判別文: その指示を削って失われるのが「重複した検証」なら削る、「規約そのもの」なら残す。
「答えを再確認する」は削ってもモデルが自発的に同じことをするので無害。
外部規約は指示が唯一の担い手なので、削ると規約ごと消える。

書き方は、頻度ベース（「○○のたびに××する」）ではなくターン終了前（「ユーザー報告を返す直前」）に置く。
理由は 2 つある。

- 発火条件が明確 — 「○○のたび」は○○の判定がモデル側の解釈に委ねられるが、「ユーザー報告を返す前」は解釈の余地が小さい
- 発火回数が畳み込まれる — 頻度ベースは N 回の Edit に対して N 回の判定が要り、そのすべてで発火する保証がない。ターン終了前チェックは判定を 1 回の確定した発火点にまとめる。`log.md` の「編集回数でなく成果物の変化で数える」という数え方とも一致する

適用例は CLAUDE.md `## log / index` の「ターン終了前セルフチェック」（[[lw-kit-詳細設計-log-index]]）。
[[赤ずきんの原則]] とも整合する（「○○の直前」という条件付き行動パターンは LLM の訓練データに乗りやすい）。

### prompt で書くか deterministic 層で締めるか

判定に解釈が要るかで分ける。

- 機械的に判定できる義務（format 実行、lint で止める）→ hook / settings / allowed-tools
- 判断を伴う義務 → prompt 側のターン終了前チェック

`log.md` 更新は後者。
「成果物が実質的に動いたか」の判定に解釈が要る（編集回数でなく変化の単位で数える）ので、hook 化できない。

層分けの考え方は [[Claude-Code-Skillの書き方]]「手順省略を仕組みで防ぐ」セクションと同じ。

## 実物を開いてから書く

モデルは開いていないファイルについて推測しやすい。
公式のプロンプティング指針は、開いていないコードについて推測しないこと、特定のファイルを参照されたら答える前にそのファイルを読むことを勧めている。

kit 内の適用は 2 つある。

- ツール呼び出しの引数を記憶から組み立てない。Edit の `old_string` は直前に Read した出力をそのまま使う（実務の手順は `wiki-style.md`「Edit する時の規律」）
- 調査結果を書く前に一次ソースを開く。目次・報告値・検索結果のスニペットだけで成果物を書かない

どちらも「推測が混ざっても出力の見た目は変わらない」という共通点がある。
書けてしまうので、書く前の手順で止める。

## wiki page の書き方

[[CO-STAR]]:

- Audience: llm-wiki-kit の wiki page の読み手は「未来の自分 + LLM」の二重読者
- Tone: 静かに、説明的、フラットなリスト（wiki.md「リスト太字禁止」と整合）
- Style: 日本語で書き、技術用語は原文のまま（wiki.md「中途半端な英単語混じり禁止」）
- Response: 5 fields frontmatter + flat layout（wiki.md 準拠）
