# レビューワークフローの設計原則

コードレビュー・設計書レビュー・デザインレビュー・原稿校正を横断して、レビューワークフローの一般的な構造を抽出した。
領域が違っても骨格は同じ: 多段階・役割分担・フィードバックループ。

## 5 段階モデル

どの領域でも、レビューは以下の 5 段階に分解できる。

| 段階              | 役割           | やること                                                     | やらないこと               |
| ----------------- | -------------- | ------------------------------------------------------------ | -------------------------- |
| 1. 準備           | 著者           | レビュー目的・観点・レビュアーを決める                       | レビュー自体               |
| 2. セルフレビュー | 著者           | チェックリストで自己検証。機械で拾える問題はここで潰す       | 他者の視点が必要な判断     |
| 3. 他者レビュー   | レビュアー     | 著者が見えない問題を指摘する。観点別に段階を分けることもある | 著者の代わりに書き直す     |
| 4. 反映           | 著者           | 指摘を取捨選択して反映する                                   | 全指摘を無条件に受け入れる |
| 5. 蓄積           | 著者 or チーム | 知見をガイドライン・チェックリスト・事例集に書き戻す         | 知見を書いて終わり         |

段階 5 が抜けているチームが多い。
ポストモーテムの世界では「ランブック更新が merge されるまで完了しない」が完了条件になっている。

## 領域別のワークフロー比較

### コードレビュー

セルフレビュー → 自動チェック（lint / format / test）→ ピアレビュー → 変更要求 → 修正 → 承認 → マージ。

- **自動化できるものは人間が見ない**: lint / CI で拾える問題はセルフレビュー以前に潰す
- **PR サイズの制約**: 200-400 行が最適。大きすぎると検出率が落ちる
- **フィードバックは code について、author についてではない**
- **レビュー後の蓄積**: PR の議論をコード内コメントに残す（PR より永続的）

Google のコードレビュー基準: 完璧でなくても、コードベースの全体的な健全性を改善するなら承認する。

### 設計書レビュー / デザインレビュー

準備（目的・参加者・チェックリスト）→ プレゼンテーション → フィードバック収集 → 分析・優先度付け → 反映 → フォローアップ。

- **段階的深度**: Conceptual → Preliminary（PDR）→ Critical（CDR）→ Final と、段階ごとに検証の深さが変わる
- **参加者 10 名未満**
- **フィードバックの構造化**: 影響度 x 実現可能性のマトリクスで優先度付け
- **フォローアップが完了条件**: レビュー結果の反映確認会議を設定する

### 原稿校正（出版）

Critique（批評）→ Developmental Editing（構成編集）→ Line Editing（行編集）→ Copy Editing（校閲）→ Proofreading（校正）。

- **各段階で見るものが明確に違う**: 構成を見る / 文を磨く / 文法・用語の統一 / 最終誤り
- **後段階は前段階の仕事をしない**: 校正は「使用法、スタイル、事実確認、内容には対処しない」
- **著者の声を残す**: 行編集は著者の個性を損なわないよう微調整する

### 技術文書レビュー

ドラフト → セルフチェック → ピアレビュー（構成・一貫性）→ SME レビュー（技術精度）→ 編集レビュー（文法・用語）→ コンプライアンス → 最終承認 → 公開。

- **最も多段階**: 7 段階。各段階でレビュアーの専門が異なる
- **RACI モデル**: 各段階で「実行責任」と「説明責任」を分離する
- **コメントの分類処理**: 「解決 / 延期 / エスカレーション」の 3 分類。段階終了時に全コメントが処理済みであることが完了条件

## 5 つの設計原則

### 原則 1: 観点の分離

1 回のレビューで全部見ようとしない。
段階ごとに「何を見るか」「何を見ないか」を明確にする。

### 原則 2: 著者が反映の主体

レビュアーは指摘する。著者が取捨選択する。
レビュアーが勝手に書き直すのではなく、著者のオーナーシップを保つ。

### 原則 3: フィードバックの構造化

自由記述のコメントではなく、分類・優先度・アクションを構造化する。
技術文書では「解決 / 延期 / エスカレーション」、デザインでは「影響度 x 実現可能性」。

### 原則 4: 完了条件にフォローアップを含める

レビューして終わりにしない。
ポストモーテムの「ランブック更新が merge されるまで完了しない」パターン。

### 原則 5: 蓄積はワークフローに組み込む

蓄積を「やるべきこと」ではなく「ワークフローの一部」にする。
意識や努力に頼る蓄積は回らない。導線として組み込む。
