# テスト駆動開発の実践

Kent Beck が提唱した TDD（Test-Driven Development）の実践手法を、書籍と現代の発展を踏まえて整理する。

## ゴールと 2 つのルール

TDD のゴールは「動作するきれいなコード」（Ron Jeffries）。
手段は 2 つのルールに集約される。

- 自動化されたテストが失敗したときのみ、新しいコードを書く
- 重複を除去する

この 2 つは作業の順序でもあり、Red-Green-Refactor のサイクルを生む。
本質はテスト網羅ではなく設計。
Kent Beck 自身「TDD はテスト技法ではない。分析技法であり設計技法」と述べる。

## Red-Green-Refactor サイクル

1. **Red**: 動作しないテストを 1 つ書く
2. **Green**: そのテストを迅速に動作させる（このステップでは罪を犯してもよい）
3. **Refactor**: テストを通すために発生した重複をすべて除去する

テストは「ラチェットの歯車」。
いったん通ればコードが動作していることが分かり、後退しない。

### Green に到達する 3 戦略

一般化への確信度で使い分ける。

- **明白な実装**: すぐ書けて確信があるなら、そのまま実装する。予想外に Red が出たらギアを下げる
- **仮実装**: ベタ書きの値を返してテストを通し、定数を本物の式・変数に少しずつ置き換える
- **三角測量**: 一般化の方向が本当に分からないときだけ、2 つ以上の例から実装を導く

## TODO リスト駆動

TODO リストはワークフローの中核。

- 着手前に、必要になりそうなテストをリストに書き出す
- テストは 1 つずつ書く（10 個一気に書くとリファクタ時の慣性が高く、グリーンから遠くなる）
- 作業中に思いついた新テストやリファクタリングは、割り込ませずリストに書く
- 「グリーンバーから行える変更は 1 つだけ」が基本

Canon TDD（Kent Beck, 2023）でもこのリスト運用は健在で、「テストシナリオのリストを書く → 1 つを実行可能テストに変換する → 通す → 気づいたシナリオはリストに追加」と再定義されている。

## テストを書く判断

### いつ書くか

テスト対象のコードを書く前に書く。
実装を終えると後からテストは書かれない。
アサートファースト: 「終わりにパスすべきアサーション」から書き始めて、必要な変数を後ろ向きに補う。

### 何をテストするか

テスト対象は「条件分岐 / ループ / 操作 / ポリモフィズム」、ただし「自分が書いたものに限る」。
他人が書いたコード（フレームワーク・ライブラリ）は信頼できないと考える理由がない限りテストしない。
目安は「不安が退屈に変わるまでテストを書く」。

### テストデータ

データに違いがあるなら、その違いは意味のあるものでなければならない。
引数逆転バグを検出するため、同じ値を異なる意味に使わない。
期待値は入力との関係が読み取れる式で書く（明示的なデータ）。

## リファクタリング

リファクタリングはグリーンの間だけ行う。
重複除去は単なる整理ではなく設計を駆動する。
Martin Fowler の 3 原則: リファクタリングと機能追加を同時にしない / テストを用意して頻繁に走らせる / 各作業を小さな単位にまとめる。

きっかけ: DRY 違反 / 直交していない設計 / 時代遅れの知識 / パフォーマンス改善。
放置したコードは「腫瘍」で、小さいうちなら安く摘出できる。

## コミットのタイミング

- **独り**: 最後に書いていたテストを失敗する状態にして終える（Broken Test）。次に戻ったときどこから再開すべきかが明白になる
- **チーム**: すべてのテストが通る状態にして終える（Clean Check-in）

絶対禁止は「テストスイートを通すためにテストをコメントアウトする」こと。

## テストが書きにくい場合

### 外部依存

- モックオブジェクト: 構築が重いリソースを偽物で置き換える。可読性が上がり低結合を促す
- セルフショント: テストケース自身をモック役にする
- クラッシュテスト用ダミー: 例外を投げる特別なオブジェクトで到達困難なエラー処理をテストする

モックの使いすぎは「無理やりテストを書くツール」への転落。
本来モックの書きにくさが設計の悪さを検知するカナリアだったのが、モックライブラリで悪い設計のままテストを通せてしまう。
「自分のコードではなく外部依存をモックせよ」「unit はクラスでなく振る舞いと定義せよ」が現代的な結論。

### UI

フロントエンド TDD の核心的な困難は「実装の詳細をテストしてしまう」構造。
内部 state を検証すると、ユーザーから見た挙動が同じでもリファクタで壊れる。
対処は props とレンダリング結果だけを通してテストすること。
「テストが、ソフトウェアが実際に使われる形に似ているほど、それが与える自信は大きい」。

## CDD と Visual TDD

TDD はロジック層のテストに強いが、UI の視覚的な詳細をコードで検証するのは難しい。
CDD（Component-Driven Development）と Visual TDD はこの隙間を埋める。

Visual TDD のワークフロー: デザイン仕様からコンポーネントの状態を列挙 → Storybook で各状態の story を作成 → 各状態に対応する実装を進める → デザインとの照合。

Storybook は単なる UI カタログではなくテスト基盤。
stories がテストケースとして機能し、コンポーネントテスト（実ブラウザ検証）とビジュアルテスト（スクリーンショット比較）の両方を支える。

## 2 つの TDD スタイル

| London School                                               | Chicago/Detroit School                 |
| ----------------------------------------------------------- | -------------------------------------- |
| Outside-In（外から内へ）                                    | Inside-Out（内から外へ）               |
| 相互作用ベース検証                                          | 状態ベース検証                         |
| 外側の API 境界から書き始め、内側の協調オブジェクトはモック | 内側のドメイン層から始め、外側へ育てる |

実務では二者択一でなく、外側は Outside-In、内側ドメインは実オブジェクトで状態検証、外部境界だけモック、という混成が推奨される。

## テスト戦略との位置づけ

TDD のテストは「プログラミングや設計の補助線」であり、本来のソフトウェアテスト（エラーを見つける過程）とは別物。
セキュリティ・負荷テスト・探索的テストはテストエンジニアの専門領域で TDD の外にある。

テストピラミッド（Mike Cohn）: ユニット（多い・速い）→ 統合 → E2E（少ない・遅い）。
テストトロフィー（Kent C. Dodds）: Static → Unit → Integration（最大）→ E2E。ROI の観点で統合テストを最厚にする。

カバレッジは「コードのカバレージではなく、状態のカバレージをテストすること」。
行の実行率 100% を目的化してはいけない。

## Canon TDD（2023）

Kent Beck は誤解・拡大解釈への問題意識から TDD の正典的定義を再整理した。
主な誤解は「設計を一緒くたにすること」で、設計を「振る舞いがどう呼び出されるか（インタフェース設計）」と「どう実装するか（実装設計）」の 2 種に分ける。
TDD が駆動するのは実装設計であり、インタフェース設計は TDD の前段で行う。
