# Self-Refine

LLM に「生成 → 自己批判 → 修正」のループを回させる手法。
同じプロンプトの末尾に自己批判を足す形は、現行モデルでは効かない。
効くのは生成とレビューを別の呼び出しに分ける形で、切り分けは「現行モデルでの扱い」セクションが持つ。

## 提唱

Madaan et al., 2023. Self-Refine: Iterative Refinement with Self-Feedback.

## 効果

提唱時の測定で、人間によるフィードバックなしで ~20% の品質改善。
プロンプト末尾に「上記の出力を 1 度読み直して、改善点を 3 つ挙げて修正してください」を追加するだけで効く、というのが提唱時の主張。
現行モデルでこの形をそのまま使っても品質は上がらず、出力とコストだけ増える（後述）。

## 構造

```text
1. 生成: モデルが Y を出力
2. 自己批判: モデルに「Y を読み直して、改善点を 3 つ挙げて」と指示
3. 修正: モデルが改善点を反映した Y' を出力
```

ループ停止条件は外部から与える（回数上限 / 品質スコア / 人間判断）。

## 現行モデルでの扱い

効果が薄く副作用が大きいのは、同じプロンプトの末尾に「読み直して改善点を 3 つ」と足す形で、これは提唱時のいちばん単純な適用でもある。
Opus 5 は指示なしで自身のミスを発見して修正するため、同じプロンプトの中で自己批判を指示すると二重になる。
公式のプロンプティング指針は、すでに実行している再チェックの指示（答えを再確認する、応答前に再検証する）を避けるよう求めており、以前のモデル向けに書いた検証指示は書き直すのではなく削除するよう勧めている。
削っても品質は落ちず、出力量とコストが減る。

手法そのものが無効になったわけではない。
効くのは、モデルの内部基準に含まれない観点を外から持ち込む形。

- 別プロセスとして回す。生成 → 別の呼び出しでレビュー → 反映と分けると、各ステップが独立するので中間出力を検査でき、レビュー基準を差し替えられる
- モデルが自発的に見ない外部規約を基準にする。プロジェクト固有の規約への適合など、訓練で身についた品質基準の外にあるもの
