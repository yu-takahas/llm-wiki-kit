# ソフトウェア設計ドキュメント体系

ソフトウェア開発における設計ドキュメントの体系を整理する。
日本の SI 系(工程別)と欧米系(読者・目的別)の 2 大潮流、Diataxis フレームワーク、[[ADR]] を比較し、llm-wiki-kit のようなフレームワーク型プロジェクトに適用可能な知見をまとめる。

## 日本 SI 系: 工程別ドキュメント体系

IPA 共通フレーム準拠の大規模 SI 開発では、工程ごとに成果物が定義される。

| 工程               | 主要成果物                                                                                            | 何を決めるか                   |
| ------------------ | ----------------------------------------------------------------------------------------------------- | ------------------------------ |
| 要件定義           | 要件定義書、機能一覧、画面一覧、画面遷移図、外部システム関連図、非機能要件書、バッチ一覧              | 「何を作るか」の合意           |
| 基本設計(外部設計) | 業務フロー図、システム構成図、画面設計書、画面遷移図、外部 IF 設計書、帳票設計書、CRUD 図、コード一覧 | 「ユーザーから見てどう動くか」 |
| 詳細設計(内部設計) | モジュール設計書、処理ロジック、DB テーブル定義、API 仕様書、エラーハンドリング定義                   | 「プログラムとしてどう作るか」 |
| テスト設計         | 単体テスト計画書、結合テスト計画書、システムテスト計画書、受入テスト計画書                            | 「どう検証するか」             |

基本設計は「外部仕様」、詳細設計は「内部仕様」という区分が軸。
規模に比例して作成資料は多くなり、規模が小さければ資料も少なくてよい。

## 欧米系: 読者・目的別の分類体系

工程別ではなく「誰が何のために読むか」で分類する。

### Product Documentation vs Process Documentation

Product Documentation(製品そのものを記述):

- PRD(Product Requirements Document): 要件・ユーザーストーリー・受入基準
- UX Design Documentation: ペルソナ、シナリオマップ、ワイヤーフレーム
- SAD(Software Architecture Document): 構造・コンポーネント・相互作用・アーキテクチャ決定
- TDD(Technical Design Document): 低レベルの実装詳細、コンポーネント設計、API 仕様
- QA Documentation: テスト計画・テストケース・テストチェックリスト
- API Documentation: API 仕様・リクエスト/レスポンス・エラーメッセージ
- User Documentation: クイックスタート、マニュアル、トラブルシューティング

Process Documentation(開発プロセスを記述): ロードマップ、バックログ、コーディング規約、テスト戦略、リリースチェックリスト。

### 5 ビューのアーキテクチャドキュメントテンプレート

フランス発のテンプレート(bflorat/architecture-document-template)は 5 つの独立した視点で構成する:

1. Application View: プロジェクト全般のコンテキスト
2. Development View: ソフトウェアアーキテクチャ詳細
3. Sizing View: パフォーマンス、インフラサイジング
4. Infrastructure View: サーバー、ミドルウェア、運用
5. Security View: セキュリティ全般

各ビューは共通構造(制約 / 非機能要件 / ソリューション)に従い、異なる役割の関係者が必要な情報に効率的にアクセスできる。

## Diataxis フレームワーク

技術ドキュメントの整理フレームワーク。
「読者が何を必要としているか」を 2 軸で分類する。

2 軸: 横軸は習得(Acquisition) ↔ 応用(Application)、縦軸は行動(Action) ↔ 認知(Cognition)。

|                | 習得(学ぶ)                         | 応用(使う)                             |
| -------------- | ---------------------------------- | -------------------------------------- |
| **行動(やる)** | Tutorial: 手を動かして学ぶレッスン | How-to Guide: 実務の問題を解決する手順 |
| **認知(知る)** | Explanation: 背景・文脈・なぜ      | Reference: 技術的事実の正確な記述      |

原則: 4 つの象限を混ぜない。
チュートリアルの中にリファレンスを書かない。
既存ドキュメントの整理にも使える — 「この文書はどの象限に属するか?」で分類すると混在や欠落が見える。

日本の SI 系の「工程別」とは直交する分類軸。
基本設計書は Reference 寄り、チュートリアルは Tutorial そのもの、設計書の why 部分は Explanation。

## LLM エージェントフレームワークの事例

arxiv の論文(2604.14228v1)が Claude Code のアーキテクチャを分析している。
llm-wiki-kit のようなフレームワーク型プロジェクトに最も近い事例。

Claude Code の構成: 7 コンポーネントモデル(UI Layer / Agent Loop / Permission System / Tool Pool / State & Persistence / Execution Environment / Safety Layers)+ 5 つの設計哲学 + 13 の設計原則 + 4 つの拡張メカニズム(MCP Servers / Plugins / Skills / Hooks)。

特徴的なのは「コンポーネント + 設計哲学 + 設計原則 + 拡張メカニズム」でドキュメントを構成する点。
従来の Web アプリ等とは異なり、エージェントフレームワークのドキュメントは「何ができるか」と「なぜそうしたか」の両方を 1 つの文書で説明する必要がある。

## 開発者ツールの README 構成

CLI ツールやフレームワークの README に共通するセクション構成:

1. Title + One-liner(これは何か)
2. Overview / Background / Problem(なぜ存在するか)
3. Key Features(何ができるか)
4. Installation / Setup / Prerequisites(どう始めるか)
5. Usage / Example Flow(どう使うか)
6. Configuration(どう設定するか)
7. How It Works / Architecture(どう動くか)
8. Commands / API Reference(リファレンス)
9. Advanced Features(応用)
10. Limitations / Scope(制約)

## 情報設計の 3 要素

今日から始める情報設計(Abby Covert)第 4 章・第 7 章の知見。
ドキュメント体系の設計は情報設計(Information Architecture)の実践にあたる。

体系を構成する 3 要素:

- オントロジー(意味): 用語の定義を決める。統制語彙(使う言葉 / 使わない言葉のリスト)を作り、言語的不安定度を減らす。「asset を 5 チームが 3 通りの意味で使っていた」のような混乱を防ぐ
- タクソノミー(分類): ものごとの分類を決める。フォルダ構成やカテゴリ分けがこれにあたる。分類に正解はなく、基準の選択が設計判断
- コレオグラフィー(順序): ものごとの順序を決める。ナンバリングや工程順がこれにあたる

ドキュメント体系に最低限必要な 3 点セット(第 7 章「全体は部分の総和に勝る」):

- 階層ダイアグラム: 構成要素の親子関係を示す
- フローダイアグラム: ユーザーの体験順序を示す
- 用語集: 統制語彙をドキュメント化したもの

また「調整は現実の一部」(第 7 章)として、完成を求めず変化に対応し続けることが強調されている。
ドキュメント体系も一度決めたら終わりではなく、継続的に箱と矢印を動かす作業。
