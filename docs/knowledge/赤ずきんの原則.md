# 赤ずきんの原則

Little Red Riding Hood Principle。
プロンプトが LLM の訓練データの「道」から遠く離れるほど、ハルシネーションや誤りが増える、というプロンプト設計原則。

## 提唱

- O'Reilly『LLMのプロンプトエンジニアリング』(John Berryman & Albert Ziegler, 2024-11)。GitHub-Copilot 発案者による著作で原則として明文化
- Ajai Chaudhary のブログ記事「The Little Red Riding Hood Principle」(2025-12) で運用ガイドに展開

## 比喩のマッピング

| おとぎ話           | プロンプト設計                                                                      |
| ------------------ | ----------------------------------------------------------------------------------- |
| 森の道（path）     | モデルが訓練時に見た形式・トーン・構造（公式レポート / メール / CV / 要約 / table） |
| 道を外れる         | 訓練データに存在しない形式・組み合わせを要求する                                    |
| 狼（Big Bad Wolf） | hallucination / wild guess / 構造崩壊                                               |
| 道を示す柵・看板   | スキーマ / 構造化テンプレート / DSL / YAML                                          |

## 失敗例

安全報告書を生成する AI エージェントに、ユーザーが「TikTok 風ラップ + リスク数値 + 生物学的比喩」を要求 → 訓練データに該当形式の組み合わせが存在せず、システムが崩壊。

## 7 つの実践ガイドライン

1. 既知の形式を模倣する（出力形式は LLM が訓練で見たことのある型に合わせる）
2. 急激なスタイル変更を避ける（同一プロンプト内で文体・トーンを途中で切り替えない）
3. スキャフォールディング — タスクを段階的に分解（事実抽出 → 要約 → 提言生成、のように小さい既知タスクの連結）
4. 過剰な創造性指示を制限する（「creative」「unique」「out of the box」を要求すると道を外れる）
5. スキーマで出力空間を制限する（JSON Schema / YAML 構造で「ここしか書けない」を作る）
6. Few-shot で模倣パターンを示す（実例を 1-3 個入れて道筋を視覚化）
7. ユーザー入力をフォーム / ドロップダウンで制御する（自由記述の入力もまた道を外す原因）
