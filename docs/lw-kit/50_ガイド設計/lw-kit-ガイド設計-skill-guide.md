# skill 設計ガイドの設計

`skill-guide.md`（skill 設計 issue 用の guide）固有の設計判断。
guide という仕組みそのものの設計は [[lw-kit-詳細設計-guide]] が持つ。
手順・行の具体は実物が正本で、本書はその why を持つ。
実物は kit では `templates/00_issues/.guide/skill-guide.md`、配布後のワークスペースでは `00_issues/.guide/skill-guide.md`。

本 guide が生まれた環境では skill 設計の手順が既に定着しており、guide が無くても大半は実行されていた。
このため設計時の主目的を記録に置いている。
手順が定着していない環境では、手順の提示そのものが主な価値になる。
定着した手順は実施しても issue に書かれないので、記録だけを読むと未実施に見え、「手順から逸脱している」という誤った結論を導く。
本 guide の役目は手順の強制ではなく、実施とスキップの記録先を用意することと、後回しにされやすいステップを都度払いにすること。

## 対象タスク

使うのは skill の新規設計と、既存 skill の設計変更。
手順の追加・削除、判断基準の変更、SSOT 分担の見直しが対象になる。

使わないのはコードを書く issue（[[lw-kit-ガイド設計-dev-guide]]）、wiki page の作成、調査系のタスク。

境界を「設計変更かどうか」に置いたのは、`allowed-tools` の 1 件追加や typo の修正まで対象にすると、guide の分量に対して該当行が少なすぎて参照されなくなるため。
軽微な修正はガイドごとスキップしてよいと実物に明記している。

## フローの成り立ち

TODO 雛形のフローは、性格の違う 2 つの手順を統合したもの。

- 理想フロー: 設計者が「こう進めたい」と考える順序。案だし・机上ドッグフーディング・SSOT スリムダウンを含む
- 実行フロー: 完了した skill 設計の記録から抽出した、実際に繰り返されていた順序。先行例精読・横展開・retro を含む

背骨には実行フローを採り、理想フロー側にしかない机上ドッグフーディング（実装前に設計書の手順を実在の対象へ通す確認）と SSOT（Single Source of Truth、正本）スリムダウンを挿した。
実際に繰り返されている手順を骨組みにする方が、記録装置として機能するため。
理想フローを骨組みにすると、実行されている手順の側に記録先がない状態が残る。

実行フローに含まれる retro だけは背骨から外した。
機構側の「含めないもの」の 1 つ目（運用として定着している手順）に該当するため。

過去の記録を理想フローで採点してフローを決める方法は採らなかった。
手順そのものが時期によって変化しているため、単一のフローで過去の記録を採点すると、手順の変化を逸脱として数えてしまう。

## セクション構成の 2 本

guide の前半は issue に足すセクションの雛形で、skill 設計では 2 本にした。

- 設計判断: skill 名 / 配置 / `disable-model-invocation` / `allowed-tools` / description / SSOT 分担
- 先行例: 参考にする既存の型（設計書と、完了した設計 issue）

設計判断をチェックリスト（`- [ ]`）にしなかったのは、チェックボックスにすると判断の根拠が残らず消化の記録になるため。
実物では全項目に「判断 + 根拠 1 行」を求めており、埋めた内容がそのまま設計書の正本になる。

項目をこの範囲に絞った理由は記録に残っていない。

## 各ステップの why

先行例精読は、設計書の型と粒度が既存の設計書群で確立しているため。
読まずに書くと型から外れ、doc-review で毎回同じ指摘を受ける。

案だしの本体は議論そのものではなく記録。
方針を相談すること自体は運用として定着しているので「議論しろ」の行は冗長になる。
残しているのは「選択肢と採否を issue に記録する」という記録側で、これが retro と知見化の素材になる。

骨子合意は `.claude/rules/skeleton-confirm.md` の通り、書き切った後の巻き戻しが高コストであるため。
実物では設計書と SKILL.md の両方に骨子合意の行を置いている。
rule が骨子確認必須の対象に「Skill 一式（SKILL.md 含む）」を挙げており、設計書側だけに置くと新規 skill で rule の必須手順が抜けるため。

机上ドッグフーディングは、設計書の手順を実在の対象に通すことで、実装前に手順の不備を検出できるため。
実起動による動作確認とは別物なので「机上」で区別している。

設計書 → SKILL.md の順序は、why が先に固まると how がぶれないため。
逆順にすると、実装で決めた具体値を後から正当化する形になり、却下代替案が残らない。

SKILL.md も doc-review に通すのは、設計書と同じ観点で見られるため。
kit リポジトリでは宣言（`docs/lw-kit/.doc-review.md`）の glob `.claude/skills/**/SKILL.md` が設計書プロファイルに配線済みで、追加の設定なしに通る。

横展開を固定リストにしたのは、skill を増減しても一覧側の更新が自動では起きないため。
リスト化しないと、skill を追加した数か月後に一覧が古いまま残っていることが発覚する。
skill 名を変えた場合の grep 行を別に置いているのは、一覧に載っている箇所を全部通しても、設定ファイルや他の SKILL.md からの参照は検出できないため。

動作確認を設計者のセッションの外に置いたのは、配備と discovery（description による自動起動の判断）が、skill を書いた本人のセッションでは検証できないため。

SSOT スリムダウンを動作確認の後に置いたのは、動作確認で SKILL.md が変わりうるため。
安定してから 1 回で削る。
このステップを guide に載せる根拠は他より強い。
各 issue の中で省略されると、後から全 skill をまとめて整理する作業が別に必要になる。
本 guide が生まれた環境では、その一括整理で数百行規模の削減が発生した。
`.claude/rules/skeleton-confirm.md` の「最後にまとめて同期するステップを設計しない」に反した場合のコストがそのまま出る。

## 準備に鮮度チェックを置く

準備には、issue 内の参照（設計書のパス / skill 名 / `[[link]]`）が現存するかを確認し、ずれていれば issue を先に直す行を置いている。

skill 設計の issue は起票から着手までの間隔が長く、その間に設計書の置き場や skill 名が変わる。
参照が古いまま TODO を消化すると、指し先が存在しないまま作業が進む。
[[lw-kit-ガイド設計-dev-guide]] は同じ趣旨の行を Explore 区切りに持つが、skill 設計側には Explore がないので準備に置いた。

対象を「参照」に絞ったのは、dev 側の「issue の主張を実ファイルと突き合わせる」より狭い代わりに、機械的に確認できるため。

## 準備で規範を全部読ませる

準備では `docs/lw-kit/.doc-review.md` が規範として宣言している `docs/knowledge/` の page を、対象 skill の種類で絞らずに全部読ませる（本数と対象は実物が正本）。

`docs/lw-kit/.doc-review.md` の宣言は同じ規範に条件を付けている（配置を判断するときだけ、レビュー系 skill のときだけ、といった形で finder に渡す範囲を絞る）。
guide 側でこの条件を写さなかったのは、条件付きにすると「読むかどうか」の判断が毎回発生し、判断を誤ると読まれないため。
レビュー時は finder に渡す量を絞る利益があるが、設計時に読む側は数本まとめて読んでも負担が小さい。

規範を執筆前に読ませること自体は `.claude/rules/skeleton-confirm.md` と同じ考え方で、レビューで毎回出る指摘を書く前に解消する。

## 含めないもの（skill 設計固有分）

`50_feedback/` の知見と失敗事例は載せない。
`docs/lw-kit/.doc-review.md` の宣言がこれらをレビュー時に渡すので、guide が重ねて指示する必要がない。
どちらもワークスペース側の蓄積である点も理由になる。
知見（`feedback-知見-*.md`）は kit の配布物に含まれないので、新規ワークスペースでは参照先が存在しない。
失敗事例は空のテンプレートとして配られるので、参照は解決するが中身がない。

🌂 中断点を読む行も載せない。
issue システムがセッション開始時に拾うもので、機構層の「含めないもの」に該当する（[[lw-kit-詳細設計-guide]]）。

ブランチと worktree の作成も載せない。
セッションの起動手順にこれらが含まれる運用では、guide の手順が始まる時点で完了している。
手順の開始前に環境側で済んでいる操作は、書いても実行されることがない。

## 却下代替案

手順をコアに絞る案は却下した。
絞ると机上ドッグフーディングと SSOT スリムダウンが再び暗黙に戻る。
この 2 つは省略されやすい側なので、載せないと記録装置として機能しない。
飛ばされることへの対策は「絞る」ではなく「載せた上でスキップ条件と記録義務を明文化する」で取った。

準備の読みものを `docs/lw-kit/.doc-review.md` と同じ条件付きで書く案も却下した（理由は「準備で規範を全部読ませる」セクション）。

これ以外の判断（セクション構成 2 本 / 設計判断の項目 / TODO 区切りの粒度）には却下代替案の記録がない。
案を比較して選んだのではなく、実際に繰り返されていた手順から抽出したものが占める。
代替案が挙がっていないことを検討漏れと読まないこと。

## スキップ規律

スキップの記録義務は冒頭定型に 1 行で置き、各手順の行では繰り返さない。
[[lw-kit-詳細設計-guide]] はメニュー方式のコピー漏れ対策として、各 guide にスキップ条件とスキップの記録義務の両方を求めている。
ガイドごとスキップ・行単位のスキップ・横展開の非該当がすべて同じ扱いになるので、個別行に書くと同じ文が繰り返される。

机上ドッグフーディングだけはスキップ条件を個別に持つ（既存 skill の改修で手順の流れが変わらない場合のみ）。
このステップは省略されやすいので、条件を狭く固定した。
条件そのものは区切り直下の注記に置き、行には残さない。
スキップするかの判断はコピーする瞬間、つまり guide を読んでいる最中に行われるので、issue 側に条件が無くても判断できる（コピー後に効く必要がある記録の義務だけを行に残す方針は [[lw-kit-詳細設計-guide]] の「共通フォーマット」）。

同じ記録義務は [[lw-kit-ガイド設計-dev-guide]] にもある。
アプリ開発では区切りごとの commit がスキップの痕跡を兼ねるという見方もあるが、commit に残るのは実施したことだけで、スキップの判断は残らない。

## 決定

### `$KIT` は配布物に定義を持たせる

実物が `$KIT/docs/knowledge/`（規範）や `$KIT/docs/lw-kit/`（設計書・hub）を指しているのは、why を kit 側に置き how を SKILL.md / guide に置く分離のため。
参照自体は正しく、欠けていたのは配布される `CLAUDE.md` に `$KIT` の定義が無いことだった（2026-07-28 判断）。

`templates/.claude/CLAUDE.md` に定義行を置き、`setup.sh` が生成時に clone 元の実パスを埋める。
説明的な定義だけでは Claude が実際に Read できずポインタが実行不能なままになり、Bash 文脈では未定義変数が空展開されて誤ったパスになるため、実パスの解決まで行う。

参照先の `docs/lw-kit/` はワークスペースにコピーされないので、kit clone を消した利用者は設計書を辿れない。
これは表記をどう変えても解消しないため、定義行に「kit 側にのみ存在する」と明記して壊れ方を説明する。

書き分けの規約:

- `templates/` 配下（配布物）から kit 側を指す時は `$KIT` 起点のパス。配布先に実体がないので `[[link]]` は必ず解決しない
- `docs/` 配下同士（`docs/knowledge/` → `docs/lw-kit/` を含む）は `[[link]]`。kit を Obsidian vault として開いた時のナビゲーションを優先する

`docs/knowledge/` は手動 cp でワークスペースに取り込めるので、取り込んだ先では設計書への `[[link]]` が解決しなくなる。
それでも `[[link]]` を選ぶのは、kit 開発時に設計書へ辿れることの方が日常的な価値が大きいという判断（2026-07-28）。
取り込む利用者側の対処は [[lw-kit-基本設計-ディレクトリ構成]] に記載する。

相対パス表記（`llm-wiki-kit/docs/...` 等）は採らない。
ワークスペース内のファイルを指していると Claude に誤解させ、相対 Read を試みて失敗する。

## 未決

- 設計判断の項目は skill の frontmatter の主要な設定を並べたものだが、`context` / `model` / `effort` 等を足すかは決めていない。項目を増やすと埋める負担が上がる
- 動作確認の「新セッションで実タスクを通す」は、実施したかどうかを guide 側から確認できない。記録義務でしか担保していない
- 生成ワークスペースでは SKILL.md を設計書プロファイルに送る配線がない。配布される宣言は `30_wiki/` 配下用の 1 枚だけで、`.claude/skills/` を経路に持つルーターも無いため、宣言に glob を 1 行足すだけでは解決しない。ワークスペース側のレビュー導線をどう整えるかは決めていない
