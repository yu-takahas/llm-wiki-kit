# 開発ガイドの設計

`dev-guide.md`（アプリ開発 issue 用の guide）固有の設計判断。
guide という仕組みそのものの設計は [[lw-kit-詳細設計-guide]] が持つ。
手順・行の具体は実物が正本で、本書はその why を持つ。
実物は kit では `templates/00_issues/.guide/dev-guide.md`、配布後のワークスペースでは `00_issues/.guide/dev-guide.md`。

dev guide の役目は、[[dev-methodology-ワークフロー基本設計]] が定義した二重ループ構造を issue の ☔ TODO に落とし込むこと。
基本設計は構造を決めたが、それを 1 タスクの手順に翻訳する橋渡しがなかった。

## 対象タスク

使うのはコードを書く issue。
機能追加・バグ修正・リファクタリング・移行作業が対象。

使わないのは skill 設計、wiki page の作成、調査系のタスク。
コードを変更しない issue には TDD・テストシナリオ・PR フローのいずれも適用できないため。

## セクション構成の 3 本

guide の前半は issue に足すセクションの雛形で、dev では 3 本にした。

- 設計仕様: Explore で設計書から確認した仕様
- 参考パターン: 既存コードのどこを参考にするか（パス + 関数名・コンポーネント名）
- テストシナリオ: Plan で列挙した具体シナリオ

Explore と Plan の出力先に 1 対 1 で対応させている。
読んだ結果の置き場を先に用意しておかないと、調査結果が記録されないまま失われる。
issue を読んだだけで何を作るか分かる状態にするのが到達点。

## Explore に何を載せるか

Explore の大部分は issue システムが自動で拾うので、guide に置くのは自動では拾えないものだけにした（一般則は [[lw-kit-詳細設計-guide]] の「guide に含めないもの」）。
dev で残したのは 3 つ。

- 記述の鮮度チェック（`updated:` と今日の差を見て、issue の主張を実ファイルと突き合わせる）
- 前回からの codebase の変化の確認（`git log --oneline -10`）
- 目的付きの読み（読んだ結果を上記 3 セクションに書き残すことを前提にした読み）

3 つ目が「目的付き」なのは、書き残し先を指定しない読みは issue に痕跡を残さないため。

## テストシナリオの粒度

1 行 = 1 Red-Green-Refactor サイクル。
粒度を `/lw-tdd` の消化単位に一致させる判断の正本は [[lw-kit-スキル設計-lw-tdd]]。

シナリオは 2 種にラベル分けする。

- コードシナリオ: 検証関数・フォールバック等。`/lw-tdd` で自走できる
- プロンプトシナリオ: 実 LLM の出力品質。API キーが必要なためユーザーが手動で実行し、1 行 = 1 サイクルは適用しない

分ける根拠（実行者がユーザー手動になる運用上の制約、コードシナリオを先に固める順序）は [[dev-methodology-ワークフロー基本設計]] が正本なので、ここでは重複させない。
guide 側の判断は「issue のシナリオ行にラベルを付けて実行者を区別する」という表現形式の部分だけ。

プロンプトシナリオには「効かないときの梯子」を置いている（段は実物が正本）。
実際のプロンプト改善作業から抽出した手順で、安く試せる調整から順に並べ、モデルの切替を最後に置いている。
この順序を選んだ判断の根拠は記録に残っていない。

## Storybook を Plan で数える

UI を持ち Storybook を使う案件が前提の節。
story の新規追加は Plan でシナリオとして数え、「同期・検証」に残すのは既存 story の乖離確認だけ、という分担にした。
基本設計の CDD / Visual TDD の位置づけに整合させた（[[dev-methodology-ワークフロー基本設計]]）。
新規追加まで後段に置くと、実装が動いた時点で完了と見なされ、story の追加が後回しになって実装と乖離する。

## Code の並べ方

削除を含む変更は expand-contract の順に並べる。
原則は [[dev-methodology-ワークフロー基本設計]] が持つ。
guide 側の判断は、これを Code 区切りの並べ方として 1 行で明記したこと。
明記しないと逆順に並べてしまい、削除を先に済ませた時点で型が壊れて外側のループに持ち越される。

削除が複数の区切りにまたがる場合は、contract を各区切りに混ぜず最後の掃除区切りにまとめてよい（移行中は新旧併存を許す）。
掃除区切りは作業行だけになるので、`/lw-tdd` は呼ばず区切りの最後に全スイートで緑を確認する。
新旧併存を許す判断そのものの理由は記録に残っていない。

区切りの見出しは番号ではなく内容名を付ける（「### Code — <内容名>」）。
番号は区切りの追加・並べ替えで振り直しが必要になるため。

## 同期・検証を区切りごとに回す

作業を複数の区切りに分ける場合、同期・検証と後処理は区切りごとに回して commit する。
最後にまとめて同期しない。
`.claude/rules/skeleton-confirm.md` の「最後にまとめて同期するステップを設計しない」と整合する。
guide のこの行がその原則から導かれたのか、独立に入ったのかは記録に残っていない。

`/lw-tdd` を呼ばない区切り（作業行だけの区切り・掃除区切り）は、区切りの末尾で全スイートを走らせて緑を確認する。
サイクルごとの緑が保証されないため。

## 後処理の順序

`/simplify` → `/code-review` → `/verify` の順。
3 つとも Claude Code に用意されている skill で、案件側で定義する必要はない。

`/verify` を最後に置くのは、`/code-review` の指摘修正で diff が変わると `/verify` の結果が古くなるため。
`/verify` はアプリを実際に起動して画面や出力を証拠として残す skill なので、確認した diff と commit する diff が一致していないと証拠の意味がなくなる。

`/simplify` と `/code-review` は lead（ユーザーと直接やり取りするメインのセッション。[[lw-kit-アーキテクチャ設計]] の用語集）が直接実行するのをデフォルトとし、大 diff のときだけ別セッションへの分割を検討する。
分割の閾値は実物が持つ。
lead 直接をデフォルトにした理由と閾値の具体値の由来は記録に残っていない。
閾値を動かす時は根拠がない前提で判断してよい。

## 準備と PR・マージ

実物はブランチ（または worktree）を切る行で始まり、PR の作成からブランチの削除までで終わる。

この 2 区切りは GitHub と squash merge を前提にしている。
PR の作成が `gh pr create`、マージ後のローカルブランチ削除が `git branch -D`（squash merge では履歴が繋がらず `-d` が失敗する）、remote ブランチの削除まで含む。
他のホスティングや merge 方式を使う案件では、コマンドと後始末の手順を読み替える。

`(ユーザー)` マークが付くのはスクリーンショットの添付とマージの実行。
画像を貼るのと最終的なマージの承認は人が判断する操作なので、lead は PR 本文に表の骨組み（画面名 / 確認内容 / Screenshots の空欄）だけ用意する。

ブランチを切る行を dev に置き、[[lw-kit-ガイド設計-skill-guide]] では落としている。
コードを書く issue ではブランチ名が PR の単位になるので、セッションの起動手順でブランチを切らない運用でも必要になるという差はあるが、この差を意識して分けた記録は残っていない。

## 含めないもの（dev 固有分）

typecheck / lint / format は載せない。
lefthook の pre-commit hook が必ず走るので、guide に書いても二重になる。
一般則（hook 等で構造的に強制されるものは載せない）は [[lw-kit-詳細設計-guide]] が持つ。

## 却下代替案

dev 固有の判断を [[lw-kit-詳細設計-guide]] に統合する案は却下した。
機構は guide の種別が増えても安定しているのに対し、dev 固有の判断は実物の改訂のたびに動く。
変化速度の違う記述を同居させると、動く側の更新で安定側の鮮度まで疑わしくなる。

これ以外の判断（セクション構成 3 本 / 後処理の順序 / Storybook を Plan で数える / シナリオのラベル分け）には、却下代替案の記録がない。
いずれも案を比較して選んだのではなく、実運用で問題が出た箇所を直して実物に反映したものだから。
このため本書では、代替案の代わりに、その行が無い場合に何が起きるかを書いている。
代替案が挙がっていないことを検討漏れと読まないこと。

## スキップ規律

実物は「小さい変更（typo / config / ログ 1 行）はこのガイドごとスキップしてよい」というスキップ条件を持つ。
guide の分量に対して小さい変更が多数を占めるため、条件を明示しないと guide 全体が参照されない運用に傾く。

[[lw-kit-詳細設計-guide]] はメニュー方式のコピー漏れ対策として、各 guide にスキップ条件とスキップの記録義務の両方を求めている。
記録義務は冒頭定型に 1 行で置き、各手順の行では繰り返さない。

dev では区切りごとの commit がスキップの痕跡を兼ねるという理由で、記録義務を置かない案も検討した。
採らなかったのは、commit が痕跡として残すのは実施したことだけで、スキップしたことは diff に現れないため。
スキーマの再生成や story の乖離確認を見送った判断は、記録しなければどこにも残らない。

## 決定

### 案件固有の具体は一般名に置き換えて配る

読み替え前提で配るのはやめる（2026-07-28 判断）。
読み替えは利用者に負荷を掛ける上、読み替えないまま従われると誤った手順になる。

置き換えの方針:

- 特定のサービス名・スクリプト名は、それが何をするものかを表す一般名にする（`DynamoDB テーブル定義` → `テーブル定義`、`npm run openapi` → `API 定義の再生成`）
- 手順の意味が具体で決まる箇所は、一般名 + `（例: ...）` の形で具体を残す（`コンポーネントカタログ（例: Storybook）`）
- 利用者が自分の環境に合わせて手を動かす前提のコマンドも、同じく例示として書く

行ごと削る案は採らない。工程そのものは案件横断で有効で、消すと guide のメニューとして機能しなくなる。

## 未決

- プロンプトシナリオの節は LLM を組み込むアプリ固有で、そうでない案件では該当行がゼロになる。分量が増えたら別 guide に切り出す判断もありうる
