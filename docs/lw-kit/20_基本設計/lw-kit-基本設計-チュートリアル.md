# llm-wiki-kit のチュートリアル

新規ユーザーの初回体験を設計する。

**本ページは決定根拠のみを持つ。**
issue の本文・手順・所要時間の表記は `templates/00_issues/tutorial-*.md` が正本で、本ページに写さない。

目標は 3 つ:

1. 30 分以内に最初の wiki を作る（離脱を避ける上限として置く。実測値との関係は下記「所要の実測は熟練者の値」）
2. 作った page が互いに繋がり、`index.md` が育つところを見せる
3. kit の skill を一通り紹介する

1 と 2 は issue 1 で果たし、3 は 4 本を通して果たす。

2 を目標に含めるのは、1 だけで終わると kit が「調べて書く道具」に見えるため。
知識が繋がって溜まり、Claude が過去の調査を引用してくるところまで見せないと、他のツールとの違いが伝わらない。

## 前提

ユーザー像は [[lw-kit-要件定義-ペルソナ]] の P1 / P2。
P1 は Claude Code を日常的に使い Obsidian も触ったことがある層、P2 は Claude Code でコードは書くが wiki は「聞いたことがある」程度の層。

共通前提は「Claude Code を使っている」こと。
skill / rule / ディレクトリ構造の意味は知らない。
Obsidian と cmux は使っていなくてもよい。

## 構成

README が担当する前段（セットアップ）と、issue 4 本の本編に分ける。

前段は README を読んで `setup.sh` を実行するまで。
`setup.sh` の出力と分岐は `setup.sh` が持つ。

本編の 4 本:

| issue                                 | 担う体験                                |
| ------------------------------------- | --------------------------------------- |
| `00_issues/tutorial-01-first-wiki.md` | 調べて書く。1 本 wiki を作る            |
| `00_issues/tutorial-02-review.md`     | レビューして直す。01 の成果物を読み返す |
| `00_issues/tutorial-03-graduation.md` | 自分のテーマで自走する。卒業            |
| `00_issues/tutorial-04-weekly.md`     | 週次メンテナンス。溜まってから開く      |

どの issue が何を紹介するかは「issue 分割の狙い」が持つ。
実際の step は各 issue の `## ☔ TODO` が持つ。

## 設計判断

### issue 分割の狙い

4 本の issue で段階的にスキルを獲得する。
どの skill をどこで紹介するかが分割の基準になる。

- issue 1: 調べて書く（`lw-research-doc` / `lw-render` / `lw-update-issue` / `lw-commit`。最小のワークフロー）
- issue 2: レビューして直す（`lw-doc-review` / `lw-cmux-teams` / `lw-fix-review`。品質改善のサイクル）
- issue 3: 自走（`lw-create-issue` / `lw-retro`。ガイドなしでやれるか試し、最後に全体を振り返る。`lw-tdd` / `lw-code-review` は名前だけ紹介）
- issue 4: 週次メンテナンス（`lw-lint` / `lw-archive-weekly`。溜まってからやる方が学びがある）

同じ skill を 2 度紹介しない（記録・commit のように毎回通るものは除く）。
紹介済みの skill を再度使う step は、その時間を未紹介の skill に回す。

### issue 1 の research → render が最重要区間

ジャーニーマップの「初体験」ステージに対応する。
research → render の流れで wiki を作るのが最初の実体験。
ここで成功体験を得られないと離脱する。
P2 は wiki 概念自体が初めてなので特に切実。

### issue 3 だけ所要を目標にしない

issue 1 と 2 は、短く終わることが主眼になる。
未紹介の skill を紹介したら次へ進み、同じ skill を 2 度紹介しない。実測で 01 が 11 分、02 が 22 分。

### 所要の実測は熟練者の値

01 の実測 11 分は、kit を作った本人が慣れた状態で通した値。
初見のユーザーは skill の呼び方や出力先の確認で止まるので、30 分程度を見込む。
目標の「30 分以内」は実測に合わせて下げず、離脱を避ける上限として据え置く。

issue 3 は目的が違う。
自分のテーマで自分のものを 1 つ作る回なので、時間はかかってよい。
所要を縮める方向の調整（step を削る、対象を絞る）は 1 と 2 にだけ効かせる。

テーマを最初から決めさせない。
`/lw-create-issue` を「テーマが決まっている前提」で置くと、決まっていない人がそこで止まる。
決まっているかを先に聞き、決まっていなければ Claude から話を振って一緒に探す。
実測ではテーマ決めに 39 分かかったが、これは無駄ではなく 03 の本体になる。

### issue 1 は短くする

issue 1 の目的は完走に絞る。
レビューも振り返りも持たせない。
ステップが増えるほど、途中で詰まって離脱する確率が上がる。

### 題材を固定する

issue 1 の research のテーマは「最近調べたのに忘れたこと」に固定し、「何を調べてもよい」をやめる。
自由度が高いと題材を選ぶところで止まる。
選べたとしても、自分に効く題材になるとは限らない。

思い付かない人のために、逃げ道を 1 つ置く。
題材は kit の元になった文書（Karpathy の LLM Wiki の gist）にして、URL を渡して調べさせる。

この題材を選ぶ理由:

- いま手元で動かしている仕組みの原典なので、なぜ調べるのかを説明しなくてよい
- できる page が「この道具は何を実現しようとしているのか」になり、以降の step の理解に効く
- 原典なので陳腐化しない。差し替えが要らない
- 一次ソースが 1 つの URL に閉じているので、`/lw-research-doc` の URL モードで確実に取れる

URL は実物（`templates/00_issues/tutorial-01-first-wiki.md`）が持つ。

### 繋がる瞬間を issue 1 の render で見せる

issue 1 で render する時に何が起きるかを、issue 側に書いておく。

- 1 本の調査から複数の page ができ、互いに `[[link]]` で繋がる
- 空だった `index.md` に行が並ぶ

ここが「知識が繋がって蓄積する」ことの最初の実物になる。
チュートリアルがこの瞬間を一度も見せずに終わっていたのが、体験が「コマンド実行チェックリスト」に見える原因になっていた。

繋がる瞬間の担当を issue 1 に置くのは、issue 2 が skill の紹介で埋まるため。
チュートリアルの目的は kit の skill を一通り紹介することで、issue 2 は doc-review / cmux-teams / fix-review の 3 つを担う。
そこに research と render を再度置くと、既に issue 1 で紹介した skill のために 10 分を使うことになる。

### issue 2 で fable を使う理由

doc-review → fix-review だけだとソロ作業で終わる。
cmux-teams で fable を立ち上げて相談する体験を入れることで、「1 人で判断に迷った時に advisor に聞ける」というワークフローを体感させる。

この step は任意にする。
cmux が何かを知らない読み手が「自分の環境にない、詰んだ」と受け取るのを防ぐため、任意であることを TODO 行の先頭で明示し、cmux が何かの 1 行説明を括弧の中でなく本文行に出す。
無い場合は Claude 本体に相談させる（Obsidian と同じ扱い。無くても止まらない）。

立ち上げた advisor の片付けは要求しない。
`/exit` でセッションごと終わるので、shutdown の確認を最後に挟むと、締めの要約の前に想定外の分岐が入る。
その旨を issue 側に 1 行書いておく。

02 に置くのは、生の指摘があって採否に迷う瞬間が 02 にしかないため。
03 は手順が書かれていないことが本体の回で、そこに新しいツールの導入を足すと性格が壊れる。

### 世界観に雨を使う

チュートリアル全体を雨のメタファーで通す。
情報は降ってきて、放っておくと流れる。raw に溜め、wiki / project に蒸留する。

世界観を語る文では数字プレフィックスを外して書く。
`10_raw/` / `30_wiki/` と並べると、読み手が欠番（20 は何か）に気を取られる。
実際に操作する場所を指す文では実パスのまま書く。

新しく作るのではなく、既にあるものに言葉を付ける。
issue テンプレの 4 セクションが `💧 進行中` / `🌂 中断点` / `☔ TODO` / `🪣 経緯` で、雨の記号を既に使っている。

README では雨のメタファーを使わない。
README が「これは何か」に分量を使わない建て付けは [[lw-kit-詳細設計-README]] が持つ。
チュートリアルの内側には 4 本の issue という整合先があるので、ここでは使う。

初出は `setup.sh` の末尾。
シェルが出力するので毎回同じものが出る。Claude の応答に置くと毎回変わる。
README 冒頭の録画にもそのまま映る。

### issue 1 本を 1 セッションにする

issue の TODO を最後まで終えたら、次の issue に進ませず `/exit` を促す。
セッションを跨ぐ再開手順は issue 側に書く。

1 セッションで 4 本続けると、後の issue ほど context が長くなり応答が鈍る。
issue が「中断して再開できる単位」であることも、実際に中断して再開することで伝わる。

各 issue の TODO の最後に `/exit` の項目を置き、次に開く issue のファイル名をそこで示す。

4 本とも同じ形で終える。作業 → 記録 → FIXED → commit → exit。
04 も FIXED にして畳む。週次で繰り返す性格の回だが、使い回すと「終わった issue は畳む」という状態管理と食い違う。
次の週にまたやるなら、その時に自分で issue を切る。

`/exit` を案内する応答は、その回にやったことと、その結果できたものの要約から始める。
どの応答かをコマンド名で特定する。「最後の step まで終えたら」と書くと、直前の step の完了報告がそれに当たるかを Claude が判断できず、事務報告だけで終わる。
ここが 1 セッションの終わりで、次に開くまで間が空く。手順を消化した記録だけが残ると、何を得たのかが分からないまま終わる。
要約する対象は issue ごとに違うので、締めの定型文の中で書き分ける（内容は実物が持つ）ので、型の締めの文に書き分ける。
page が何本できたかのような具体を添える。

### 蓄積は増えた瞬間だけ見せる

蓄積は、数えた結果ではなく増えたという変化で見せる。

出すのは issue 1 の締め。
`/exit` を促す応答の要約で、page が何本できてどう繋がったかを書く。
空だったところに複数の page と `index.md` の行が生まれた直後で、数字が動くのが最も意味を持つ場所になる。
issue の冒頭で「page 0 本」と出しても情報がなく、応答が長くなるだけになる。

この要約は `/lw-render` の出力ではない。
skill が Process 8 で出すのは引用元 page の一覧までで、件数の増減は数えない。
issue 側の Claude への指示として置く。

### 応答は全体像・いまここ・次の 1 手の 3 段

型の文面は各 issue の `## 🌧️ Claude への指示` が持つ。ここにはその型を選んだ理由を書く。

一覧は名前だけ、説明はいまの分だけにする。
全体の位置が見えないまま進むのも、全 step を説明して読み手が最初の 1 手に辿り着く前に離脱するのも避ける。
成果物の一覧に表を使わない。同じ理由で縦に伸びる。

issue の入口と出口には、この切り方の例外を置く。
最初の応答は 3 段に入る前に、この issue で何をやってどうなるかを紹介する。
step の一覧は名前しか出さないので、これがないと自分が何を始めたのか分からないまま 1 手目に入ることになる。
出口の要約は「issue 1 本を 1 セッションにする」が持つ。

1 回の応答で渡すコマンドは 1 つに限る。
次のコマンドを先に見せると、そのぶん応答が伸び、いまやることが埋もれる。

`/add-dir` のように Claude の応答が返らないコマンドでは、終わったと伝えてもらう一文を添える。
ローカルコマンドは Claude のターンを起こさないので、これがないと次に進めない。

型の置き場は `## 🌧️ Claude への指示`。
💧 と 🌂 は `/lw-update-issue` が上書きするので、その中には置けない。
`.claude/CLAUDE.md` と `.claude/rules/` にも置かない。配布物の設定ファイルにチュートリアル固有の記述を混ぜないため、4 本の重複を引き受ける。

4 本で共通にするのは型の 3 段構造、「1 回の応答で渡すコマンドは 1 つ」、「終えたら `/exit` を促す」の 3 つ。
issue ごとに書き分けるのは次の 3 点。

- step 一覧の例示行は、その issue の実 TODO から起こす（他の issue の例を流用しない）
- issue 固有のコマンドの但し書き（`/add-dir` 等）は、そのコマンドが出てくる issue にだけ例として置く。規定自体は「応答が返らないローカルコマンドでは」の形で共通側に残す
- 締めの文は、次の issue がない 04 では「次の issue に進めず」を落とす。打つコマンドが定まらない step を持つ 03 は代替を足す

step を増減したら `## ☔ TODO` と `## 🌧️ Claude への指示` の例示行の両方を直す。
同じ並びを 2 箇所が持つので、片方だけ直すとずれる。過去に例示行と TODO がずれた（現在は解消済み）。

### issue の書き方

チュートリアル issue 自体が issue の書き方の見本になる。
issue の 4 セクション構造（進行中 / 中断点 / TODO / 経緯）に `## 🌧️ Claude への指示` を 1 つ足した形にする。

H1 直下のリード文は読み手に向けて書き、`## 🌧️ Claude への指示` は Claude に向けて書く。
宛先が違うので節を分ける。
状況説明を節にすると `## 💧 進行中` `## 🌂 中断点` と並び、何がどう違うのか読み手が判別できなくなるので、見出しなしのリード文に置く。

TODO の各項目には「何が起きるか」を添える。
1 項目につき 1-2 行に収める。issue を開くと全文がターミナルに流れるので、長いほど読まれなくなる。

「何が起きるか」は skill の実挙動と食い違わせない。
書く前に SKILL.md を読んで確認する。食い違いやすい点:

- `/lw-render` が作る page は 1 本とは限らない（entity / concept / synthesis にまたがる）
- `/lw-render` は書き始める前に確認を求めて止まる

初回は `just render` でおまかせにしてよいと issue に書く。
提示される 4 判断項目は初日のユーザーには判断材料にならず、読み飛ばされた上に長さだけが残る。
skill 側の出力なので issue の応答の型では縛れない。

### 概念の段階的導入

全ディレクトリの意味を最初に説明しない。
各 step で触るディレクトリだけをその場で説明する。どこで何を説明するかは各 issue の `→` 行が持つ。

`20_library/` / `40_project/` は 4 本を通して説明しない。「使いたくなったら見てね」で十分。

`00_issues/.guide/` も教えない。
チュートリアルの 4 issue にコードを書くタスクがないため、配布する guide が初日には 1 本も該当しない。
guide の存在は、`/lw-create-issue` が起票時に該当するものを提案する形で伝える（[[lw-kit-詳細設計-guide]] の「起票時の導線」）。

### Obsidian の扱い

Obsidian がなくても全 issue が完走できる建て付けにする。
Obsidian が無くても完走できることを issue 1 の冒頭で明示する。

### lint / weekly を初日にやらない理由

初日に実行しても実質 no-op になる（lint はヒットなし、weekly はほぼ空）。
溜まってからやる方が各 skill の価値が体感できる。
issue 4 として「スプリント終わりのメンテナンス」シナリオで体験させる。

### つまずきリカバリ

skill が起動しない / 出力先が想定と違う時に立ち止まらせないため、各 issue の末尾に相談先を書く。

### skill の配置と、扱わない skill

チュートリアルで使う skill は `templates/.claude/skills/` に project-local として配置する。
ワークスペースごとに独立なので global にする必要がない。
配布される全リストはそのディレクトリが持つ。

`lw-tdd` / `lw-code-review` はチュートリアルで実行しない。issue 3 の末尾で名前だけ紹介する。
コードを書くタスクがチュートリアルに無いので、実行させても題材が作れない。

`lw-sync`（kit 更新の取り込み）は未実装のため扱わない。実装はワークスペース側の issue で予定している。
実物には「将来実装予定」の 1 文を置くだけにして、TODO の項目にはしない。
