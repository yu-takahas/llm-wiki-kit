# llm-wiki-kit の rules 設計

`.claude/rules/` の設計・運用・改訂の起点ページ。
rule の新設・改訂・責務の切り分けに迷った時に読む。
[[lw-kit-詳細設計-CLAUDE.md]] が CLAUDE.md を担うのと対で、本ページは rules を担う。
Claude Code の rules / memory 一般論は [[Claude-Codeのメモリ階層]]、本ページは llm-wiki-kit 固有の決定。

**本ページは決定根拠のみを持つ。**
rule の一覧・各 rule の `paths`・各 rule が持つ規約は `templates/.claude/rules/` の実体が正本で、本ページに写さない。

rule の実体は 2 箇所にある。
kit では `templates/.claude/rules/`、生成されたワークスペースでは `.claude/rules/`。
改訂は両方に反映するが、機械的なコピーにはしない。配布版は `$KIT` 参照とワークスペース固有の page 名を落とした形にしてある。

## 責務分担

rule をどこに書くかは、5 つの置き場の境界で決める。本表が置き場境界の正本。

| 置き場                   | 持つもの                                      | 性質                                 |
| ------------------------ | --------------------------------------------- | ------------------------------------ |
| rules (`.claude/rules/`) | 領域別の規約・判定（こう書け / こう判定せよ） | 常に正しく保つ、`paths` で条件ロード |
| wiki (`30_wiki/`)        | 設計思想・背景・なぜその設計か                | 設計記録、判断の経緯                 |
| `.claude/CLAUDE.md`      | 全体の index と、領域に紐づかない規約         | 何をどこで管理するかの地図           |
| `.claude/skills/`        | 多段手順のワークフロー                        | 起動時にロード                       |
| auto memory              | ユーザー個人の好み                            | 全プロジェクト横断で常時ロード       |

中核の原則は、判定・規約は rules、設計思想・背景は wiki に分けること。
規約は守る瞬間にロードされている必要があるが、wiki の設計記録はファイルを編集する時にロードされない。
そこに規約を置くと、守るべき瞬間に届かないまま定義だけが残る。
実例として、wiki の type 判定ラインを wiki に同居させたところ、判定基準が更新されず古いまま残った。

rules と CLAUDE.md は規約の対象範囲で分かれる。
領域（ディレクトリ）に紐づく規約は `paths` で絞れるので rules が持ち、どの領域で作業していても効く規約は絞れないので CLAUDE.md が持つ。

## rules の一覧を設計書が持たない理由

rule の一覧と各 rule の `paths` は `templates/.claude/rules/` の実体が持つ。
設計書に表として写すと、rule を新設・廃止するたびに 2 箇所の更新が要り、片方が漏れる。

各 rule が具体的に何を持つかも書かない。
セクション名を列挙すると rule の改訂に追従できない（実際に `issue.md` へ 2 セクション足した時、本ページの記述が据え置きになった）。
中身はその rule のリード文が宣言している。

`paths` はそのファイルが条件付きロードされる対象ディレクトリの glob で、`paths` なしの rule は全作業で読み込まれる。
どちらを使うかの判断は次節。

## 粒度・分割・paths 設計

- 基本は `paths` 単位で 1 ファイル（1 つのディレクトリに閉じる規約は 1 ファイルにまとめる）
- 複数ディレクトリ横断の規約は 1 ファイルに集約する（schema のように raw / wiki / project にまたがるものは分割しない）
- 1 ファイルの主題が肥大したら、独立した判定・規約を別ファイルに切り出す

| ロード方式           | 使いどころ                                                     |
| -------------------- | -------------------------------------------------------------- |
| `paths` あり         | そのディレクトリで作業する時だけロード、context 圧迫を避ける   |
| `paths` なし（常時） | 全作業に共通する規律、または対象がまだ存在しない時点で効く規律 |

特定ディレクトリの編集にだけ効く規約は `paths` で絞る。
`paths` なしにするのは 2 つの場合。
作業ディレクトリを問わない多段の作業手順と、対象ファイルがまだ存在しない時点で効く必要がある規律（新規作成前なので `paths` が発火しない）。
宣言 1-2 行で済む規約は rule でなく CLAUDE.md が持つ。

## 不採用にした設計選択

検討して採らなかった選択肢。同じ提案が再燃した時に「検討済み」と分かるよう残す。

### 波及の確認先を項目の列挙で持つ

派生作業の広さを見積もる時、確認先を 6 項目（設計書 / SKILL.md 実物 2 部 / rules / templates 盤面 / hub / アーキテクチャ設計）の yes/no で答えさせ、2 項目以上なら着手しないという案。

過去 9 commit で検算して不採用にした。

- 列挙が実際の変更パターンを覆えない。最頻出だった 3 種（`50_feedback/` の各ファイル / guide / `CLAUDE.md`）がどれも項目に無く、逆に hub とアーキテクチャ設計は 1 度も出なかった
- 概念が増えるたびに表の更新が要る。標準でない独自概念を足すと、そこだけチェックから漏れる
- 項目が独立でなく連動する（rules を触れば 2 部同期は必ず付く）ため、独立に数えると実態より軽く出る

代わりに `grep -rl "<ファイル名>"` で写しの在りかを見る形にした。
列挙を持たないので概念が増えても更新が要らず、ファイル単位の粒度も出る（同じディレクトリでも配布物とそうでないものが分かれる）。

### 判定表と閾値で機械的に決めさせる

同じ広さ判定を、数値の閾値で自動的に切る案。

不採用。ルールで縛る形にすると外すのが難しくなり、規定を増やしすぎる方向に働く。
nudge の強さで入れて、効かなかったら強くする順序を採った。
強くする方向は文言の強化でなく、発生地点に近づけること（宣言 → 手順 → 出力スロット → 機械 gate）。
[[Claude-Code-Skillの書き方]] の「LLM の手順省略は仕組みで防ぐ。禁止指示 1 行では止まらない」が反対材料なので、効きは運用で測る。
指標は派生主導の commit 比率で、下がらなければ規定の強さを上げる。

### 独立した rule に切り出す

派生作業のゲートを新しい rule として分ける案。

不採用。常時ロードのファイルが 1 つ増える。
`skeleton-confirm.md` が「着手前のゲート」という同じ性格を持つので、そちらへの追記で足りる。

## 検算チェックリスト

rule を新設・改訂した後に確認する。

- `paths` は作業ディレクトリと一致しているか（常時ロードが本当に必要なものだけ `paths` なしにしているか）
- 規約・判定が wiki の設計記録にしか無い状態になっていないか（rules 側に規範文があるか。根拠は設計書に残してよい）
- rule を新設・廃止したら、配布物 `templates/.claude/rules/` と生成済みワークスペースの両方に反映したか
- CLAUDE.md に rules の詳細を書き写していないか
- auto memory にワークスペース固有の規約が紛れていないか
