# llm-wiki-kit の rules 設計

`.claude/rules/` の設計・運用・改訂の起点ページ。
rule の新設・改訂・責務の切り分けに迷った時に読む。
[[lw-kit-詳細設計-CLAUDE.md]] が CLAUDE.md を担うのと対で、本ページは rules を担う。
Claude Code の rules / memory 一般論は [[Claude-Codeのメモリ階層]]、本ページは llm-wiki-kit 固有の決定。

## 責務分担

rule をどこに書くかは、4 つの置き場の境界で決める。

| 置き場                   | 持つもの                              | 性質                                 |
| ------------------------ | ------------------------------------- | ------------------------------------ |
| rules (`.claude/rules/`) | 規約・判定（こう書け / こう判定せよ） | 常に正しく保つ、`paths` で条件ロード |
| wiki (`30_wiki/`)        | 設計思想・背景・なぜその設計か        | 設計記録、判断の経緯                 |
| `.claude/CLAUDE.md`      | ワークスペース全体の普遍 index        | 何をどこで管理するかの地図           |
| auto memory              | ユーザー個人の好み                    | 全プロジェクト横断で常時ロード       |

中核の原則は、判定・規約は rules、設計思想・背景は wiki に分けること。
wiki の設計記録は判断時点のスナップショットで後から更新されないため、規約をそこに置くと定義だけが古いまま取り残される。
実例として、wiki の type 判定ラインを wiki に同居させたところ、判定基準が更新されず古いまま残った。

## 現在の rules 構成

| rule                  | paths                                                                                    | 役割                                    |
| --------------------- | ---------------------------------------------------------------------------------------- | --------------------------------------- |
| `wiki.md`             | `10_raw/**` / `30_wiki/**/*.md` / `40_project/**/*.md`                                   | wiki schema（配置を問わず共通）         |
| `wiki-style.md`       | `30_wiki/**/*.md`                                                                        | `30_wiki/` のスタイル規約               |
| `project.md`          | `40_project/**/*.md`                                                                     | 案件固有 wiki 規約                      |
| `issue.md`            | `00_issues/**`                                                                           | issue 編集規律                          |
| `log-index.md`        | ルート 5 ファイル（`log.md` / `index.md` / `0_icebox.md` / `1_issues.md` / `2_done.md`） | log とインデックスの記入規約            |
| `skeleton-confirm.md` | なし（常時ロード）                                                                       | 骨子確認 + 派生作業に降りる前の広さ確認 |

`paths` はそのファイルが条件付きロードされる対象ディレクトリの glob、なし（常時ロード）は全作業で読み込まれる。

各 rule が具体的に何を持つかは書かない。
セクション名を列挙すると rule の改訂に追従できず、片方だけ古くなる（実際に `issue.md` へ 2 セクション足した時、この表が据え置きになった）。
中身はその rule のリード文が宣言している。

## 粒度・分割・paths 設計

- 基本は `paths` 単位で 1 ファイル（wiki は `30_wiki/`、project は `40_project/`、issue は `00_issues/`）
- 複数ディレクトリ横断の規約は 1 ファイルに集約する（wiki schema は raw / wiki / project にまたがるので `wiki.md` 1 つ）
- 1 ファイルの主題が肥大したら、独立した判定・規約を別ファイルに切り出す

| ロード方式           | 使いどころ                                                   |
| -------------------- | ------------------------------------------------------------ |
| `paths` あり         | そのディレクトリで作業する時だけロード、context 圧迫を避ける |
| `paths` なし（常時） | 全作業に共通する規律（骨子確認のような作業手順）             |

特定ディレクトリの編集にだけ効く規約は `paths` で絞り、作業ディレクトリを問わず効く規律だけ `paths` なしにする。

## 不採用にした設計選択

検討して採らなかった選択肢。同じ提案が再燃した時に「検討済み」と分かるよう残す。

### 波及の確認先を項目の列挙で持つ

派生作業の広さを見積もる時、確認先を 6 項目（設計書 / 実物 2 部 / rules / 配布物 / hub / アーキテクチャ設計）の yes/no で答えさせ、2 項目以上なら着手しないという案。

過去 9 commit で検算して不採用にした。

- 列挙が実際の変更パターンを覆えない。最頻出だった 3 種（知見ファイル / guide / `CLAUDE.md`）がどれも項目に無く、逆に hub とアーキテクチャ設計は 1 度も出なかった
- 概念が増えるたびに表の更新が要る。標準でない独自概念を足すと、そこだけチェックから漏れる
- 項目が独立でなく連動する（rules を触れば 2 部同期は必ず付く）ため、独立に数えると実態より軽く出る

代わりに `grep -rl "<ファイル名>"` で写しの在りかを見る形にした。
列挙を持たないので概念が増えても更新が要らず、ファイル単位の粒度も出る（同じディレクトリでも配布物とそうでないものが分かれる）。

### 判定表と閾値で機械的に決めさせる

同じ広さ判定を、数値の閾値で自動的に切る案。

不採用。ルールで縛る形にすると外すのが難しくなり、規定を増やしすぎる方向に働く。
nudge の強さで入れて、効かなかったら強くする順序を採った。
[[Claude-Code-Skillの書き方]] の「LLM の手順省略は仕組みで防ぐ。禁止指示 1 行では止まらない」が反対材料なので、効きは運用で測る。

### 独立した rule に切り出す

派生作業のゲートを新しい rule として分ける案。

不採用。常時ロードのファイルが 1 つ増える。
`skeleton-confirm.md` が「着手前のゲート」という同じ性格を持つので、そちらへの追記で足りる。

## 検算チェックリスト

rule を新設・改訂した後に確認する。

- `paths` は作業ディレクトリと一致しているか（常時ロードが本当に必要なものだけ `paths` なしにしているか）
- 規約・判定が wiki の設計記録に残っていないか（残っていれば rules に移す）
- CLAUDE.md に rules の詳細を書き写していないか
- auto memory にワークスペース固有の規約が紛れていないか
