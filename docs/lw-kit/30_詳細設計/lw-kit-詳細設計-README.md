# llm-wiki-kit の README 設計

`README.md` を書く / 改訂する時の設計指針。

**本ページは決定根拠と、決定として確定した項目を持つ。**
README の文言・並び順・各項目の説明文は `README.md` が正本で、本ページに写さない。
写すと実物と一緒にずれる。

## README は誰のためか

公開物。
GitHub で repo に辿り着いた人が、試すかどうかを決める場所。

読み手は [[lw-kit-要件定義-ペルソナ]] の P1 と P2 になる。
P1 は README を 30 秒で判断し、P2 は「コーディング向けツール」に見えると素通りする。
この 2 つがそのまま冒頭の制約になる。

利用者が自分のワークスペースに置く README は対象外。
配布物（`templates/`）に README は含まれておらず、利用者が書くかどうかも自由。
本ページが規定するのは kit repo 自身の `README.md` だけ。

## 3 層のどこを持つか

同じ kit について、3 つの場所が別の問いに答える。

| 場所                                                       | 答える問い     | 想定する読み手                   |
| ---------------------------------------------------------- | -------------- | -------------------------------- |
| 作品紹介サイト（<https://takahas.dev/works/llm-wiki-kit>） | これは何か     | IT リテラシーを問わない          |
| `README.md`                                                | どう使うのか   | clone するかどうかを決めている人 |
| `docs/lw-kit/`                                             | 詳しい話の入口 | 中身を知りたい開発者・メンテナ   |

**README の主題は「どう使うのか」。**
ざっと確認して、インストールまで辿り着ける分量に収める。

「これは何か」に厚く答えるのはサイトの役。
あちらは前提を置かずに説明する場所で、README よりも広い読み手に向く。
同じ説明を両方に書くと、直すときに 2 箇所になる。

例外が 1 つある。
動かすのに何が要るかは、サイトと README の両方に出す。
読み手が実物へ進むかを決めるのはサイトを読んでいる時点で、README を読むのはそのあとになるため、片方だけに置くと判断の材料が届かない。

3 つは相互にリンクして補い合う。
README から出す先は 2 本。
これは何かを知りたい読み手にはサイトへ、仕組みを知りたい読み手には設計書へ送る。

**設計書へ送る導線は [[lw-kit-アーキテクチャ設計]] を名指しする。**
`docs/lw-kit/` には設計書が多数あるが、README が示すのは 1 本だけにする。
構造・ワークフロー・設計原則が 1 箇所にまとまっており、他の設計書へはそこから辿れるため。
ディレクトリごと指すと、読み手はどれから読むかを自分で決めることになる。

## 冒頭は短く、使い方へ送る

**「これは何か」は冒頭の数行で足りる。**
厚い説明はサイトが持つので、README は早く使い方に入る。

置くのは 2 つ。
何のテンプレートかを述べる 1 行と、使うと何が起きるかの短い提示。
P2 に届かせるため、コードだけでなく設計書やナレッジ管理に使えることをここに含める。

ここを空にはしない。
GitHub から直接来た読み手はサイトを経由しておらず、冒頭が無いと価値が伝わらないまま手順が始まる。
短く置いて、詳しくはサイトへ送る。

## 載せるもの / 載せないもの

判断の軸だけを置く。
実際に何がどう並んでいるかは `README.md` を見る。

載せる側の軸は 2 つ。

- インストールまで辿り着くのに要るもの（何が要るか / どう入れるか / 最初に何をするか）
- 始めた直後に迷うもの（触るディレクトリ / 使える skill）

載せない側の軸は 3 つ。

- 「これは何か」の詳しい説明と、動機と実際の使われ方。サイトが持つ。README が同じ絵を薄めて再演すると、両方の密度が下がる
- 設計判断とその理由。[[lw-kit-アーキテクチャ設計]] を入口に `docs/lw-kit/` が持つ
- 実装の詳細（frontmatter の schema、命名規約、type 一覧）。配布される rules が持ち、利用者はワークスペース側で読む

## 視覚要素

**冒頭にロゴを置き、その下に端末の録画を 1 本置く。**
静止画の構造図は置かない。

ロゴは作品を識別するもので、構造を説明しない。
形式は動くラスタを使う。README では CSS が効かないため、静止素材では動きが出ない。
構造の図は「これは何か」に答えるもので、サイトが既にその役を持っている。
README の主題が「どう使うのか」なので、見せるのは動いている様子になる。

撮る範囲は、clone から最初の一歩までを 1 本に繋ぐ。
`setup.sh` でワークスペースができ、Claude Code が起動し、話しかけると案内が始まるところで切る。
セットアップが通ることと、使うと何が起きるかが 1 本に収まる。

操作を記述したファイルを repo に置き、`setup.sh` を変更したときに撮り直せるようにする。

**再現できるのは `setup.sh` まで。**
Claude の応答は毎回変わるので、その先は撮り直すたびに違う絵になる。
操作の記録は持つが、出力が同じになることは保証しない。

長さは 30 秒以内に収める。
P1 が README を判断する窓が 30 秒で（[[lw-kit-要件定義-ペルソナ]]）、それより長い録画は自分の役目を壊す。
超える場合は再生速度で詰め、撮る範囲を削る前に速度を見る。

映るのはチュートリアルの中身になる。
`setup.sh` が最後に案内するのが tutorial-01 で、話しかけた先で動くのもそれになる。
撮り直しの要否は [[lw-kit-基本設計-チュートリアル]] の改訂に連動する。

## バッジ

**バッジは、試すかどうかの判断に要るものだけを置く。**
他人の評価や repo の属性は、判断の材料にならないので置かない。

置くのは 3 つ。

| バッジ               | 答えるもの             |
| -------------------- | ---------------------- |
| requires Claude Code | 自分の環境で動くか     |
| last commit          | 作者が使い続けているか |
| license              | 使ってよいか           |

last commit を置くのは、個人が公開した kit にとって「放置されていないか」が試す前の関心になるため。
自動で更新されるので、記述が実物とずれない。

requires Claude Code だけが静的なバッジで、対応が変わったときに追従しない。
それでも置くのは、この kit の前提が他のどの依存よりも強く、合わない読み手が早く離脱できる方が双方にとって良いため。
本文の「動かすのに要るもの」と重複するが、一目で伝わる利点がそれに勝る。

star の数は置かない。
公開して間もない段階で少ない数を掲げると、判断の材料でなく逆の印象を与える。
数が育ったら再検討する。

template repository であることも置かない。
GitHub が repo の上部にラベルを出すので二重になる。

CI とテストカバレッジ、パッケージの版は、そもそも持っていないので候補にならない。
CI を持つようになったら、その時点で「試すかどうかの判断に要るか」を問い直す。

## サイズ感

ざっと確認してインストールまで辿り着ける分量に収める。
行数の上限は決めていない。

分量が増えるのは、載せない側の軸（実装の詳細、設計判断）が紛れ込んだとき。
削る前に、どの軸が紛れているかを先に見る。

## 不採用にした設計選択

検討して採らなかったもの。
同じ提案が再燃したときに、検討済みと分かるよう残す。

**世界観・物語性・キャラクター性を前面に出す案は採らない。** 読み手が公開物の初見であり、判断に要る情報を先に置く必要がある。個人が自分のために書く README なら成り立つが、kit repo の README は前提が違う。

**実務情報を `lw-kit.md`（meta-project ハブ）へ寄せ、README を入口に徹させる案は採らない。** `docs/lw-kit/` は clone した利用者が読める場所にあるが、試すかどうかの判断は README の中で完結する必要がある。設計書へ送るのは、判断のあとに来る詳細だけにする。

## 改訂指針

- 冒頭で「これは何か」に分量を使わない。数行で切り上げて使い方に入る
- 何かを足したくなったら、載せる側の 2 軸に当たるかを先に見る。当たらなければサイトか設計書へ送る
- skill やディレクトリの説明を足すときは、実物（SKILL.md / `templates/`）を読んでから書く。挙動の正本は SKILL.md になる
- 手順の説明を長くしない。判断に要る情報が後ろへ押し出される
- サイト側の本文を改訂したときは、README との重複が生まれていないかを見る。分担が動いたなら本ページの表を先に直す
- 設計書へ送る導線を増やさない。名指しするのは [[lw-kit-アーキテクチャ設計]] 1 本に保つ

## 検算チェックリスト

`README.md` を改訂した後に確認する。

- README だけを読んでインストールまで辿り着けるか
- 冒頭にロゴと録画があるか。録画が 30 秒以内か
- 冒頭を読んで、何ができるかと誰向けかが分かるか。そこに分量を使いすぎていないか
- 動かすのに要るものが書かれているか。サイト側の記述と食い違っていないか
- サイトの本文と同じ文が無いか
- 設計書への導線が [[lw-kit-アーキテクチャ設計]] 1 本になっているか
- skill の挙動の記述が SKILL.md と一致しているか
- 実装の詳細（schema / 命名規約 / type 一覧）が紛れ込んでいないか
- ざっと確認してインストールまで辿り着ける分量に収まっているか
- 本ページが README の文言・並び順・説明文を写していないか
