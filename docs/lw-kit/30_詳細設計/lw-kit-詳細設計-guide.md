# llm-wiki-kit の guide

guide は issue の ☔ TODO に流し込むワークフローのメニュー。
タスク種別ごとに「毎回やること」を 1 ファイルにまとめ、起票時に必要な部分だけ issue へコピーして使う。
実物は `00_issues/.guide/*.md`。

本書は guide という仕組みの設計（配置・フォーマット・増やし方）を持つ。
手順や行の具体は実物が正本で、本書はその why と却下代替案を持つ。

## 目標と非目標

目標は guide の機構を決めること。
どこに置くか、どういう形式で書くか、どう増やすか、何を載せないか。

非目標:

- 個別 guide の中身の判断（どの手順を何行で書くか）。各 guide の個別設計書（`50_ガイド設計/`）が持つ
- guide の一覧。hub の [[lw-kit]] が持つ
- 進捗・実装状況。guide は増減するが機構は安定していて、変化速度が違う

## なぜ guide が要るか

guide を持たない運用では、☔ TODO が起票のたびにアドホックに書かれる。
ワークフローの固定ステップが暗黙のままなので、抜け漏れが issue ごとに違う形で起きる。
アプリ開発なら API スキーマの再生成忘れや設計書の同期漏れ、skill 設計なら実装後の設計書スリムダウンの後回しといった形で出る。

issue システム（🌂 中断点 + `CLAUDE.md` + rules）はこれを拾えない。
issue が持つのは「この issue で前回どこまでやったか」という固有の状態で、「このタスク種別なら毎回やること」という手続きの置き場がないため。

rule に書かない理由は、rule が常時ロードで全セッションに効くから。
タスク種別ごとの手順を rule に置くと、無関係なセッションでも context を消費する。
guide は起票時に 1 本だけ読めばよいので、独立したファイルに置く方が負担が小さい。

guide にはもう 1 つ、記録装置としての役割がある。
運用として定着した手順は、実施しても issue に書き残されない。
このため後から issue を読み返すと未実施に見え、「手順から逸脱している」という誤った結論を導く。
この誤読は、対策の方向を「記録の整備」ではなく「逸脱の防止」に向かわせる。
guide が「この種別なら毎回これをやる」を持っていれば、実施の記録もスキップの記録もそこに紐づけられる。
このため各 guide は、手順を並べるだけでなく、スキップしてよい条件とスキップした事実を記録する義務を書く。
抜け漏れ防止と記録装置は別の目的であり、後者を落とすと guide は単なるチェックリストになる。

## 配置

`00_issues/.guide/` に置く。
使う場所（issue）の隣に置くという判断。

ドット prefix は issue の状態ディレクトリ（`.10_todo/` 等）と同じ扱いで、active issue のファーストビューから外す意図。
guide は毎日読むものではなく起票時に参照するものなので、`00_issues/` 直下に置くと WIP 一覧のノイズになる。

kit の `templates/00_issues/.guide/` にも同梱し、標準装備として配布する。

却下代替案: `.claude/rules/` に置く。
常時ロードのコストに加えて、本文を issue に移植して使うという性格が rule（読ませるだけ）と合わない。

## メニュー方式

guide は該当するセクション・行だけを issue にコピーして使う。
全文コピーではない。

却下代替案: 全コピー型のテンプレート。
該当しない行もスキップ扱いで残す運用になり、未チェックの `[ ]` が issue に残って完了判定を曖昧にする。

トレードオフ: コピー漏れは検出できない。
guide 側には「コピーされたか」を知る手段がないため、機構では対処できない。
対策は各 guide 側で取る（スキップ条件と記録義務。「共通フォーマット」セクション）。

## 共通フォーマット

guide は 2 部構成にする。

- 前半: issue に足すセクションの雛形（設計仕様 / 参考パターン等、情報の蓄積）
- 後半: ☔ TODO の雛形（チェックリスト、消化するもの）

分ける理由は両者の性格が違うから。
セクションは調査結果や判断を書き残す場所、TODO は完了を記録する場所であり、混ぜると判断がチェック消化に変質する。

冒頭には定型の要素を置く。
冒頭宣言、該当箇所だけコピーする旨、項目の追加・並び替えは自由な旨、guide ごとスキップしてよい条件、スキップした事実を記録する義務、`(ユーザー)` マークの意味（lead ではなく人間が手を動かす項目。lead の定義は [[lw-kit-アーキテクチャ設計]] の用語集）。
具体的な文言は実物が正本。

コピーのタイミングと単位も定型に含める。

- コピーするのは着手する時。着手が遠い issue に全区切りを積むと、TODO の分量が作業の重さを誤認させる
- issue に既に区切り構造がある場合、guide の区切り見出しは持ち込まず該当行だけ差す

どちらも guide を実際に既存 issue へ適用して判明したもの。
前者は 4 行の issue が 20 行になり、未着手のまま重い issue に見えるようになった。
後者は対象別に区切られた issue に guide の工程別の区切りを重ねると、同じ issue に 2 系統の見出しが並ぶため。

コピーされる行は 1 行に収める。
完了条件やスキップ条件のような補足は、区切りの直下に注記として置く（注記はコピーされない）。
行が複数行にまたがると、コピーする側が要約して貼るので、書いた内容がそのまま届かない。
このため行に残すのは「実行の瞬間に効く義務」（記録の義務等）に絞り、「終わったかを判定する条件」は注記に置く。

## guide の冒頭宣言

各 guide は冒頭宣言を持つ。
形式は h1 タイトルの直後に `## 対象タスク` の節を置き、「使う」と「使わない」を各 1〜2 行で書く。
guide 内の並び順は h1 → `## 対象タスク` → 冒頭定型の注意書き → 本体。
以降、この節を冒頭宣言と呼ぶ。

固定見出しにするのは、読み取り側が節単位で取り出せて、冒頭散文の書き方に依存しないため。
散文の中に紛れさせると、guide ごとの書き方の差で照合が不安定になる。

選択の材料を guide 側に置くのは、guide を増やしても参照する側の変更がゼロで済むから。

却下代替案: 参照側（`/lw-create-issue` の `SKILL.md`）に guide の一覧をハードコードする。
新設のたびに追従が必要で、固定リストが実態と乖離する。

先例は `.doc-review.md`（レビュー時に読む観点・規範をディレクトリごとに宣言するファイル。[[lw-kit-スキル設計-lw-doc-review]]）。
共通するのは「選択の材料を、読む側ではなく読まれる側に置く」構造まで。
`.doc-review.md` はディレクトリ単位に 1 枚置いて glob の一覧を持つのに対し、guide の冒頭宣言は各 guide が自分の適用条件を持つ。
guide 側を分散にしたのは、一覧を 1 箇所に集めると新設のたびに一覧の更新が要り、却下代替案と同じ問題に戻るため。

## 起票時の導線

guide 自体は受動的なファイルで、参照されなければ機能しない。
起票時に参照する導線がないと、存在しないのと同じ状態になる。
この導線は `/lw-create-issue` に置く。
起票時に `00_issues/.guide/` の guide を読み、冒頭宣言と照合して該当するものを提案する責務を持たせる。

本書が持つのは「冒頭宣言というスキーマを制定する」ところまで。
読み取り側の実装と判断は [[lw-kit-スキル設計-lw-create-issue]] が持つ。

## guide に含めないもの

1. 運用として定着している手順（`/lw-commit` / `/lw-retro` / `/lw-update-issue` 等）。guide がなくても毎回実行されるので、記載しても冗長
2. hook 等で構造的に強制されるもの。書かなくても走るため。何が該当するかは案件のツールチェーン依存なので、個別 guide 側で判断する
3. issue システムが自動で拾うもの。🌂 中断点 / `CLAUDE.md` / rules / `related` はセッション開始時に効くので、guide が重ねて書く必要はない。載せるのは自動では拾えないもの（読んだ結果の書き残し先が要る読み、記述の鮮度チェック等）だけ
4. 個別 guide 固有の判断根拠。`50_ガイド設計/` の個別設計書が持つ

1 には注記が要る。
「issue の記録に残っていないこと」を「実施していないこと」と読み替えてはいけない（背景は「なぜ guide が要るか」セクション）。

## 命名規約

実物と設計書は 1 対 1 で対応させる。

- 実物: `00_issues/.guide/<対象>-guide.md`
- 設計書: `docs/lw-kit/50_ガイド設計/lw-kit-ガイド設計-<対象>-guide.md`

`<対象>` には対象タスクが立つ語を置く。
ファイル名は `-guide.md` で揃えるが、guide を読み取る側の glob は `00_issues/.guide/*.md` にする。
`.guide/` 配下は guide だけを置く場所なので、読み取り側で名前を絞る必要がない。
設計書の側にも `-guide` を残すのは、実物のファイル名をそのまま設計書名に含めるため。
末尾を落として `-<対象>` だけにすると、実物と設計書で `<対象>` の表記が別々に育ち、対応関係がファイル名から読めなくなる。

## guide の増やし方

1. 対象タスクの種別を見極める。既存 guide でカバーできないか先に確認する
2. 実物を `00_issues/.guide/` に作る。kit リポジトリで作業している場合は `templates/00_issues/.guide/` にも複製する
3. 冒頭に対象タスクの宣言を書く（起票時の導線が読む）
4. 個別の設計書を `50_ガイド設計/` に作る（kit リポジトリの場合。ワークスペースでは案件の設計書の置き場に読み替える）
5. hub の [[lw-kit]] の設計書一覧に追加する（kit リポジトリの場合）

## 保守規律

- 実物は kit の `templates/` とワークスペースの 2 部が存在する。片方だけ直すと配布物が古いままになるので、kit リポジトリで作業する場合は両方に反映する（ワークスペース単体で使う場合は 1 部しかないので該当しない）
- 実物を rename したら参照を追従する。guide と `SKILL.md` は双方向に参照し合う（skill が判別基準の正本として guide を指す場合と、guide が skill の手順を呼ぶ場合がある）。漏れると skill 実行時に参照が解決しない
- 実物と設計書の 1 対 1 を保つ。実物だけ増えると why の置き場がなくなり、設計書だけ増えると配られない手順の設計書が残る

## 未決

- 各 guide が手順を網羅的に載せるか、コアに絞るか（コピーが選択式なのは確定済み）。guide ごとに性格が違うので、個別の設計書側の判断とする
- wiki 系（page 作成 / render）や調査系の guide を作るかは後続の判断
- guide 横断の原則を層として立てるかは個別設計書が 3〜4 本になってから再検討する。数が足りないうちは、抽出された原則ではなく予想を書くことになるため
