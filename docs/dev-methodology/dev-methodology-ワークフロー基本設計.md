# ワークフロー基本設計

TDD と AI 駆動開発を組み合わせた開発ワークフローの設計。
案件横断の原則と why を定める。
具体値（テストコマンド・テストランナー・数値目標・hooks の具体設定）は各案件の CLAUDE.md と SKILL.md が持つ。
原則が依存するのは役割（commit 前検証・振り返り・TODO 管理）で、`lw-commit` 等はその実装名。

本書の構成:

- 回し方: 二重ループ構造 / テスト戦略
- 強制の仕組み: ガードレールと配置層 / AI コーディングのガードレール
- 導入: ロードマップ

成果物の設計判断: [[dev-methodology-CLAUDE.md設計]] / [[dev-methodology-settings.json設計]] / [[lw-kit-スキル設計-lw-tdd]] / [[lw-kit-ガイド設計-dev-guide]]

本文で定義なしに登場する前提:

- issue の ☔ TODO: 進行中タスクのチェックリスト。テストシナリオの 1 行がそのまま TDD サイクルの作業単位
- `/lw-commit`: commit ワークフロー skill。言い訳対戦表でセルフチェックを促す
- `/lw-retro`: 振り返り skill。リファクタ要否や TDD 違反の自己点検

## 二重ループ構造

開発ワークフローは 2 つのループで構成する。

### 外側ループ: explore-plan-code-commit

インタフェース設計のループ。「何を作るか」「どう変えるか」を決める。

1. **Explore**: 設計書・既存コードを読み、問題を理解する。変更はしない
2. **Plan**: 実装計画を立てる。テストシナリオを TODO リストに書き出す
3. **Code**: 内側ループ（Red-Green-Refactor）を回して実装する
4. **Commit**: 全テストグリーンで commit。設計書・openapi 等の同期を確認

小さな変更（typo / ログ 1 行 / リネーム）では Explore / Plan を飛ばしてよい。

### 内側ループ: Red-Green-Refactor

実装設計のループ。TODO リストの項目を 1 つずつ消化する。

1. **Red**: テストを 1 つ書き、実行して失敗を確認する
2. **Green**: テストを通す最小限の実装を書く
3. **Refactor**: テストがグリーンのまま重複を除去し構造を改善する

1 周を小さく回す（目安 15-30 分）。
TODO リストから 1 つ取り出し → Red → Green → Refactor → 次の 1 つ、を繰り返す（「AI コーディングのガードレール」の「シナリオ列挙→1 つずつ」参照）。

Green の判定は複合条件: テスト pass + typecheck pass。テストだけ通っても型が壊れていれば Green ではない。
削除を含む変更は expand-contract の順に並べる（新 → 移行 → 旧削除）。逆走すると型が壊れて外側ループに持ち越す事故になる。

### 設計書ファーストと TDD の関係

設計書は外側ループ（インタフェース設計）に属する。
TDD は内側ループ（実装設計）に属する。
両者は競合しない。Canon TDD が分けた「振る舞いがどう呼び出されるか」と「どう実装するか」の分離に対応する。

## ガードレールと配置層

ルールをどこに置き、どう強制するか。層の定義・割当基準・昇格経路を扱う。

ルールを 3 つの層に分けて配置する。
判定基準: 「必ず・例外なく起きるべき」→ 自動実行、「状況判断が要る」→ 助言。

遵守率の認識:

| 層               | 性質                                                  | 遵守率       | 配置先       |
| ---------------- | ----------------------------------------------------- | ------------ | ------------ |
| rules（助言）    | コンテキストに入るが、実際に手を動かす頃には忘れがち  | 低           | 助言層       |
| issue の ☔ TODO | チェック付ける/付けないがあるからまだやる             | 中〜高       | 運用の仕組み |
| skill            | やる直前に context に入るから忘れない。毎回手順を踏む | 高           | skill 層     |
| hooks            | 勝手に fire するから間違えようがない                  | 最高（自動） | 自動実行層   |

この認識がガードレールの割当を決める。手順の強制が要るものは rules ではなく skill に置く。

### 助言層（CLAUDE.md / rules）

Claude が参照する指示。守られないことがある。

- 二重ループの流れ（案件 CLAUDE.md の開発ワークフローセクション）
- テストを書くタイミングと判断基準
- コミット規約
- テストランナーの使い分け
- リファクタと機能追加を混ぜない

### 自動実行層（hooks）

ライフサイクルで必ず走るシェルコマンド。

- `PostToolUse`（`Write`/`Edit` 後）: 自動整形（formatter）
- `PreToolUse`（`Bash` で `git push` 検知）: lint + test ゲート。失敗で push をブロック

commit ゲート vs push ゲート: 設計書は「全テストグリーンで commit」だが、hook を掛けるタイミングは commit 時と push 時の 2 択がある。commit 時ゲートは赤い commit を防ぎ二分探索しやすくなるが、摩擦が増える。push 時ゲートは摩擦が少ないが赤い commit が積まれる余地がある。hook 導入時にどちらに掛けるか判断する。

### permission 層（settings.json）

自動許可と危険操作ブロック。

- allow: テスト / typecheck / lint 等の反復コマンド（具体値は案件のパッケージマネージャに合わせる）
- deny: `git push --force` / `rm -rf` / DB 破壊操作

### 割当の判定

| ルール                             | 層                                                 | 理由                                       |
| ---------------------------------- | -------------------------------------------------- | ------------------------------------------ |
| テストを実装前に書く               | 助言（案件 CLAUDE.md）                             | 状況判断が要る（テスト不要なケースがある） |
| テストを削除/skip して通すのを禁止 | 助言（案件 CLAUDE.md）、守られなければ hook に昇格 | 原則は助言で十分、再発したら自動実行に     |
| Red で実行して失敗を確認           | 助言（案件 CLAUDE.md）                             | テスト実行の判断は文脈依存                 |
| push 前の lint + test              | 自動実行（hook）                                   | 例外なく走るべき                           |
| 自動整形                           | 自動実行（hook）                                   | 例外なく走るべき                           |
| テスト・ビルドコマンドの自動許可   | permission（settings.json）                        | permit prompt の削減                       |
| 破壊操作のブロック                 | permission（settings.json）                        | 安全弁                                     |

### エスカレーション経路

守られなかったときの昇格判断。

```
助言層（案件 CLAUDE.md / rules）— nudge: いつ skill を使うか、一般原則
  + /lw-tdd skill — 手順: Red-Green-Refactor を回す。遵守率が高い
    ↓ それでも守られなかったら
hooks（自動実行: push 前ゲート等）
  ↓ 最終手段
フレームワーク導入（`superpowers` 等）
```

助言層と /lw-tdd skill は補完関係。助言層が「そろそろ /lw-tdd 使ったら？」と nudge し、skill が手順を回す。
hooks への昇格は実績ベース（違反事例が繰り返されたら）。

tdd_guard（テストファイル存在チェック hook）は不採用。理由: 本設計書が「テストを実装前に書く」を「状況判断が要る」として助言に割り当て済みで、自動実行層の資格がない。代理指標（テストファイルの存在）が弱く、除外リスト保守の負担と誤検知が自動実行層全体の信頼を毀損する。

## AI コーディングのガードレール

AI がやりがちな失敗モードと、それを防ぐ具体ルール。どの層に置くかは「ガードレールと配置層」で扱う。

### 必須ガードレール

- **Red 確認必須**: テストを書いたら実行して失敗を確認してから実装に進む。AI は Red 確認を飛ばしがち
- **テスト削除・緩め禁止**: テストを通すためにテスト自体を削除・コメントアウト・skip しない。テストが間違っていると判断した場合は理由を添えてユーザー確認
- **シナリオ列挙→1 つずつ**: テストシナリオを TODO リストに列挙し、1 つずつ Red-Green-Refactor に変換する。10 個一気に書かない
- **証拠提出**: Red の失敗出力を貼ってから実装に進む。Green の成功出力も貼る。完了報告にもテスト実行出力を含める。成功の主張だけで終わらせない。証拠は三点セット（実行コマンド / exit code / 実出力）で、要約ではなく実物を貼る
- **自分が書いたものだけテストする**: フレームワーク・ライブラリ自体の動作テストは書かない
- **外部依存だけモック**: DI の対象は制御不能な外部依存（LLM / DB）のみ

## テスト戦略

何をどこまでテストするか、テストの速度・ランナー・カバレッジの方針。

### 何をテストするか

条件分岐 / ループ / 操作 / ポリモフィズム、ただし自分が書いたものに限る。
目安は「不安が退屈に変わるまで」。

### 何をテストしないか

- フレームワーク・ライブラリ自体の動作（zod / Next.js / AWS SDK）
- セキュリティ・負荷テスト・探索的テスト（TDD の外、専門領域）
- 信頼できると考える理由がある他人のコード

### テスト速度

テストは速く保つ。
内側ループ 15-30 分はテストスイートが数秒で走る前提。
遅いテスト（統合系・E2E）は別系統に隔離し、内側ループでは速いテストだけを回す。

### テストランナーの共存

案件ごとに案件固有設定で定義する。
共存パターン例: アプリ本体のテスト（`node --test` + tsx）と UI コンポーネントテスト（vitest + Storybook）の 2 系統。

### CDD / Visual TDD

TDD がロジック層、CDD / Visual TDD が UI 層を担う。
Storybook は UI カタログではなくテスト基盤。stories がテストケースとして機能する。

### カバレッジ

行カバレッジは目的ではない。
「コードのカバレージではなく、状態のカバレージをテストすること」。
数値目標は CI で強制できる利点があるので案件固有設定で設定してよいが、数値達成を自己目的化しない。

### LLM プロンプト回帰テスト

TDD 文献の守備範囲外だが、LLM を使うプロダクトでは避けて通れない。

- 実行タイミング: LLM プロンプトを変更したとき、および同期・検証フェーズ
- 実行者: ユーザー手動（API キーが必要なため、キーを読み込むラッパー経由で実行する）
- ワークフロー上の位置: 同期・検証フェーズの品質検証として実行。FAIL や品質劣化があればプロンプトシナリオループに入る
- Claude Code が自分で実行しない（API キー運用上の制約）

プロンプトシナリオループ: テスト期待値を厳しくする（Red）→ プロンプト調整（Green）→ ユーザーが実行 → 結果確認の繰り返し。
コードシナリオ（検証ロジック / フォールバック等）を先に完了してからプロンプトシナリオに入る。
品質を構造的に保証する仕組み（検証 + フォールバック）はコードシナリオで作り、プロンプトはチューニングに専念する。

各案件の案件固有設定で具体的なコマンド（`npm run test:prompt` 等）を定義する。

## 導入ロードマップ

何をいつ導入するか。助言から始めて実績を見て昇格する。

### すぐ

- skill 層: `/lw-tdd` で内側ループを回す
- 助言層: 案件 CLAUDE.md に開発ワークフロー / コミット規約 / テストランナー共存を整備
- permission 層: 案件 settings.json に allow / deny を設定
- 既存 skill 連携: `/lw-commit` / `/lw-retro` に TDD 観点を追加

### 次（実績を見て判断）

- `PostToolUse` hook で自動整形
- `PreToolUse` hook で push 前の lint + test ゲート（commit 時か push 時かは導入時に判断）
- 助言層のルールが守られない項目があれば hook に昇格

### 将来検討

- subagent 分離: 採用済み。1 シナリオ = 1 subagent で context を隔離する（ドッグフーディングで遵守率維持に有効と確認。詳細は [[lw-kit-スキル設計-lw-tdd]]）
- MCP: gh CLI + AWS CLI で足りる。Playwright MCP は E2E を本格化するときに
- dev-methodology 抽出の検証: 2 案件目が同じワークフローを案件固有設定に落とすとき、本設計書の汎用部分が実際に再利用できるか確認する
