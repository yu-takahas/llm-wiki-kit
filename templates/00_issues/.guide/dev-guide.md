# 開発ガイド

## 対象タスク

使う: コードを書く issue（機能追加 / バグ修正 / リファクタリング / 移行作業）。
使わない: skill 設計 / wiki page の作成 / 調査系のタスク。

---

開発 issue を書くときのメニュー。
コマンド例はプロジェクト固有のもの。案件のスタック・規約に合わせて読み替える。
該当するセクション・行だけ issue にコピーする（該当しないものはコピーしない）。
コピーするのは着手する時。着手が遠い issue に全区切りを積むと、TODO の分量が作業の重さを誤認させる。
起票だけして着手が先になる issue は、準備と Explore だけ置き、以降の区切りは着手時にコピーする。
issue に既に区切り構造がある場合、guide の区切り見出しは持ち込まず該当行だけ差す。
項目の追加・並び替えは自由。
小さい変更（typo / config / ログ 1 行）はこのガイドごとスキップしてよい。
ガイドごとでも行単位でも、スキップしたら 🪣 経緯に 1 行残す（コピー漏れとスキップ判断は guide 側からは区別できないため）。
`(ユーザー)` マークはユーザー本人が手を動かす項目（lead は実行せず、完了を待つ）。

---

## 設計仕様

Explore で設計書から確認した仕様をまとめる。
issue を読んだだけで何を作るか分かる状態にする。

## 参考パターン

既存コードのどこを参考にするか。
ファイルパス + 関数名・コンポーネント名で。

消化はチェックで表す。

### 準備

- [ ] `git checkout -b <issue 名>`（worktree で作業する場合は worktree を切る）

### Explore

issue の 🌂 中断点 + CLAUDE.md + rules で大部分は自動。
以下は自動では拾えないもの。

- [ ] issue の鮮度チェック: 🪣 経緯の最新エントリ（無ければ `created:`）と今日の日付の差を見る。日が空いていたら issue に書いてある主張（「〜は OK」「〜は完了」等）を実ファイルと突き合わせて、ずれがあれば issue 更新を提案する
- [ ] 前回から codebase が変わっていないか確認する（`git log --oneline -10`）
- [ ] 関連する設計書・既存コード・テストを読み、結果を issue の「設計仕様」「参考パターン」セクションに書き残す

### Plan

設計書の扱い:

- 仕様が既にあり変更なし → そのまま従う
- 仕様がない → Plan の前に設計書へ仕様を書く
- 仕様があるが今回の変更で設計が変わる → 先に設計書を書き換えてから Code に入る

- [ ] テストシナリオを Code 区切りに列挙する（1 行 = 1 Red-Green-Refactor サイクル、行頭に `シナリオ:`）
- [ ] シナリオの内容を確認する（追加・修正があれば更新）
- [ ] UI を変える場合: コンポーネントカタログ（例: Storybook）で作る対象を決める（新しい部品 → Component / 新しい画面 → Page / 既存画面の修正 → その Page）
- [ ] UI を変える場合: 対象がとる状態を story にする（読み込み中 / 空 / エラー / データ表示 等）

story は Plan で書き切る。Code のシナリオには持ち越さない。

### Code

シナリオは各 Code 区切りに書く。
シナリオ行は `シナリオ:` を頭に付けて作業行と区別する（`/lw-tdd` が対象を選別するため）。

`/lw-tdd` を呼んでシナリオを 1 行ずつ消化する。
気づいたシナリオは途中で追記していい。
シナリオに乗らない作業行（関数削除 / コード移行 / revert 等）は普通の TODO として混ぜてよい（`/lw-tdd` の対象外）。
削除を含む変更は expand → migrate → contract の順に並べる（新しいものを作る → 利用側を移行する → 旧を削除する）。逆走すると型が壊れて外側ループに持ち越す事故になる。
削除が複数区切りにまたがる場合は、contract を各区切りに混ぜず最後の「### Code — 掃除」区切りにまとめてよい（移行中は新旧併存を許す）。掃除区切りは作業行だけの区切りなので、最後に全スイートで緑を確認する。
作業行だけの区切りもある。その場合 `/lw-tdd` は呼ばず、区切りの最後に全スイートを走らせて緑を確認する。
区切りの見出しは「### Code — <内容名>」の形で、番号ではなく内容名を付ける。
サイクル固有の注意はシナリオ行の直下に書く。
共有テーブルの行を足すだけの変更は、配線 1 サイクル + テーブル駆動テストに畳む。

同期と `/simplify` は各区切りの中に入れる。
`/code-review` と `/verify` は「仕上げ」で issue 全体に 1 回。
途中でレビューを足すのは、後続の区切りが同じコードを複製・改造する予定があるときだけ。

シナリオの書き方:

- 優先順: ハッピーパス → エッジケース → エラー系
- 層別（DB 層 / API / 画面 / LLM プロンプト 等）に整理すると見やすい
- 既存テストが assert している文言・挙動を変える場合は、その更新もシナリオに数える。新規シナリオを足すだけだと既存テストが赤くなるので、変更前の文言を grep して洗い出す
- LLM プロンプトを含む場合は 2 種に分けてラベルを付ける
  - コードシナリオ: 検証関数・フォールバック等。`/lw-tdd` で自走
  - プロンプトシナリオ: 実 LLM の出力品質。(ユーザー) API キーを読み込ませてプロンプト回帰テスト（例: `npm run test:prompt`）をバッチ実行（1 行 = 1 サイクルは適用しない）。コードシナリオを先に固めてからプロンプトを差し替える

区切りの中身（上から順に実行する）:

- [ ] シナリオ: ...
- [ ] シナリオ: ...
- [ ] 同期: ...（「変更内容に応じた同期」から該当行を差す）
- [ ] `/simplify` で品質掃除。デフォルトは lead 直接実行。大 diff（400 行超 / 10 ファイル超）のみ fan-out を検討
- [ ] `/lw-commit`

#### 変更内容に応じた同期

区切りごとに、該当する行だけ上の区切りに差す。

- [ ] API を変えた場合: API 定義（例: OpenAPI スキーマ）の再生成 + 型定義との突合
- [ ] DB スキーマを変えた場合: テーブル定義の更新 + seed / fixture の追随
- [ ] LLM プロンプトを変えた場合: (ユーザー) API キーを読み込ませてプロンプト回帰テストで品質検証。FAIL やフォーマット劣化があればプロンプトシナリオループで改善（下記参照）
- [ ] UI コンポーネントを変えた場合: 既存の story / スナップショットが実装と乖離していないか確認、必要なら修正
- [ ] env 変数を追加した場合: `.env.example` 更新
- [ ] コマンドや規約を追加した場合: 案件の CLAUDE.md に追記
- [ ] 設計書の同期（既に記載済みなら確認だけでよい。全量は `40_project/<案件>/` を見る。例: `<案件>-アーキテクチャ設計` / `<案件>-データモデル設計` 等の派生 page）

#### プロンプトシナリオループ

LLM プロンプトの品質改善は `/lw-tdd` の対象外（API キーが要るためユーザー手動）。
以下のループで回す:

1. プロンプト回帰テストのアサーションを理想の出力に合わせて厳しくする（Red）。LLM 出力の assert は完全一致ではなくキー概念の部分一致（non-null + 特定語を含む 等）にする
2. プロンプト / few-shot / 検証ロジックを調整する（Green）
3. (ユーザー) API キーを読み込ませてプロンプト回帰テストを実行
4. FAIL があれば 2 に戻る。flaky なら LLM 揺れの範囲かテスト期待値を緩和するか判断

効かないときの梯子（上から順に試す）:

- プロンプト文言の追記・明確化
- few-shot 例の追加
- schema 構造の変更（optional → required 化、describe、フィールド順での CoT 誘導）
- モデル切替で切り分け（上位モデルで通るなら現行モデルのプロンプト改善余地あり、上位でも落ちるなら設計変更が必要）

コードシナリオ（LLM 出力の検証関数・フォールバック等）で品質を構造的に保証し、プロンプトシナリオでチューニングする。
コードシナリオを先に完了してからプロンプトシナリオに入る。

### 仕上げ（issue 全体で 1 回）

- [ ] `/code-review` で diff レビュー。デフォルトは lead 直接実行。fan-out 時は有益な angle（cross-file / conventions / altitude）に絞る。指摘された bug は `/lw-tdd` のバグ修正モードで修正（再現テスト先行）
- [ ] `/verify` で実アプリ確認（非自明な変更の場合、test-only diff ではスキップ。UI 変更時はブラウザで目視）
- [ ] `gh pr create` で PR を作る（既存 PR がある場合は push で更新）
- [ ] (ユーザー) PR にスクショを貼る（UI 変更がなければスキップ）。lead はテーブル骨組み（画面名 / 確認内容 / Screenshots 空欄）を用意する
- [ ] CI が通っていることを確認する
- [ ] (ユーザー) Merge PR ボタンを押す
- [ ] `git branch -D <branch>`（squash merge のため `-d` は失敗する）
- [ ] `git push origin --delete <branch>`（remote ブランチも削除）
