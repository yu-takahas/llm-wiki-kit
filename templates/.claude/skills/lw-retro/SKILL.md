# lw-retro

反映（＝振り返り）に特化した探索 skill。
観察を集め、反映先を判断し、骨子確認して反映する。
設計判断の why は `$KIT/docs/lw-kit/40_スキル設計/lw-kit-スキル設計-lw-retro.md`、本ファイルは実行手順の how。

入力: `$ARGUMENTS` は「jsonl から読め」等の補足指示（省略可）。

## 全体像

```text
1. 読み返し → 2. 観察収集 + 点検（配線 / TDD）（探索強制） → 3. リファクタ検討 → 4. 反映先判断 → 5. 骨子提示・確認・反映 → 棚卸しチェック → 完了報告
```

肝は探索モードで広く集めること。
再発の扱いは責務 4 参照。
各責務は該当なしで終わることもありうる。
該当なければ skip して次へ進む。

## 言い訳対戦表（起動前チェック）

探索強制は領域別走査 + 探索モード宣言の 2 つ（詳細は責務 2）。

| 言い訳                             | 現実                                                                     |
| ---------------------------------- | ------------------------------------------------------------------------ |
| 反映するものは無い                 | 領域（作業スタイル / feedback / wiki / project / memory）を必ず一巡問う  |
| ざっと見て該当なし                 | 探索モードに入れ（→ 責務 2）                                             |
| 観察が出たので全部 lead に上げる   | 再発は事例行 +1、新規差分だけ骨子提示（→ 責務 4）                        |
| 触ったのは一部だが全部見るのは面倒 | リファクタ検討は今セッションで触ったファイル全部（一部でない）           |
| 宣言は doc-review が読むファイル   | 宣言の配線を更新するのは蓄積側、retro が主導線（検出は責務 2、反映は 5） |

## 事前条件

- 反映先の構造（作業スタイル / `50_feedback/` / `30_wiki/` / `40_project/` / memory）を把握している
- 振り返り材料の所在（context window / jsonl）を確認

## 手順（5 責務）

### 1. セッション読み返し

既定は context window から読む。
lead が「jsonl から」と指示した時だけ jsonl を読む（context が greedy に縮んだ時の外部記憶）。
jsonl は全文を Read せず、`grep` で該当行を絞ってから読む（全文ロードは context を縮めて探索を阻害する）。
対象は user 発話と assistant のテキスト応答で、tool_result / system reminder は捨てる。

### 2. 観察収集（探索強制）

探索モードに切り替える。
活用でなく発散、「該当なし」で流さず掘る。
本責務は無条件の領域別走査 1 つと、条件付きの点検 2 つ（配線点検 / TDD 自己点検）からなる。
いずれも候補を挙げるところまでで、実際の Edit は責務 5 で行う（責務 4 の重複検出を通すため）。

冒頭で `/tmp/lw-review/<issue 名>/` を 1 回だけ確認する。
今セッション開始以降の日時のレビュー結果があれば、知見抽出の材料として使い、同時に配線点検の起動条件が成立したと判定する。

#### 領域別走査

領域別に必ず一巡問う: 作業スタイル / `50_feedback/` / `30_wiki/` / `40_project/` / memory。
`50_feedback/` は `Glob(50_feedback/*.md)` でファイル一覧を走査し、セッション中の出来事に該当するファイル（知見・観察・指針・プロファイル）に追記先がないか確認する。
プロファイル（`feedback-プロファイル-*.md`）にセッション中のレビューで検証された seed があれば、`[confirmed]` への昇格候補として挙げる。
既存 seed に当たらない観点がセッション中のレビューで新しく確認された場合は、プロファイルの該当層セクションへの新規追記候補として挙げる（既存 seed の昇格だけで済ませない）。
各領域「無し」は許す（水増しを誘発しないため）。

#### doc-review 宣言の配線点検

起動条件は、冒頭の確認でレビュー結果があったか、worker に設計書を渡したか。
どちらも無ければ skip する（宣言は多数あり、全件走査は得られるものに対してコストが高い）。
`Glob(**/.doc-review.md)` で宣言を発見し、今セッションで触った領域の宣言に絞って次を問う。
ルート `.doc-review.md`（ルーター）の参照先も対象に含める（`Glob` は cwd 配下しか走査せず、外部 repo の宣言はルーター経由でしか辿れない）。

- 新しく作った / 更新した知見・プロファイルが、宣言の参照欄に載っているか
- 規範の注記（finder に渡す範囲の絞り込み）が実態と合っているか（広すぎ / 狭すぎ）
- 今セッションで新設した `40_project/<案件>/` に宣言があるか（未作成は `Glob` のヒットには出ないので問いの形で確認する）

各項目「無し」は許す（領域別走査と同じ）。

#### TDD 自己点検

実装 TODO を含むセッションのみ。
設定・文書だけのセッションでは skip する。

- Red を飛ばした箇所はなかったか
- Green で過剰実装しなかったか
- 型壊れを外側ループへ持ち越さなかったか

### 3. リファクタ検討

`git diff --stat` + `git status`（untracked 含む）で今セッションの変更ファイルを洗い出し、変更量が大きいファイルから優先的に見直す。
軽い編集ほど「◯月✗日追記」式に履歴を継ぎ足す劣化が出やすい、これを警戒する。
判断軸は再掲せず参照する（type 役割 / 陳腐化しない書き方 / 出典は `wiki.md`、編集規約は `wiki-style.md`）。
観察収集と同じ探索の所作なので、探索強制と出口の重複検出を共有する。

### 4. 反映先判断

収集した観察・知見の反映先を判断する。

- lead の作業スタイル観察 → [[feedback-観察-作業スタイル]]
- レビュー知見・失敗事例・指針 → `50_feedback/feedback-*.md`（該当ファイルに追記）
- 汎用知識 → `30_wiki/<title>.md`
- 案件固有 → `40_project/<案件>/<title>.md`
- 個人の好み / セッション越え動作 → memory
- レビュー観点（昇格・新規追記）→ `feedback-プロファイル-*.md` の該当層セクション
- 配線ずれ → 該当する `.doc-review.md`（配線に関する事項のみ、観点そのものは書かない）
- TDD 規律の崩れ → [[feedback-観察-失敗事例]]

知見エントリに書かないもの:

- 仕様が未確定の設計判断（SKILL.md / CLAUDE.md / rules 等にルール化される予定のものは実装後に正本が生まれる。未確定段階で書くと仕様変更時に実態と乖離する）
- 知見ファイルのスコープ外（各知見ファイル冒頭の「書かない」を参照）

出口の重複検出: 既存記述と被る観察は drop せず、再発として扱う。
作業スタイル台帳（[[feedback-観察-作業スタイル]]）への反映は台帳冒頭の追記ルールに従う（既存項目なら事例行 +1、新規または迷うなら INBOX）。

### 5. 骨子提示 → lead 確認 → 反映

残った反映候補を骨子で提示し、lead 確認の上で Edit 反映する。
自走度は 2 段。

| 段     | 対象                                                                                                          | 動作                                          |
| ------ | ------------------------------------------------------------------------------------------------------------- | --------------------------------------------- |
| 軽微   | 既存 page への事例追記レベル / seed の昇格 / プロファイルへの観点追記 / 宣言の参照欄修正                      | 自走 Edit（確認なし）                         |
| 要確認 | 新規 page 作成（宣言の新規作成を含む）/ memory 保存 / 主要セクション書き換え / 別リポジトリの宣言への書き戻し | 骨子・要点を提示して lead 確認 → Edit / Write |

memory 保存は今回限りの指示と長期方針の区別が lead にしか付かないため、必ず確認する。
反映先の判断に迷ったら要確認側に倒す（聞く方が安い）。

## エラーハンドリング

| ケース                               | 方針                                                            |
| ------------------------------------ | --------------------------------------------------------------- |
| jsonl 指示だが path 不明             | session の jsonl path を lead に確認して停止                    |
| 新規観察がゼロ（全て既存項目の再発） | 再発の事例行追記だけ行い「新規の観察なし、再発 N 件追記」と報告 |

## 必須動作

- 収集は探索モードで広げる。再発の扱いは責務 4 に従う
- 走査の途中経過は報告せず、完了報告 1 回に寄せる（各領域・各点検の該当なしを個別に報告しない）
- memory 保存は必ず lead 確認
- `/lw-retro` は反映先 page / doc-review 宣言 / memory 以外を触らない（振り返りフローに閉じる、log / index 追記は lead 自走）
- 完了報告に棚卸し起動条件の判定結果を必ず含める（成立 / 不成立とも数値付き）

## 棚卸し起動条件チェック（責務 5 の後に実行）

5 責務の完了後に以下の計測を実行する。
棚卸し自体はこの skill では実行しない（棚卸し ＝ 整理は retro ＝ 蓄積と責務が異なる）。

```bash
bash .claude/skills/lw-retro/tanaoroshi-check.sh 50_feedback/feedback-観察-作業スタイル.md
```

シェルスクリプトを別ファイルに外出ししている理由: SKILL.md の `$ARGUMENTS` 展開がスクリプト内の変数参照を壊すため。

起動条件（いずれか成立で棚卸しを提案）: 前回棚卸し日より後の事例行 10 件以上 / INBOX 5 件以上 / 対策済み再発 1 件以上（当日分は数えない、スクリプトの実装に合わせる）。
前回棚卸し日行が無い場合は全件カウント（成立側に倒す）+ 行の欠落を報告する。

条件成立時の報告例: 「棚卸しの起動条件が成立しています（事例 N 件 / INBOX M 件 / 再発 K 件）」。
やるか・いつやるかは lead に委ねる。
