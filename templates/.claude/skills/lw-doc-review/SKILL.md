# lw-doc-review

層別 finder 並列 → merge → 指摘ファイル出力に特化した skill。
修正は `/lw-fix-review` が担う（doc-review は指摘のみ）。
設計判断の why は `$KIT/docs/lw-kit/40_スキル設計/lw-kit-スキル設計-lw-doc-review.md`、本ファイルは how + 具体値の正本。

入力: `$ARGUMENTS` はファイルパス / `@` 付きパス / 自然言語（「さっき作ったファイル」等）。

| オプション         | 意味                                                                                    |
| ------------------ | --------------------------------------------------------------------------------------- |
| (なし)             | プロファイルにセクションがある層だけ起動（読み手は `## 読み手` 次第、通例は起動しない） |
| `--quick`          | 1 体が 4 層を見る（層外 finder なし・合議マークなし・コスト低・実時間は並列より遅い）   |
| `--full`           | 4 体フル並列 + 通例（モデル使い分け込み。読み手はプロファイルゲート維持）               |
| `--profile=<種別>` | プロファイルを明示指定（自動判定を skip）                                               |

## 全体像

```text
1. 入力解決とロード → 2. effort 判定 → 3. finder 並列 spawn
  → 4. merge → 5. 指摘ファイル Write → 6. サマリー報告
```

quick でも full でも 6 ステップ全てを通す。quick で merge が自明（1 finder）でも層順ソート + 指摘ファイル Write は省略しない。fix-review の入口を `/tmp/lw-review/` に統一するため。

## 言い訳対戦表（起動前チェック）

| 言い訳                                             | 現実                                                                                                                                                                                 |
| -------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| full にした方がいい気がする                        | フル化は明示オプトイン（`--full`）。デフォルトはプロファイルゲートで層を選ぶ                                                                                                         |
| プロファイルは内容を読めば分かる                   | LLM 内容判定は却下済み。4 段階判定に従い、落ちたら聞く                                                                                                                               |
| merge 手順は件数が少ないから省略                   | 引用 grep 再計算と合議判定は件数に関わらず通す                                                                                                                                       |
| quick だから merge と Write は省略してサマリーだけ | quick でも指摘ファイルは `/tmp/lw-review/` に Write する。fix-review の入口統一                                                                                                      |
| 直せそうな指摘だから直しておく                     | 直さない。doc-review は指摘まで。修正は `/lw-fix-review` の責務                                                                                                                      |
| 指摘が多いから厳選して報告だけ                     | 全件を指摘ファイルに記録し、表示だけ畳む                                                                                                                                             |
| 通例の指摘も層順に混ぜて merge する                | 層外レポート。merge にも合議判定にもかけない（引用を持たないため）                                                                                                                   |
| 通例の欠落がプロファイルと近いので省く             | 完全一致なら finder が外す。近いだけなら「プロファイル照合」欄に違いを書いて出す                                                                                                     |
| 通例が全部「該当なし」で返ってきた                 | 検索と照合の痕跡があるか見る。痕跡のない「該当なし」は、web search をしていないものとして扱う                                                                                        |
| finder に文書の背景も渡すと親切                    | 記述・範例コンテキストは渡さない（背景を渡すと finder が既知の文脈で読み、初見の読者が詰まる箇所を検出できなくなる）。層 finder に渡すのは規範のみで、層外 finder には規範も渡さない |
| 規範コンテキストが多いから関連しそうなものだけ読む | 宣言に載っているものは全部読む。範囲を絞りたいなら宣言の注記で制御する                                                                                                               |

## 事前条件

- **llm-wiki ルートの特定**: cwd に `40_project/` があればそこ。なければ add-dir のうち `40_project/` を持つパスを llm-wiki ルートとする。以降の `40_project/` / `1_issues.md` 等の相対パスはすべて llm-wiki ルート起点
- アクティブ issue 名の把握: llm-wiki ルートの `1_issues.md` の WIP セクションから取得。なければ `_no-issue/`
- 対象ファイルの存在確認

## 層定義

4 層 finder のベースライン。各 finder にはこの行と、プロファイルの該当セクションを渡す。

| 層   | 見る                                                                     |
| ---- | ------------------------------------------------------------------------ |
| 骨格 | セクション構成の妥当性、論理の流れ、スコープ、分量バランス               |
| 中身 | 主張の根拠・論理の飛躍、事実の正確性、具体例の適切さ、用語の一貫性       |
| 文章 | 冗長 / 説明不足、トーン・文体の一貫性、曖昧な指示語・主語欠落            |
| 表記 | 誤字脱字、表記ルール準拠、同一概念の表記揺れ、Markdown 記法、frontmatter |

各層の「見ない」は他 3 層と層外 finder の担当分で、finder プロンプトに列挙して渡す。
境界が紛れやすい 2 点: 来歴・時系列が適切かの判断は中身層。文の構造とトーンは文章層。

層外 finder（読み手・通例）の定義は各テンプレートが持つ。
層順（骨格→中身→文章→表記）は「直す順序」で、上位が変われば下位の前提が変わる。

## 手順（6 ステップ）

### 1. 入力解決とロード

`$ARGUMENTS` からオプション語（`--quick` / `--full` / `--profile=<種別>`）を先に切り出し、残りを対象ファイルの指定として扱う。
オプション語を残したまま対象ファイルを探すと、オプションが自然言語の一部として素通りして体制判定に効かない。

切り出した後、対象ファイルを特定し Read する。特定できなければ聞く。

**宣言ファイルの発見（Glob + ルーター）:**

llm-wiki ルートで `Glob(**/.doc-review.md)` を実行し、全宣言ファイルを取得する。
対象ファイルのパスと比較し、最寄り祖先ディレクトリの `.doc-review.md` を宣言として使う（以下 walk-up）。
ルートの `.doc-review.md` はルーターなので宣言候補から除外する。

発見なし、またはルーターのみヒットした場合、llm-wiki ルートの `.doc-review.md`（ルーター）を読む。
外部 repo の対象ファイルは Glob で拾えないため、ルーター経由で誘導する。
ルーターは対象ファイルのパスを上から順に前方一致で照合し、最初にマッチした行の参照先を宣言として使う。
ルーターの解決規則:

- 上から順の最初一致（最長一致にしない）
- パターンは前方一致のディレクトリパス（glob でなく）
- 「それ以外」行を必須とし、既定動作を暗黙にしない
- 参照は 1 hop 限定（参照先がルーターだったらエラー）

walk-up でもルーターでも見つからなければ宣言なしで続行（ベースラインのみ、正常系）。
宣言内の参照はパス直書き（dot ファイルのため `[[link]]` が Obsidian で効かない）。

**プロファイル判定（4 段階、上から順に適用）:**

1. ユーザー明示指定（`--profile=設計書` 等）
2. 宣言ファイルのプロファイル欄の glob マッチ。glob は対象を具体的に絞る（広い glob は段階 2 で先にマッチし、段階 3 の type 対応表が使われなくなる）
3. frontmatter の type から対応表で推定:

| frontmatter type                                | プロファイル |
| ----------------------------------------------- | ------------ |
| design                                          | 設計書       |
| concept / entity / source / synthesis / project | wiki         |

4. ユーザーに聞く。選択肢に「(c) この対応を宣言に保存して次回から自動判定」を同梱。lead が (c) を選べば宣言に Edit で追記する

定義済みプロファイル: エッセイ / 技術ブログ / 設計書 / wiki（`50_feedback/feedback-プロファイル-*.md`）。
プロファイルは宣言ファイル側で自由に追加定義でき、SKILL.md は判定ロジックのみ持つ。

**知見のロード:**

宣言の知見欄に記載された `feedback-知見-*.md` を Read し、各エントリの層フィールドで振り分け準備する。

**規範コンテキストのロード:**

宣言のコンテキスト・規範欄に記載されたファイルを Read する。注記があれば注記の範囲だけ渡す。
記述・範例コンテキストは読まない（finder に渡さない。fix-review が使う）。

**宣言メタ指摘の検出:**

規範コンテキストを読む際に、参照先不存在・注記と実物の明白な矛盾に気づいたらメモしておく（指摘ファイル冒頭に出力）。

### 2. effort 判定

判定材料:

- プロファイルのセクション有無（= 起動判定。`## 読み手` は完全一致で判定、`## 読み手の定義` と混同しない）
- ユーザーの明示オプション（`--quick` / `--full`）

**体制表（フル時のモデル割当）:**

| 層     | モデル | 根拠                                                                                      |
| ------ | ------ | ----------------------------------------------------------------------------------------- |
| 骨格   | opus   | 文書全体の俯瞰と論理評価に推論力が必要                                                    |
| 中身   | opus   | 同上                                                                                      |
| 文章   | fable  | 表現の判断駆動であり fable で十分な品質が出る                                             |
| 表記   | sonnet | 明文規約のチェックリスト照合で足りる                                                      |
| 読み手 | sonnet | 読者としての反応を返す役割、推論力より自然さ                                              |
| 通例   | opus   | 外部の一般的期待と文書を突き合わせて欠落を挙げる。web search の結果を評価する推論力が要る |

表は根拠のみを持つ。起動条件は以下に一本化する。

- 層 finder（骨格・中身・文章・表記）: プロファイルにセクションがない層は起動しない。`--full` なら 4 層をベースラインで全起動。`--quick` なら 1 体が 4 層を見る（モデルは opus）
- 読み手: プロファイルに `## 読み手` がある時のみ起動する。`--full` でもこのゲートを維持する（ベースラインとなる層定義を持たないためフォールバック対象外）
- 通例: `--full` でのみ起動する。デフォルトと `--quick` では起動しない。プロファイルの `## 通例` は起動ゲートではなく、`--full` 時に探す方向のヒントとして渡す

spawn 前に体制を 1 行報告する（「中身 opus / 文章 fable / 表記 sonnet の 3 体」等）。

### 3. finder 並列 spawn

全 finder を Agent の戻り値で受ける方式で並列 spawn する。
`name` パラメータは付けない（SendMessage でアドレス可能な named agent にしない）。
通例 finder は手順に web search を含むので、web search を実行できる構成で起動する。
finder プロンプトで Write/Edit を禁止する指示を入れる（テンプレート参照）。
全 finder を 1 メッセージで同時に spawn し、全結果を待つ。

**各 finder への入力配布:**

層 finder（骨格・中身・文章・表記）:

| 入力                         | 全 finder 共通 | 層固有                             |
| ---------------------------- | -------------- | ---------------------------------- |
| 文書全文                     | はい           |                                    |
| 自層の層定義（見る/見ない）  |                | はい                               |
| プロファイルの自層セクション |                | はい（なければベースラインのみ）   |
| 自層の知見                   |                | はい（層フィールドでフィルタ）     |
| 規約ファイル                 |                | 表記のみ                           |
| 規範コンテキスト             |                | 該当する finder に（注記の範囲で） |

層外 finder（読み手・通例）:

| finder | プロファイルから渡すもの                                   | テンプレート |
| ------ | ---------------------------------------------------------- | ------------ |
| 読み手 | `## 読み手の定義` と `## 読み手`                           | 読み手用     |
| 通例   | 全文（「既にある観点は出すな」の判定に全セクションが要る） | 通例用       |

層外 finder にも文書全文は渡す。
規範コンテキストは渡さない（規範は「書かれているものの是非」の基準で、層外 finder の仕事には効かない）。
層順に入らないので層タグを持たず、merge にも乗らない。

### 4. merge

メインが全 finder の戻り値を受け取り、以下の決定論的規則で merge する:

1. **行番号の再計算**: 各指摘の「引用」文字列で文書内を grep し行番号を再計算する
2. **合議マーク判定**: 同一セクション かつ（再計算行番号の距離 ≤ 2 または一方の引用が他方の引用を部分文字列として含む）→ 合議マーク付与
3. **ソート**: 層順（骨格→中身→文章→表記）+ 重要度順（必須→推奨→任意→確認（事実）→確認（意図））
4. **再評価の判定**: 骨格に「必須」があるかを見て、ヘッダの「再評価」行に「あり（骨格に必須 N 件）」か「なし」を書く。指摘 1 件ずつには付けない（条件が文書単位なので、付けると下位層全件の列挙になる）

引用が文書内で非一意 → セクション見出しで絞る。
引用が原文に見つからない → 位置不明としてセクション末尾に配置、合議判定から除外。

層外 finder のレポート（読み手・通例）は merge 対象外（引用を持たないので規則 1 の行番号再計算が成立しない）。そのまま末尾に配置する。

### 5. 指摘ファイル Write

出力先: `/tmp/lw-review/<issue-name>/YYYYMMDD-HHMM-<対象ベースネーム>.md`

`<対象ベースネーム>` は対象ファイルのファイル名から拡張子を除いたもの（例: `SKILL` / `Dario-Amodei`）。

同名のファイルが既にある場合（同じ分に 2 回走らせた時）は上書きせず、末尾に `-2` から連番を付ける。
レビュー結果は監査ログとして残す規約なので、前回分を消さない。

```bash
mkdir -p /tmp/lw-review/<issue-name>
date '+%Y%m%d-%H%M'
```

ファイル内構成:

```markdown
# レビュー: <ファイル名>

- 対象: <パス>
- 宣言: <パス>（経路: walk-up / ルーター / なし）
- プロファイル: <種別>（判定経路: type / 宣言 / 明示 / 聞いた）
- 体制: <層(モデル) の列挙>
- 指摘: N 件（必須 A / 推奨 B / 任意 C / 確認（事実） D / 確認（意図） E）※層 finder の指摘のみを数える
- 層外レポート: 読み手 <あり / なし> / 通例 M 件
- 再評価: <あり（骨格に必須 N 件。中身以下は骨格修正後に再評価）/ なし>

---

## 宣言メタ指摘（あれば）

## 骨格（あれば）
### [重要度] タイトル
- 層 / 位置 / 引用 / 指摘 / 提案 / 根拠

## 中身（あれば）
## 文章（あれば）
## 表記（あれば）

---

## 読み手レポート（あれば）
1. 感情が動いた箇所
2. 脱落しそうになった箇所
3. 読後に残ったもの

---

## 通例レポート（あれば）
1. 同定した種別と根拠
2. 欠落一覧
   ### [重要度] 何が欠けているか
   - なぜ必要か / 出典 URL / どこに足すか / プロファイルに同観点がないことの確認
3. 該当なし（欠落 0 件のとき。何を検索し何と照合したかを 1-2 行）

---

## 合議マーク
| 箇所 | 指摘した finder | 合議数 |
```

### 6. サマリー報告

ユーザーへのサマリー表示は、重要度ごとに表示量を変える:

- 必須: 展開（全文表示）
- 推奨: 1 行リスト
- 任意: 件数のみ
- 確認: 件数のみ
- 読み手レポート: 全文表示
- 通例レポート: 全文表示（欠落は畳むと「何が無いか」が伝わらない）

宣言メタ指摘があればサマリーに含める。
サマリーの末尾に指摘ファイルのパスを出す。修正に進むかは lead が決める。

## finder プロンプトテンプレート

出力フォーマットの正本は共通骨組み。他のテンプレートは差分だけを書く。
本ファイルが 500 行を超えた時、または通例用テンプレートが独立して伸び始めた時に、モード別（full 用 / quick 用）の 2 ファイルに分ける（1 ファイルにまとめるとどのモードでも読むので削減にならない）。

### 共通骨組み（4 層 finder 用）


### 通例用テンプレート

```
あなたは文書レビューの「通例」finder。
この種の文書に一般的に求められる要素を文書の外から持ち込み、対象文書に丸ごと書かれていない要素を報告する。
書かれているものの良し悪しは見ない。ファイルの編集はしない。

## あなたの層定義
見る:
- 種別の同定: この文書が実態として何の種類の文書として読まれるかを、frontmatter type やプロファイル名でなく中身から判定する
- 一般的期待との照合: 同定した種別について「この種の文書に一般的に含まれる要素 / 読者が期待する要素」を調べ、対象文書に丸ごと存在しない要素を挙げる
- 宣言された目的に対する不足: 文書が冒頭で自ら宣言する目的に対し、達成に要る要素で書かれていないもの
- 想定読者の行動に要る情報の欠落: 想定読者が次の行動をとるのに要る情報で、丸ごとないもの

見ない（別の finder が担当）:
- 事実の真偽検証（中身の確認（事実） が担当）。書かれている前提・制約の妥当性もここに含む
- 既存セクション内の表現・構成の改善（骨格・文章が担当）
- プロファイルに既にある観点による指摘（該当層の finder が出す）
- 文書内の論理から導ける構成の抜け（骨格が担当）
- 他文書との重複・守備範囲（骨格の「スコープ」等が担当）
- 読者としての反応（読み手が担当。「自分が詰まった」でなく「この種の文書なら通常ある」を報告する）
- 欠落を埋める本文の代筆（何が要るかと根拠まで。埋め方は著者が決める）

## プロファイル（全文）
<プロファイル全文を挿入。なければ「プロファイルなし」>

プロファイルの読み方:
- 各層のセクションにある観点は、その層の finder が出す。同じ観点の欠落を報告しない
- `## 通例` は探す方向のヒントで、観点リストではない。ここに書かれた方向で調べ、見つけた要素を報告する
- `## 読み手の定義` は想定読者の同定に使う

## 手順
1. 種別の同定: 文書の中身から、何の種類の文書として読まれるかを 1 行で決める。プロファイルの種別や frontmatter の type と食い違えば、報告項目 1 にその旨を書く
2. web search: 同定した種別について、一般的に含まれる要素と読者が期待する要素を調べる
   - クエリの型: 「<種別> 構成要素」「<種別> 書き方 必須項目」「<種別> チェックリスト」「<種別> テンプレート」。`## 通例` にヒントがあれば、その方向のクエリを足す
   - 日本語の資料が薄ければ英語でも引く
   - 上限 5 回。公式ガイド・規格・定評のある解説を優先し、出典 URL を控える
3. 照合: 調べた要素のうち、対象文書に丸ごと存在しないものを挙げる。プロファイルに同じ観点があるものは外す
4. 各欠落に「なぜこの種の文書に必要か」を出典付きで書く。欠落を埋める本文は書かない
5. 外部資料の用語をそのまま持ち込まない。英語の略語や業界用語を使う時は、初出で日本語の説明を添える（例:「SOP」→「標準作業手順書（SOP）」）。読み手は外部資料を読んでいない

## レビュー対象
ファイル: <パス>
<文書全文>

## 出力フォーマット
以下の 3 項目を返す。

1. **種別と根拠**: 同定した種別と判断の根拠。プロファイルの種別と食い違う場合はその旨
2. **欠落一覧**: 上限 10 件、重要度順。確信のない欠落は捨てるか「確認（意図）」に落とす
3. **該当なし**: 欠落が 0 件なら「該当なし」と書き、何を検索して何と照合したかを 1-2 行で残す

欠落 1 件の形式:

### [重要度] 欠けている要素
- 欠落: 何が丸ごとないか
- 理由: なぜこの種の文書に必要か。出典 URL を添える
- 位置: どこに足すか（既存セクション名、または新設セクションを置く位置）
- プロファイル照合: 同じ観点なし / 近い観点があれば「<層>の「<観点>」とは <何が違うか>」

重要度: 必須 / 推奨 / 任意 / 確認（意図）。
確認（意図）は「著者が意図的に省いた可能性がある」時に使う。
確認（事実）は使わない（真偽検証はしない）。
```

## エラーハンドリング

| 状況                             | 挙動                                                           |
| -------------------------------- | -------------------------------------------------------------- |
| 対象ファイル特定不能             | 聞いて停止                                                     |
| type なし + 宣言マッチなし       | 聞く + 宣言保存の選択肢                                        |
| 宣言ファイルなし                 | ベースラインのみで続行（正常系）                               |
| finder 戻り値が空 / 形式不正     | その finder 0 件として続行 + サマリーに明記（再 spawn しない） |
| 通例が web search を実行できない | その旨をサマリーに明記（痕跡のない「該当なし」と区別する）     |
| 引用が原文にない                 | 位置不明扱い（merge 規則に従う）                               |
| アクティブ issue なし            | `_no-issue/` に出力                                            |
| 出力先を作成できない             | `mkdir` で作成を試み、失敗したら報告して停止                   |
| 未知のオプション語が来た         | 対象ファイル指定として扱わず、無視してサマリーに 1 行残す      |

## 必須動作

- finder は指摘のみ、Write しない。出力ファイルは merge 後の 1 本のみ
- 全モードで指摘ファイルを `/tmp/lw-review/` に Write する。サマリーの inline 報告のみで完了しない
- 全件を指摘ファイルに記録し、表示だけ畳む
- 修正しない。指摘ファイルの出力までが doc-review の責務
- 合議マークを重複統合で消さない
- 記述・範例コンテキストを finder に渡さない
- 触ってよいファイルは指摘ファイルと宣言（「保存」を選んだ場合）のみ
