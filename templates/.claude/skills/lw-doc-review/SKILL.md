# lw-doc-review

層別 finder 並列 → merge → 指摘ファイル出力に特化した skill。
修正は `/lw-fix-review` が担う（doc-review は指摘のみ）。
設計判断の why は `$KIT/docs/lw-kit/40_スキル設計/lw-kit-スキル設計-lw-doc-review.md`、本ファイルは how + 具体値の正本。

入力: `$ARGUMENTS` はファイルパス / `@` 付きパス / 自然言語（「さっき作ったファイル」等）。

| オプション         | 意味                                                                            |
| ------------------ | ------------------------------------------------------------------------------- |
| (なし)             | 自動判定。迷ったら quick 側に倒す                                               |
| `--quick`          | 1 体が 4 層を見る（読み手なし・合議マークなし・コスト低・実時間は並列より遅い） |
| `--full`           | 4 体フル並列（モデル使い分け込み）                                              |
| `--profile=<種別>` | プロファイルを明示指定（自動判定を skip）                                       |

## 全体像

```text
1. 入力解決とロード → 2. effort 判定 → 3. finder 並列 spawn
  → 4. merge → 5. 指摘ファイル Write → 6. サマリー報告
```

quick でも full でも 6 ステップ全てを通す。quick で merge が自明（1 finder）でも層順ソート + 指摘ファイル Write は省略しない。fix-review の入口を `/tmp/lw-review/` に統一するため。

## 言い訳対戦表（起動前チェック）

| 言い訳                                             | 現実                                                                               |
| -------------------------------------------------- | ---------------------------------------------------------------------------------- |
| full にした方がいい気がする                        | フル化は明示オプトイン（`--full`）。自動判定は迷ったら quick 側                    |
| プロファイルは内容を読めば分かる                   | LLM 内容判定は却下済み。4 段階判定に従い、落ちたら聞く                             |
| merge 手順は件数が少ないから省略                   | 引用 grep 再計算と合議判定は件数に関わらず通す                                     |
| quick だから merge と Write は省略してサマリーだけ | quick でも指摘ファイルは `/tmp/lw-review/` に Write する。fix-review の入口統一    |
| `--fix` と言われたから直す                         | 直さない。「`/lw-fix-review` を実行してください」と案内する                        |
| 指摘が多いから厳選して報告だけ                     | 全件を指摘ファイルに記録し、表示だけ畳む                                           |
| finder に文書の背景も渡すと親切                    | 記述・範例コンテキストは渡さない（初見読者を演じる価値が壊れる）。渡すのは規範のみ |
| 規範コンテキストが多いから関連しそうなものだけ読む | 宣言に載っているものは全部読む。範囲を絞りたいなら宣言の注記で制御する             |

## 事前条件

- **llm-wiki ルートの特定**: cwd に `40_project/` があればそこ。なければ add-dir のうち `40_project/` を持つパスを llm-wiki ルートとする。以降の `40_project/` / `1_issues.md` 等の相対パスはすべて llm-wiki ルート起点
- アクティブ issue 名の把握: llm-wiki ルートの `1_issues.md` の WIP セクションから取得。なければ `_no-issue/`
- 対象ファイルの存在確認

## 手順（6 ステップ）

### 1. 入力解決とロード

`$ARGUMENTS` から対象ファイルを特定し Read する。特定できなければ聞く。

**宣言ファイルの発見（Glob + ルーター）:**

llm-wiki ルートで `Glob(**/.doc-review.md)` を実行し、全宣言ファイルを取得する。
対象ファイルのパスと比較し、最寄り祖先ディレクトリの `.doc-review.md` を宣言として使う。
ルートの `.doc-review.md` はルーターなので宣言候補から除外する（ヒットしても「発見なし → ルーター処理」に進む）。

発見なし、またはルーターのみヒットした場合、llm-wiki ルートの `.doc-review.md`（ルーター）を読む。
外部 repo の対象ファイルは Glob で拾えないため、ルーター経由で誘導する。
ルーターは対象ファイルのパスを上から順に前方一致で照合し、最初にマッチした行の参照先を宣言として使う。
ルーターの解決規則:

- 上から順の最初一致（最長一致にしない）
- パターンは前方一致のディレクトリパス（glob でなく）
- 「それ以外」行を必須とし、既定動作を暗黙にしない
- 参照は 1 hop 限定（参照先がルーターだったらエラー）

walk-up でもルーターでも見つからなければ宣言なしで続行（ベースラインのみ、正常系）。
宣言内の参照はパス直書き（dot ファイルのため `[[link]]` が Obsidian で効かない）。

**プロファイル判定（4 段階、上から順に適用）:**

1. ユーザー明示指定（`--profile=設計書` 等）
2. 宣言ファイルのプロファイル欄の glob マッチ。glob は対象を具体的に絞ること（広い glob は type 対応表を影で潰す）
3. frontmatter の type から対応表で推定:

| frontmatter type                                | プロファイル |
| ----------------------------------------------- | ------------ |
| design                                          | 設計書       |
| concept / entity / source / synthesis / project | wiki         |

定義済みプロファイル: エッセイ / 技術ブログ / 設計書 / wiki（`50_feedback/feedback-プロファイル-*.md`）。
プロファイルは宣言ファイル側で自由に追加定義でき、SKILL.md は判定ロジックのみ持つ。

4. ユーザーに聞く。選択肢に「(c) この対応を宣言に保存して次回から自動判定」を同梱。lead が (c) を選べば宣言に Edit で追記する

**知見のロード:**

宣言の知見欄に記載された `feedback-知見-*.md` を Read し、各エントリの層フィールドで振り分け準備する。

**規範コンテキストのロード:**

宣言のコンテキスト・規範欄に記載されたファイルを Read する。注記があれば注記の範囲だけ渡す。
記述・範例コンテキストは読まない（finder に渡さない。fix-review が使う）。

**宣言メタ指摘の検出:**

規範コンテキストを読む際に、参照先不存在・注記と実物の明白な矛盾に気づいたらメモしておく（指摘ファイル冒頭に出力）。

### 2. effort 判定

判定材料:

- プロファイルのセクション有無（= 起動判定。`## 読み手` は完全一致で判定、`## 読み手の定義` と混同しない）
- ユーザーの明示オプション（`--quick` / `--full`）

**体制表（フル時のモデル割当）:**

| 層     | モデル | 根拠                                                                                          |
| ------ | ------ | --------------------------------------------------------------------------------------------- |
| 骨格   | opus   | 文書全体の俯瞰と論理評価に推論力が必要                                                        |
| 中身   | opus   | 同上                                                                                          |
| 文章   | fable  | 表現の判断駆動であり fable で十分な品質が出る                                                 |
| 表記   | sonnet | 明文規約のチェックリスト照合で足りる                                                          |
| 読み手 | sonnet | 読者としての反応を返す役割、推論力より自然さ（プロファイルに `## 読み手` がある場合のみ起動） |

プロファイルにセクションがない層は起動しない。`--full` なら 4 層（骨格・中身・文章・表記）をベースラインで全起動。読み手は `--full` でもプロファイルゲート（`## 読み手` の有無）を維持する（読み手はベースラインとなる層定義を持たないためフォールバック対象外）。`--quick` なら 1 体が 4 層（読み手を除く）。quick のモデルは opus。

spawn 前に体制を 1 行報告する（「中身 opus / 文章 fable / 表記 sonnet の 3 体」等）。

### 3. finder 並列 spawn

全 finder を素の Agent 戻り値方式で並列 spawn する。
`name` パラメータを付けない（SendMessage でアドレス可能な named agent にしない）。
finder プロンプトで Write/Edit を禁止する指示を入れる（テンプレート参照）。
全 finder を 1 メッセージで同時に spawn し、全結果を待つ。

**各 finder への入力配布:**

| 入力                         | 全 finder 共通 | 層固有                             |
| ---------------------------- | -------------- | ---------------------------------- |
| 文書全文                     | はい           |                                    |
| 自層の層定義（見る/見ない）  |                | はい                               |
| プロファイルの自層セクション |                | はい（なければベースラインのみ）   |
| 自層の知見                   |                | はい（層フィールドでフィルタ）     |
| 規約ファイル                 |                | 表記のみ                           |
| 規範コンテキスト             |                | 該当する finder に（注記の範囲で） |

読み手 finder はプロファイルに `## 読み手` がある時のみ起動し、別テンプレートを使う。

### 4. merge

メインが全 finder の戻り値を受け取り、以下の決定論的規則で merge する:

1. **行番号の再計算**: 各指摘の「引用」文字列で文書内を grep し行番号を再計算する
2. **合議マーク判定**: 同一セクション かつ（再計算行番号の距離 ≤ 2 または一方の引用が他方の部分文字列を含む）→ 合議マーク付与
3. **ソート**: 層順（骨格→中身→文章→表記）+ 重要度順（必須→推奨→任意→確認(事実)→確認(意図)）
4. **再評価注記**: 骨格に「必須」があれば、下位層の指摘に「骨格修正後に再評価」を付与

引用が文書内で非一意 → セクション見出しで絞る。
引用が原文に見つからない → 位置不明としてセクション末尾に配置、合議判定から除外。

読み手レポートは merge 対象外。そのまま末尾に配置。

### 5. 指摘ファイル Write

出力先: `/tmp/lw-review/<issue-name>/YYYYMMDD-HHMM-<対象ベースネーム>.md`

`<対象ベースネーム>` は対象ファイルのファイル名から拡張子を除いたもの（例: `SKILL` / `Dario-Amodei`）。

```bash
mkdir -p /tmp/lw-review/<issue-name>
date '+%Y%m%d-%H%M'
```

ファイル内構成:

```markdown
# レビュー: <ファイル名>

- 対象: <パス>
- 宣言: <パス>（経路: walk-up / ルーター / なし）
- プロファイル: <種別>（判定経路: type / 宣言 / 明示 / 聞いた）
- 体制: <層(モデル) の列挙>
- 指摘: N 件（必須 A / 推奨 B / 任意 C / 確認(事実) D / 確認(意図) E）

---

## 宣言メタ指摘（あれば）

## 骨格（あれば）
### [重要度] タイトル
- 層 / 位置 / 引用 / 指摘 / 提案 / 根拠

## 中身（あれば）
## 文章（あれば）
## 表記（あれば）

---

## 読み手レポート（あれば）
1. 感情が動いた箇所
2. 脱落しそうになった箇所
3. 読後に残ったもの

---

## 合議マーク
| 箇所 | 指摘した finder | 合議数 |
```

### 6. サマリー報告

ユーザーへのサマリー表示は畳む:

- 必須: 展開（全文表示）
- 推奨: 1 行リスト
- 任意: 件数のみ
- 確認: 件数のみ
- 読み手レポート: 全文表示

宣言メタ指摘があればサマリーに含める。
`--fix` が指定されていた場合: 「指摘ファイルを出力しました。`/lw-fix-review` を実行してください」と案内する。

## エラーハンドリング

| 状況                         | 挙動                                                            |
| ---------------------------- | --------------------------------------------------------------- |
| 対象ファイル特定不能         | 聞いて停止                                                      |
| type なし + 宣言マッチなし   | 聞く + 宣言保存の選択肢                                         |
| 宣言ファイルなし             | ベースラインのみで続行（正常系）                                |
| finder 戻り値が空 / 形式不正 | その finder 0 件として続行 + サマリーに明記（再 spawn しない）  |
| 引用が原文にない             | 位置不明扱い（merge 規則に従う）                                |
| アクティブ issue なし        | `_no-issue/` に出力                                             |
| `--fix` が指定された         | 指摘ファイル出力後「`/lw-fix-review` を実行してください」と案内 |

## 必須動作

- finder は指摘のみ、Write しない。出力ファイルは merge 後の 1 本のみ
- 全モードで指摘ファイルを `/tmp/lw-review/` に Write する。サマリーの inline 報告のみで完了しない
- 全件を指摘ファイルに記録し、表示だけ畳む
- 修正しない（`--fix` でも）。fix-review を案内する
- 合議マークを重複統合で消さない
- 記述・範例コンテキストを finder に渡さない
- 触ってよいファイルは指摘ファイルと宣言（「保存」を選んだ場合）のみ
