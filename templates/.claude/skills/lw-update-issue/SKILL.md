# lw-update-issue

進行中 issue の 💧 進行中 / 🌂 中断点 / ☔ TODO を更新し、旧内容を 🪣 経緯に降ろす skill。
設計判断の why は `$KIT/docs/lw-kit/40_スキル設計/lw-kit-スキル設計-lw-update-issue.md`、本ファイルは実行手順の how。

入力: `$ARGUMENTS` は対象 issue のファイル名 / `[[link]]` / パス。省略時は会話文脈から推定する。
`--fixed` / `--faded`（または自然文の「FIXED にして」「閉じて」）があれば状態遷移まで行う。

## Process 概観

```text
1. 対象特定 → 2. Read → 3. 洗い出し（探索）→ 4. 選んで 🪣 に書く（活用）
  → 5. 💧/🌂 上書き → 6. ☔ TODO チェック → 7. ☔ TODO 追加 → 8. 状態遷移 → 9. 自己報告
```

ステップ 8 は指示があるときだけ走る。無ければ 9 へ進む。

## 言い訳対戦表（起動前チェック）

| 言い訳                                                        | 現実                                                                                           |
| ------------------------------------------------------------- | ---------------------------------------------------------------------------------------------- |
| 💧/🌂 に変化がないから何もしなくていい                        | ☔ TODO だけ変化している場合もある。変化がないなら「変化なし」と報告して skip                  |
| 🪣 に降ろすほどの内容がない                                   | 会話で議論・決定したことも経緯の一部。💧/🌂 に書いてあることだけが「起きたこと」ではない       |
| 旧 💧/🌂 を要約して短くまとめよう                             | 洗い出し（3）で種類を省かない。量の調整は選別（4）でやる                                       |
| 🪣 セクションが無いから更新できない                           | 無ければ自動追加する（☔ TODO の後、関連の前に挿入）                                           |
| 経緯の内容は分かってるから降ろしと上書きをまとめて 1 回でやる | ステップ 3 の `date` 取得を踏まないまま走る。洗い出し（3）→ 書く（4）→ 上書き（5）は別ステップ |
| TODO が全部 `[x]` になったので閉じておく                      | 指示が無ければ状態遷移しない（8）。全完了と閉じてよいかは別                                    |
| 閉じるので 🌂 に「次は commit から」と残しておく              | 終端形は再開指示を残さない（`.claude/rules/issue.md`）。commit まで確定しているものとして書く  |

## 事前条件

- `.claude/rules/issue.md`（4 セクション構造・「🪣 経緯の書き方」）を把握している

## Process（9 ステップ）

### 1. 対象 issue の特定

`$ARGUMENTS` にファイル名 / `[[link]]` / パスがあればそれを使う。
無ければ会話文脈から推定する（直近で作業している issue、会話で言及された issue 等）。

候補が複数ある・特定できない場合は lead に「どの issue を更新しますか?」と確認して停止。

### 2. Read

対象 issue を Read し、現在の 💧/🌂/☔ の内容を取得する。
🪣 経緯セクションの有無も確認する（無ければステップ 4 で自動追加）。

### 3. 洗い出し（探索）

`Bash(LANG=ja_JP.UTF-8 date '+%Y/%m/%d (%a) %H:%M')` で現在時刻を取得する。

旧 💧/🌂 と会話文脈から「このセッションで何が起きたか」の**候補を挙げる**。ここでは issue に書かない。
💧/🌂 に書いてあることだけが「起きたこと」ではない。会話で議論・決定・調査したことも含める。

`.claude/rules/issue.md`「🪣 経緯の書き方」の分類ごとに走査し、**該当なしも明示する**。

- 判断・決定・方針転換: 方針が変わった / 前提が崩れた / 決めた
- 測った事実: 「調べたが該当なし」「A と B が同じ結果を返すと確認した」
- 痕跡が残らない不採用: skip したレビュー指摘、検討して今回は採らなかった設計
- 同じ実装で再び誤りやすい箇所: どのファイルのどの処理か

走査の結果は応答に書く（issue には書かない）。
このステップで種類を省かない。量の調整は次のステップでやる。

💧/🌂 に変化がなく候補も挙がらない場合は 4 を skip。☔ TODO のみ更新があればそれだけ実行する。

### 4. 選んで 🪣 に書く（活用）

3 で挙げた候補を 1 つずつ選別し、生き残ったものだけをエントリに書く。
何を書くかは `.claude/rules/issue.md`「🪣 経緯の書き方」が正本。

**書く前に、候補ごとに対象 issue を `Bash(grep -n "<候補のキーワード>" <対象 issue>)` で引く。**
ヒットしたら既に他セクション（☔ / 🌂 / 💧 / 背景 等）が持っているので、書かずに落とすか 1 行の参照にする。
context に情報があると重複を自力で検出できないので、同じファイルの中だけは機械的に照合する。
他ファイル（設計書 / 知見 / 別 issue）まで grep する必要はない。

**走査は候補列挙であって、書く枠ではない。**
エントリを分類見出しで構成しない。該当なしの明示は 3 の応答が持つので、エントリには書かない。

**生き残りがゼロならエントリを作らない**（見出しだけの空エントリを置かない）。

書き先は常に新しい `### YYYY/MM/DD (曜) HH:MM` 見出し（時刻は 3 で取得済み）。
同一セッションで 2 回目以降でも、既存エントリの本文に書き足さない。

| 言い訳                                | 現実                                                                     |
| ------------------------------------- | ------------------------------------------------------------------------ |
| これも判断の文脈だから残す            | 実況は `log.md` と `git log` が持つ。結論と、示された理由だけ書く        |
| 参照 1 行では不安なので写す           | 写しは参照より先に古くなる。実在を確認して 1 行にする                    |
| 分類ごとに 1 つは挙がったので全部書く | 挙げた候補に判別文を通し、生き残りだけ書く                               |
| 他に正本があるはずだから落とす        | 実在を確認していないなら落とさない                                       |
| これは作業の実況だから落とす          | 再測定でしか知れない事実は実況の顔をしている。判別文で確かめてから落とす |
| 判断ではないから落とす                | 採らなかった案は実物に残らない。🪣 が唯一の正本になる                    |

参照に落とすものは、書いた直後に実在を確認する。

- `[[link]]` → `Bash(find 00_issues/ 20_library/ 30_wiki/ 40_project/ 50_feedback/ -name "<title>.md")`
- 他ファイルのセクション名 → `Bash(grep -n "<見出し>" <パス>)`
- 同じ issue の他セクション → `Bash(grep -n "<見出し>" <対象 issue>)`

`###` 見出しの下には空行を入れる（markdownlint MD022 対策）。
🪣 経緯セクションが無い場合は、☔ TODO の後・関連の前に `## 🪣 経緯` を新設する。

### 5. 💧/🌂 上書き

会話文脈から最新の状態を書く。

- 💧 進行中 = いま何をしているか / 何が判明したか（状態の snapshot）
- 🌂 中断点 = 次にやること / 再開点（再開時の行動指示）

💧 と 🌂 で同じ next-step を重複して書かない。💧 は状態、🌂 は再開指示に役割分担する。

### 6. ☔ TODO チェック（活用）

今セッションで完了した項目を `[x]` にする。
変化なしなら skip。

区切りの終端にある `- [ ] /lw-commit` の行は閉じない。
commit を実行した事実を持つのは `/lw-commit` の側で、そちらが自分で閉じる。
ステップ 8 で状態遷移まで行う場合はこの限りでない（終端形が `[ ]` を残さないと規定している）。

### 7. ☔ TODO 追加（探索）

会話中に生まれた新しい作業を探す。
スコープ外に切り出した対応、別 skill への反映、後片付け、設計変更に伴う追従作業など。
見つけたら ☔ TODO に追加する。

🌂 中断点に書くだけでは足りない。☔ に落とさないと「全件 `[x]` = 完了」の判定が狂う。

該当なしなら「新規 TODO: なし」と報告して skip。

### 8. 状態遷移

`$ARGUMENTS` に `--fixed` / `--faded`（または同義の自然文）がある時だけ走る。
無ければ何もしない。指示が無いのに閉じない。

1. `.claude/rules/issue.md`「FIXED / FADED 化時の終端形」に従って 4 セクションを書き換える。5 から 7 で書いた内容も終端形に合わせ直す
2. `find 00_issues/ -name "<name>.md"` で対象の現在のパスを取る（タイトルは全体で一意なので 1 件に決まる）
3. 2 の出力を移動元にして `git mv` する
   - FIXED → `git mv <2 の出力> 00_issues/.90_fixed/`
   - FADED → `git mv <2 の出力> 00_issues/.99_faded/`

移動元を `00_issues/<name>.md` と決め打ちしない。
FADED はどの状態からでも遷移でき、対象が `.10_todo/` / `.00_icebox/` にいることがある。

書き戻し（`.claude/rules/issue.md`「完了 / 廃棄時の規律」）の要否は本 skill が判断しない。
閉じる指示は仕分け済みの意思表示として受ける（page への反映は `/lw-retro` の責務）。

`1_issues.md` / `2_done.md` への転記はしない（`/lw-commit` の責務）。
盤面と issue の状態は次の `/lw-commit` まで一時的にずれる。

### 9. 自己報告

選別の内訳と、書いた 🪣 エントリの**行数と 1 行サマリ**を報告する。

```text
候補 <N> 件 → 書いた <M> / 参照に落とした <K> / 落とした <L>。🪣 に +<行数> 行。<何を書いたか 1 行>
```

行数は自力で数えず、コマンドで取る。

- エントリが 2 件以上 → `Bash(grep -n "^### 20" <対象 issue>)` で見出しの行番号を出し、先頭 2 つの差を取る
- 🪣 を新設して 1 件目を書いた → `Bash(grep -n "^## 🪣\|^## 関連" <対象 issue>)` の 2 つの差を取る（`## 関連` が無ければ総行数との差）

閾値は持たない。数字と要約が目に入れば、書きすぎと的外れをユーザーが検出できる。
候補件数を先に出すのは、3 の洗い出しを飛ばすと書けないため。

🪣 に追記が無かった場合は次のいずれかを報告する。

- 候補を挙げて選別で全部落ちた → 「候補 <N> 件、すべて既存の正本にあり追記なし」
- 候補が挙がらず 4 を skip した → 「候補なし、🪣 への追記なし」

## エラーハンドリング

| ケース                                | 方針                                                                                                                                     |
| ------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| `$ARGUMENTS` なし + 文脈から特定不可  | 「どの issue を更新しますか?」と案内して停止                                                                                             |
| 候補が複数ある                        | 候補を列挙して lead に選択を促す                                                                                                         |
| 対象 issue が WIP 以外（TODO 等）     | 更新は実行する（TODO / ICEBOX の issue も 💧/🌂 更新は有効）。状態遷移は 8 の指示に従う                                                  |
| 🪣 経緯セクションが未存在             | 4 で自動追加する                                                                                                                         |
| 💧/🌂 に変化がなく候補も無い          | 4 を skip                                                                                                                                |
| 候補は挙がったが選別で全部落ちた      | エントリを作らない                                                                                                                       |
| 状態遷移の指示があるが対象が曖昧      | 1 で停止する。推定で閉じない                                                                                                             |
| `git mv` が not under version control | 起票直後の issue はまだ追跡されていない。本 skill は `git add` を持たないので、`/lw-commit --fixed` で閉じるよう lead に案内して停止する |

## よくあるミス

1. 洗い出しの段階で種類を落とす（4 の選別を先取りして薄く書く。ステップ 3 の趣旨違反）
2. 会話文脈を無視して旧 💧/🌂 だけコピーする（会話で議論・決定したことも経緯の一部、ステップ 3 の趣旨違反）
3. 走査の分類をそのままエントリの見出しにする（枠を埋める圧力が働いて全部書くことになる、ステップ 4 の趣旨違反）
4. 書く前の `grep` を飛ばし、同じ issue の他セクションが持つ内容を書く（context にあると重複だと気づけない。実測で落ちた行の 7 割がこの経路、ステップ 4）
5. 参照に落とした先の実在を確認しない（`[[link]]` や見出しが解決しないまま残る、ステップ 4）
6. 既存の見出し行を `old_string` に含めた Edit で、`new_string` に戻し忘れて見出しごと消す（lint にも markdownlint にも出ない、ステップ 4）
7. 会話中に生まれた新作業を 🌂 に書くだけで ☔ に落とさない（「全件 `[x]` = 完了」判定が狂う、ステップ 7 の趣旨違反。ステップ 6 のチェックとステップ 7 の追加は探索・活用が逆なので別ステップにしている）

## 必須動作

- 💧/🌂 を上書き（5）する前に、旧内容を必ず洗い出し（3）の候補に含める。上書き後は復元できないため。書くかどうかは選別（4）に従う
- 洗い出し（3）では issue を編集しない。書くのは選別（4）に一本化する
- 書く前に候補ごとに対象 issue を `grep` する（4）。同じファイルの中の重複は自力で気づけない
- 参照に落としたものは、書いた直後に実在を確認する（4）
- `/lw-update-issue` は対象 issue 以外のファイルに触らない（更新フローに閉じる）。issue の内容改訂は `log.md` に記録しない（規約は `.claude/rules/log-index.md`）
- 状態遷移は指示があるときだけ（8）。自発的に閉じない（`.claude/rules/issue.md`「ユーザー確認」）
- `1_issues.md` / `2_done.md` への転記はしない。盤面は `/lw-commit` が持つ
