# lw-fix-review

設計判断の why は `$KIT/docs/lw-kit/40_スキル設計/lw-kit-スキル設計-lw-fix-review.md`、本ファイルは how + 具体値の正本。

入力: `$ARGUMENTS` でレビュー結果を受け取る（`/tmp/lw-review/` / 会話内テキスト / 対象ファイル明示）。

reviewer (fresh context) が出した指摘を、会話コンテキストを持つ本 skill が取捨選択して対象ファイルに反映し、再利用可能な知見を `50_feedback/feedback-知見-*.md` に蓄積する（判断に迷うものは lead に相談する）。

## 自走範囲

対象ファイルの Edit + 既存知見ファイルへの追記が「lead 指示なしで触ってよい境界」。
lead 相談はコスト大か、閉じた条件に該当する場合のみ（詳細はステップ 2）。
対象文書側の修正で解消できる指摘はそちらを優先する。
他 page 側を直す必要がある場合は自走せず lead に提示する。

## 言い訳対戦表（起動前チェック）

| 言い訳                            | 現実                                                                                   |
| --------------------------------- | -------------------------------------------------------------------------------------- |
| 件数が多いから一括提示            | lead 相談は依存順で 1 件ずつ。自走分は一括報告でよい                                   |
| 他 page の不整合も直しておく      | allowlist 外。lead に提示して指示を得てから修正する                                    |
| 全件「なし」だからテスト省略      | 却下がある場合は却下理由テストの痕跡を書く義務がある。痕跡なしの「なし」は信用できない |
| advisor がいないから spawn する   | spawn しない。相談役ステップを飛ばして lead 相談に進む（「相談役」セクション）         |
| 全件 advisor に聞けば精度が上がる | 相談役に回すのは lead 相談レーンのみ。自走レーンに回すと往復だけ増える                 |
| advisor に聞いたから lead は省く  | 相談役は判断材料を足すだけ。採否は lead が決める                                       |

## 実行フロー

### 1. 入力解決 + 対象ファイル特定

`$ARGUMENTS` からレビュー結果を取得し、対象ファイルを Read する。

| 入力形式                     | レビュー結果の取り方                           | 対象ファイルの特定                                     |
| ---------------------------- | ---------------------------------------------- | ------------------------------------------------------ |
| `/tmp/lw-review/` 配下       | `find` で特定して Read                         | findings ファイル内の対象ファイル情報から特定          |
| 会話内のレビュー指摘テキスト | 直前の会話履歴から指摘リストを抽出             | 直近の会話で言及された対象ファイル                     |
| 自然言語指定                 | 「さっきのレビュー」等から会話履歴で path 特定 | `$ARGUMENTS` で `<target-file>` 明示があればそれを優先 |

- レビュー結果が特定できないとき → lead に確認して停止
- 対象ファイルが特定できないとき → `<target-file>` 指定を促して停止

doc-review の指摘ファイルに層外レポート（読み手 / 通例）が含まれる場合は、指摘リストから分離して保持する。
どちらもコスト判定にも採否ルーティングにも乗せない（扱いはステップ 6）。

- 読み手レポート: 読者の反応であって修正指示ではない
- 通例レポート: 「何が丸ごと欠けているか」の指摘で、引用を持たず、埋める作業の規模が件ごとに大きく違う

指摘ファイル冒頭の「プロファイル: <種別>」から該当プロファイル（`50_feedback/feedback-プロファイル-<種別>.md`）を特定し、`## fix 制約` があれば Read して Edit 時に守る。
セクションがなければ制約なしで進む。

### 2. コスト判定 + 自走ルーティング

各指摘にコスト（小 / 大）を付与し、reviewer が付けた重要度ラベル（必須 / 推奨 / 任意 / 確認（事実）/ 確認（意図））と組み合わせてルーティングを決定する。
確認（事実）= 著者にしか判断できない事実確認事項。確認（意図）= 著者が意図的にそうした可能性を問うもの。

#### コスト判定

| コスト | 操作的定義                                                                        |
| ------ | --------------------------------------------------------------------------------- |
| 小     | Edit 1-2 回、対象セクション内で完結、他ファイルへの波及なし                       |
| 大     | Edit 3 回以上、または複数セクションの移動・統廃合、または他ファイルとの整合が必要 |

#### 自走ルーティング（上から順に適用）

```
1. ラベル欠落 → lead 相談（重要度を推測で補わない）
2. 確認（意図）→ lead 相談（意図は lead かユーザーの側にしかない）
3. 確認（事実）→ 判断材料が手元にあれば自走、無ければ lead 相談
4. コスト大 → lead 相談（任意・推奨・必須を問わず）
5. 閉じた条件に該当 → lead 相談
6. 判断に迷う × 推奨・任意 → スキップ + サマリー表に理由付き記録
7. それ以外 → 自走で直す
```

ラベル欠落を「確認（事実）」に写像しない。
確認（事実）は「材料が手元にあれば自走」に降りる分岐を持つので、重要度が分からない指摘を通すには緩い。
欠落したまま最後まで落ちると「それ以外 → 自走」に当たり、本来 lead に聞くべき指摘が無審査で適用される。

「確認（事実）」ラベルは reviewer が fresh context で判断材料を持たないときに付く。
lead 側に材料があるかは別問題なので、材料の有無で分ける。

- 手元にある（次の作業予定 / 参照先文書の目的 / 過去の決定を知っている）→ 自走し、根拠をサマリー表の理由欄に書く
- 手元にない（実測が要る / ユーザーの意図が要る）→ lead 相談

#### lead 相談の条件

コスト小でも lead 判断が要るもの:

- 既存ファイル × 構造・規約・命名に踏み込む変更
- 必須ラベルの指摘で直し方に迷う場合

主要セクション書き換え級の大改造と他ファイルへの波及は、コスト判定で「大」に落ちるのでルーティング 4 が拾う。

未 staged のファイル（git add されていない = lead 未確認）への fix は、規則 5（閉じた条件）と規則 6（判断に迷う）に該当しても自走してよい。規則 4（コスト大）は緩めない。
骨子合意から構造が変わった場合はサマリーに明示行を出す（相談はしない、ただし隠さない）。

逃げ道: lead が「全部採用で」「ここだけ反映して」等のスキップ指示を出した場合は判断スコープを絞って実行する。

### 3. Edit 反映

自走と判定された指摘を Edit で反映する。
複数指摘がある場合は 1 件ずつ Edit する（一括 Write はしない、変更箇所が明示されないため）。

**合議マーク箇所の照合**: 指摘ファイル末尾の合議マーク表で対象の指摘を特定する（箇所欄に指摘タイトルが併記されている）。合議した指摘群（同一箇所を複数 finder が指摘）は、上位層の修正を先に適用し、下位層の指摘が解消済みかを照合する。
1 つの Edit で複数指摘が同時に解消される場合、解消済みの指摘は「合議解消」として閉じる（重複修正を避ける）。

**アンカーの再確認**: 指摘ファイルのヘッダが「再評価: あり」の場合、骨格の Edit を全て適用した後に、下位層（中身・文章・表記）の指摘の引用を対象ファイルで grep し直す。
引用が見つからない指摘は「アンカー無効」としてスキップし、サマリー表に記録する。
骨格修正が下位層の対象箇所を実際に書き換えたかどうかは、注記でなく、引用が対象ファイルに見つかるかどうかで判定する。

Edit 失敗時は該当指摘を「Edit 失敗」として記録し、他指摘の処理は継続する。

### 4. 蓄積判定・第 1 パス

自走分の蓄積ラベルを確定し、知見ファイルに追記 Edit する。lead 相談前に保存を完了させる。

手順:

1. `find 50_feedback -name "feedback-知見-*.md"` で蓄積先候補を走査
2. 対象プロジェクトに該当するファイルを Read
3. 各指摘に蓄積ラベルを付与（判定基準は「蓄積ラベルの判定基準」セクション参照）
4. 「既存補強」「却下パターン」「新規知見」の指摘を知見ファイルに追記 Edit

該当する知見ファイルがない場合は追記せず、ステップ 5 の lead 相談に「該当知見ファイルなし。`feedback-知見-<名前>.md` を作成しますか?」と提案する。

### 5. lead 相談 + 蓄積判定・第 2 パス

「lead 相談」区分の指摘がある場合のみ走る。

先に相談役へ材料を求める（手順は「相談役」セクション）。
相談役が不在なら、この求めを飛ばして lead 相談に進む。

そのうえで一覧を表示し、依存順で 1 件ずつ回答を求める。
依存順は指摘が層を持つなら層順（骨格→中身→文章→表記）、持たないなら重要度順。
code-review の指摘は層を持たない。
自走 Edit できる指摘は一括適用してまとめ報告。lead 判断が要る指摘だけ 1 件ずつ。

```text
lead 相談 N 件:

1. [重要度/層] <指摘 1> — コスト / 理由
2. [重要度/層] <指摘 2> — コスト / 理由
...

1 件目: [重要度/層] <指摘 1> — <詳細>
advisor: <見解の要約。相談役に回していなければ行ごと省略>
どう扱いますか?
```

層を持たない指摘は `[重要度]` だけを書く。

1 件の回答を得てから次を出す。

lead 回答後:

1. 回答に従って Edit 反映（採用 / 不採用）
2. 相談分の蓄積ラベルを確定 + 追記 Edit（lead の回答理由が蓄積入力として最も価値が高い）

相談 0 件ならこのステップをスキップする。

### 6. サマリー報告

```text
lw-fix-review 完了

自走 N 件 / 相談 J 件 / スキップ S 件
蓄積: 新規知見 A 件 / 既存補強 B 件 / 却下パターン C 件

| # | 指摘 | 重要度 | コスト | 採否 | 却下理由テスト | 蓄積ラベル | 理由 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| F01 | <指摘 1> | 必須 | 小 | 自走 | — | なし | <理由> |
| F02 | <指摘 2> | 推奨 | 大 | 相談→不採用 | 「<ファイル名を消した却下理由>」→ 成立 | 却下パターン | <理由> |
| F03 | <指摘 3> | 任意 | 大 | スキップ | 「<ファイル名を消した却下理由>」→ 不成立 | なし | <理由> |
```

却下理由テスト欄: 採用された指摘は「—」。却下（不採用 / スキップ / lead 却下）された指摘は「ファイル名を消した却下理由文」と成立/不成立を書く。痕跡なしで「なし」にしない。

骨子合意から構造が変わった場合は、表の後に `構造変更の明示: <内容>` を 1 行足す（なければ省略）。

**昇格候補の提示**: 全指摘の採否確定後、根拠が既存知見名で採用された指摘を抽出し、該当知見エントリに昇格 3 条件（複数回再現 + 毎回採用 + 機械的に照合可能）を照合する。条件を満たすエントリがあればサマリー末尾に別枠で提示する:

```text
昇格候補 N 件:
- <知見エントリ名> → 規則文案: 「<規則文>」 → <昇格先（対象 repo CLAUDE.md / プロファイル）>
```

昇格候補がなければ省略する。
CLAUDE.md / プロファイルへの追記は allowlist 外。提案のみ行う。

**層外レポートの扱い**: ステップ 1 で分離したレポートがあれば、サマリー表の後に全文を出す。

読み手レポートの 3 項目（感情が動いた箇所 / 脱落しそうになった箇所 / 読後に残ったもの）は引用も重要度も持たないので、fix-review は自走で直さない。

通例レポートは重要度を持つが、欠落を埋める作業は本文の新規執筆になるので自走しない。
何をどこに足すかは lead が決める。
lead が「埋める」と判断した欠落は、その指示を指摘として受けて Edit する。

**seed 昇格候補の提示**: lead が採用した通例レポートの欠落があれば、サマリー末尾に別枠で出す。

```text
seed 昇格候補 N 件:
- <観点文> → <出典 URL> → `feedback-プロファイル-<種別>.md` の <層名> セクション
```

通例の欠落は 1 回の採用で候補にする（既存の昇格 3 条件は適用しない）。
通例 finder は毎回 web search するので同じ観点が再現する保証がなく、「複数回再現」を待つと昇格しないため。
プロファイルへの追記は allowlist 外なので提案のみ行う。

## 相談役

lead 相談に回す指摘について、cmux-teams で立っている advisor に見解を求める仕組み。
fix-review は相談役を spawn しない。既にいる advisor に問うだけで、いなければ何もしない。

### 起動条件

`ListAgents` の Teammates セクションに `advisor` がいる時だけ走る。
Peer sessions は対象外（別の作業をしているセッションなので相談役ではない）。

いない場合は相談役への問い合わせを飛ばし、現行どおり lead 相談に進む。
不在は正常系で、spawn もフォールバック経路の新設もしない。
cmux を使っていない環境では常に不在になり、その環境では現行動作のまま動く。

### 何を回すか

ステップ 2 で「lead 相談」に振り分けられた指摘が対象。判別は 1 文で行う。

**答えが文書の外（一般論・類例・外部情報）にありうる指摘は回す。答えが lead かユーザーの手元にしかない指摘は回さない。**

回る側: コスト大、構造・規約・命名に踏み込む変更、必須ラベルで直し方に迷うもの、確認（事実）のうち外部知識で埋まるもの。

落ちる側: 確認（意図）、実測すれば済むもの、ラベル欠落。
ラベル欠落を回さないのは、重要度の付与が reviewer の責務だから。
advisor に推測させると「重要度を推測で補わない」（ステップ 2）を迂回することになる。

自走レーンの指摘は回さない。往復のコストに見合わない。

### 投げ方

`SendMessage({to: "advisor", ...})` で送る。
1 通に 1 件だけ入れる（複数件を混ぜると返答がどの指摘に対応するか判別できない）。

含めるもの:

- 指摘の原文をそのまま（doc-review なら 6 要素、code-review なら findings 1 件）
- 対象ファイルのパスと、指摘ファイルのパス（`/tmp/lw-review/` 配下）
- fix-review 側の推奨と、その理由
- 問い（背景にどういう一般的な考え方があるか / 類似問題の一般的な解決パターン）
- web search を使ってよいこと
- 返答形式（選択肢を出し、推奨を 1 つ添えて返す）

文書全文は貼らない。
advisor は issue と関連資料を読んでいるが対象文書は読んでいないので、パスを渡して要る範囲を自分で Read させる。

推奨を必ず添える。
推奨のない問いには指摘の要約が返るだけで、材料が増えない。

### 返答の受け方

advisor は `SendMessage` で返す。非同期なので投げた直後には届かない。

ステップ 5 の冒頭で未着なら 1 回だけ催促する。
それでも未着なら、その指摘を相談役なしで lead 相談に回す。
後から届いた見解は捨てず、サマリーの該当行に追記する。

advisor の見解は材料であって決定ではない。採否は lead が決める。
web search は advisor 側が担う（fix-review は `WebSearch` を持たない）。
advisor が引いた URL は、その指摘の根拠として lead 提示に含める。

### 蓄積に入れない

advisor の見解そのものは蓄積入力にしない。
ステップ 5 の第 2 パスが根拠にしているのは lead の回答理由であって、相談役の見解ではない。

lead が「advisor の言うとおりで」と答えた場合は、advisor が示した中身を理由欄に書く。
「advisor がそう言った」を理由にすると、LLM 同士で決めた内容が知見ファイルに溜まる。

## 蓄積ラベルの判定基準

デフォルト「なし」の加点方式。上から順に判定する。

### 既存補強

指摘の根拠が既存知見への `[[link]]` の場合に候補。
操作的テスト: 既存エントリを Read して「既存の記述だけで今回の指摘を再現できたか?」。
再現できたなら なし（効いた事実を毎回記録すると肥大化する）。
既存に無い適用条件・反例・境界が今回見つかった時だけ 1-2 行追記。

### 却下パターン

却下（スキップ / 不採用 / 相談での lead 却下）で理由が一般化可能な場合。
却下理由テスト: 「却下理由の文から対象ファイル名を消しても文が成立するか」。
適用痕跡（ファイル名を消した文 + 成立/不成立）をサマリー表に書く義務がある。痕跡なしで「なし」にしない。

知見ファイルの採用判断の参考リストに 1 行記録する。

### 新規知見

最も高いバー。操作的テスト 2 つ:

- 一般化テスト: 指摘・対策の文から対象ファイル名を別ファイルに置換しても成立するか。ファイル固有の事実なら なし
- 再導出テスト: fresh context の reviewer が、この知見なしで次回も同じ指摘を自力で出せるか。出せるなら書かない。蓄積の価値は fresh では気づけないもの（プロジェクト固有の規約・過去の決定・暗黙の好み）にだけある

加えて必須 5 フィールド（タイトル / 状況 / 影響 / 対策 / 分類。出典は `$KIT/docs/knowledge/レビュー知見のまとめ方.md`）が全部埋まることを機械的な完了条件にする。対策が書けない指摘は知見として未成熟 → なし。

`50_feedback/feedback-知見-*.md` に追記する場合は `- 層:` も埋める（値は 骨格 / 中身 / 文章 / 表記 / なし）。
doc-review が finder へ振り分けるキーで、欠けたエントリは doc-review が渡さずに報告へ回すため、書き手側で埋めておく。
対策の宛先が finder でなく fix-review や lead の手順になっているものは `なし` にする。
複合値は `骨格 / 中身` のように `/` 区切りで書く。2 層の finder から独立に同じ指摘が出た時だけ許し、迷ったら層順の上位（骨格 > 中身 > 文章 > 表記）に倒す。

### なし

上記いずれにも該当しない。大半がこれになるのは正常。

### ノイズ制御

1 回の fix-review で新規知見は 0-2 件が正常。
3 件以上出たら蓄積ラベルの判定基準（一般化テスト / 再導出テスト等）が甘くなっているサイン。サマリーで lead に報告し、SKILL.md の判定基準の見直しを検討する。

## エラーハンドリング

| 状況                                            | 挙動                                                                          |
| ----------------------------------------------- | ----------------------------------------------------------------------------- |
| 入力不明（引数なし + 会話に手がかりなし）       | 「レビュー結果の path or 内容を指定してください」と確認停止                   |
| 対象ファイル特定失敗                            | `<target-file>` 明示指定を促す                                                |
| 対象ファイル Read 失敗（存在しない / 権限なし） | 即停止、エラーを返す                                                          |
| 全件「lead 相談」                               | ステップ 5 を通し、lead 回答に従って Edit。自走 Edit 0 件としてサマリーを出す |
| Edit 失敗（diff 不一致 / 一意特定不能）         | 該当指摘を「Edit 失敗」として記録、他指摘の処理は継続                         |
| 採用件数 0                                      | サマリーだけ返す（「全件不採用」と判断したケースを残す）                      |
| advisor が Teammates にいない                   | 相談役への問い合わせを飛ばして lead 相談に進む（正常系。spawn しない）        |
| advisor が返答しない                            | 1 回だけ催促し、来なければその指摘を相談役なしで lead 相談に回す              |

## ルール

横断不変条件（各ステップの詳細は実行フロー参照）:

- 書き込み面の allowlist: Edit 対象は「対象ファイル」と「既存 `feedback-知見-*.md` への entry 追記」のみ。新規知見ファイルは作成しない
- 自走範囲は allowlist が前提（反映後の内容は lead が `git diff` で確認できる）
- レビュー結果ファイルは削除しない（監査ログとして残す）
- 暗黙完了しない（完了サマリーを必ず出す）
- 相談役を spawn しない（既にいる advisor に問うだけ。不在なら飛ばす）
- 相談役は lead 相談を置き換えない（見解は材料、採否は lead。advisor の見解を蓄積入力にしない）
