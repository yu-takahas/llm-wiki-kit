# lw-fix-review - レビュー結果を lead 自走採否で反映 + 知見蓄積

入力: `$ARGUMENTS` でレビュー結果を受け取る（`/tmp/lw-review/` / 会話内テキスト / 対象ファイル明示）。

reviewer (fresh context) が出した指摘を、コンテキスト持ちの lead が取捨選択して対象ファイルに反映し、再利用可能な知見を `50_feedback/feedback-知見-*.md` に蓄積する。

## 自走範囲

対象ファイルの Edit + 既存知見ファイルへの追記が「lead 指示なしで触ってよい境界」。
lead 相談は閉じた 4 条件に該当する場合のみ（詳細はステップ 2）。
対象文書側の修正で解消できる指摘はそちらを優先する。
他 page 側を直す必要がある場合は自走せず lead に提示する。

## 言い訳対戦表（起動前チェック）

| 言い訳                       | 現実                                                                                 |
| ---------------------------- | ------------------------------------------------------------------------------------ |
| 件数が多いから一括提示       | lead 相談は依存順で 1 件ずつ。自走分は一括報告でよい                                 |
| 他 page の不整合も直しておく | allowlist 外。lead に提示して指示を得てから修正する                                  |
| 全件「なし」だからテスト省略 | 却下がある場合は一般化テストの痕跡を書く義務がある。痕跡なしの「なし」は信用できない |

## 実行フロー

### 1. 入力解決 + 対象ファイル特定

`$ARGUMENTS` からレビュー結果を取得し、対象ファイルを Read する。

| 入力形式                     | レビュー結果の取り方                                        | 対象ファイルの特定                                     |
| ---------------------------- | ----------------------------------------------------------- | ------------------------------------------------------ |
| `/tmp/lw-review/` 配下       | Glob で特定して Read                                        | findings ファイル内の対象ファイル情報から特定          |
| 会話内のレビュー指摘テキスト | 直前の会話履歴から指摘リストを抽出                          | 直近の会話で言及された対象ファイル                     |
| 自然言語指定                 | 「さっきのレビュー」等から会話履歴・git status で path 特定 | `$ARGUMENTS` で `<target-file>` 明示があればそれを優先 |

- レビュー結果が特定できないとき → lead に確認して停止
- 対象ファイルが特定できないとき → `<target-file>` 指定を促して停止

### 2. コスト判定 + 自走ルーティング

各指摘にコスト（小 / 大）を付与し、reviewer が付けた重要度ラベル（必須 / 推奨 / 任意 / 確認）と組み合わせてルーティングを決定する。
「確認」= 著者にしか判断できない事実確認事項。

#### コスト判定

| コスト | 操作的定義                                                                        |
| ------ | --------------------------------------------------------------------------------- |
| 小     | Edit 1-2 回、対象セクション内で完結、他ファイルへの波及なし                       |
| 大     | Edit 3 回以上、または複数セクションの移動・統廃合、または他ファイルとの整合が必要 |

#### 自走ルーティング（上から順に適用）

```
1. 確認 → lead に回す（事実確認が要る指摘は常に lead 判断）
2. コスト大 → lead に回す（任意・推奨・必須を問わず）
3. 閉じた 4 条件に該当 → lead 相談
4. 判断に迷う × 推奨・任意 → スキップ + サマリー表に理由付き記録
5. それ以外 → 自走で直す
```

#### lead 相談の 4 条件

- 既存ファイル × 構造・規約・命名に踏み込む変更
- 既存ファイル × 主要セクション書き換え級の大改造
- 既存ファイル × 他ファイルとの整合が崩れる波及
- 必須ラベルの指摘で直し方に迷う場合

未 staged のファイル（git add されていない = lead 未確認）への fix は原則すべて自走。
骨子合意から構造が変わった場合はサマリーに明示行を出す（相談はしない、ただし隠さない）。

逃げ道: lead が「全部採用で」「ここだけ反映して」等のスキップ指示を出した場合は判断スコープを絞って実行する。

### 3. Edit 反映

自走と判定された指摘を Edit で反映する。
複数指摘がある場合は 1 件ずつ Edit する（一括 Write はしない、変更箇所が明示されないため）。

**合議マーク箇所の照合**: 合議マークが付いた指摘群（同一箇所を複数 finder が指摘）は、上位層の修正を先に適用し、下位層の指摘が解消済みかを照合する。
1 つの Edit で複数指摘が同時に解消される場合、解消済みの指摘は「合議解消」として閉じる（重複修正を避ける）。

Edit 失敗時は該当指摘を「Edit 失敗」として記録し、他指摘の処理は継続する。

### 4. 蓄積判定・第 1 パス

自走分の蓄積ラベルを確定し、知見ファイルに追記 Edit する。lead 相談前に保存を完了させる。

手順:

1. Glob（`50_feedback/feedback-知見-*.md`）で蓄積先候補を走査
2. 対象プロジェクトに該当するファイルを Read
3. 各指摘に蓄積ラベルを付与（判定基準は「蓄積ラベルの判定基準」セクション参照）
4. 「既存補強」「却下パターン」「新規知見」の指摘を知見ファイルに追記 Edit

該当する知見ファイルがない場合は追記せず、ステップ 5 の lead 相談に「該当知見ファイルなし。`feedback-知見-<名前>.md` を作成しますか?」と提案する。

### 5. lead 相談 + 蓄積判定・第 2 パス

「lead 相談」区分の指摘がある場合のみ、まず一覧を表示し、依存順（層順: 骨格→中身→文章→表記）で 1 件ずつ回答を求める。
自走 Edit できる指摘は一括適用してまとめ報告。lead 判断が要る指摘だけ 1 件ずつ。

```text
lead 相談 N 件:

1. [重要度/層] <指摘 1> — コスト / 理由
2. [重要度/層] <指摘 2> — コスト / 理由
...

1 件目: [重要度/層] <指摘 1> — <詳細>
どう扱いますか?
```

1 件の回答を得てから次を出す。

lead 回答後:

1. 回答に従って Edit 反映（採用 / 不採用）
2. 相談分の蓄積ラベルを確定 + 追記 Edit（lead の回答理由が蓄積入力として最も価値が高い）

相談 0 件ならこのステップをスキップする。

### 6. サマリー報告

完了条件チェック: 全指摘に蓄積ラベルが付与され、却下された指摘には一般化テストの適用痕跡があることを確認する。

```text
lw-fix-review 完了

自走 N 件 / 相談 J 件 / スキップ S 件
蓄積: 新規知見 A 件 / 既存補強 B 件 / 却下パターン C 件

| # | 指摘 | 重要度 | コスト | 採否 | 一般化テスト | 蓄積ラベル | 理由 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| F01 | <指摘 1> | 必須 | 小 | 自走 | — | なし | <理由> |
| F02 | <指摘 2> | 推奨 | 大 | 相談→不採用 | 「<ファイル名を消した却下理由>」→ 成立 | 却下パターン | <理由> |
| F03 | <指摘 3> | 任意 | 大 | スキップ | 「<ファイル名を消した却下理由>」→ 不成立 | なし | <理由> |
```

一般化テスト欄: 採用された指摘は「—」。却下（不採用 / スキップ / lead 却下）された指摘は「ファイル名を消した却下理由文」と成立/不成立を書く。痕跡なしで「なし」にしない。

**昇格候補の提示**: 全指摘の採否確定後、根拠が既存知見名で採用された指摘を抽出し、該当知見エントリに昇格 3 条件（複数回再現 + 毎回採用 + 機械的に照合可能）を照合する。条件を満たすエントリがあればサマリー末尾に別枠で提示する:

```text
昇格候補 N 件:
- <知見エントリ名> → 規則文案: 「<規則文>」 → <昇格先（対象 repo CLAUDE.md / プロファイル）>
```

昇格候補がなければ省略する。
CLAUDE.md / プロファイルへの追記は allowlist 外。提案のみ行い、lead 承認後にその場で実行する。

## 蓄積ラベルの判定基準

デフォルト「なし」の加点方式。上から順に判定する。

### 既存補強

指摘の根拠が既存知見への `[[link]]` の場合に候補。
操作的テスト: 既存エントリを Read して「既存の記述だけで今回の指摘を再現できたか?」。
再現できたなら なし（効いた事実を毎回記録すると肥大化する）。
既存に無い適用条件・反例・境界が今回見つかった時だけ 1-2 行追記。

### 却下パターン

却下（スキップ / 不採用 / 相談での lead 却下）で理由が一般化可能な場合。
操作的テスト: 「却下理由の文から対象ファイル名を消しても文が成立するか」。
テストの適用痕跡（ファイル名を消した文 + 成立/不成立）をサマリー表に書く義務がある。痕跡なしで「なし」にしない。

知見ファイルの採用判断の参考リストに 1 行記録する。

### 新規知見

最も高いバー。操作的テスト 2 つ:

- 一般化テスト: 指摘・対策の文から対象ファイル名を別ファイルに置換しても成立するか。ファイル固有の事実なら なし
- 再導出テスト: fresh context の reviewer が、この知見なしで次回も同じ指摘を自力で出せるか。出せるなら書かない。蓄積の価値は fresh では気づけないもの（プロジェクト固有の規約・過去の決定・暗黙の好み）にだけある

加えて必須 5 フィールド（タイトル / 状況 / 影響 / 対策 / 分類。出典は `$KIT/docs/knowledge/レビュー知見のまとめ方.md`）が全部埋まることを機械的な完了条件にする。対策が書けない指摘は知見として未成熟 → なし。

### なし

上記いずれにも該当しない。大半がこれになるのは正常。

### ノイズ制御

1 回の fix-review で新規知見は 0-2 件が正常。
3 件以上出たら蓄積ラベルの判定基準（一般化テスト / 再導出テスト等）が甘くなっているサイン。サマリーで lead に報告し、SKILL.md の判定基準の見直しを検討する。

## エラーハンドリング

| 状況                                            | 挙動                                                          |
| ----------------------------------------------- | ------------------------------------------------------------- |
| 入力不明（引数なし + 会話に手がかりなし）       | 「レビュー結果の path or 内容を指定してください」と確認停止   |
| 対象ファイル特定失敗                            | `<target-file>` 明示指定を促す                                |
| 対象ファイル Read 失敗（存在しない / 権限なし） | 即停止、エラーを返す                                          |
| 全件「lead 相談」                               | Edit せずサマリーだけ返す（採用 0 / 相談 N 件として完了報告） |
| Edit 失敗（diff 不一致 / 一意特定不能）         | 該当指摘を「Edit 失敗」として記録、他指摘の処理は継続         |
| 採用件数 0                                      | サマリーだけ返す（「全件不採用」と判断したケースを残す）      |

## ルール

横断不変条件（各ステップの詳細は実行フロー参照）:

- 書き込み面の allowlist: Edit 対象は「対象ファイル」と「既存 `feedback-知見-*.md` への entry 追記」のみ。新規知見ファイルは作成しない
- 自走範囲は allowlist + `git diff` 事後確認が前提
- レビュー結果ファイルは削除しない（監査ログとして残す）
- 暗黙完了しない（完了サマリーを必ず出す）
