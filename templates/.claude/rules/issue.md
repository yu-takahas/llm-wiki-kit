# issue

`00_issues/<name>.md` は進行中タスクの中断点メモ（git ブランチ + issue tracker 代替）。
issue は状態管理・内部構造・閉じ方にルールがあり、逸脱すると知識の書き戻し漏れや状態の不整合が起きるため rule 化している。

## 状態管理

状態 = フォルダ位置。状態変更 = ファイル mv で完結、frontmatter は不変。

| 状態   | フォルダ                |
| ------ | ----------------------- |
| WIP    | `00_issues/` 直下       |
| TODO   | `00_issues/.10_todo/`   |
| ICEBOX | `00_issues/.00_icebox/` |
| FIXED  | `00_issues/.90_fixed/`  |
| FADED  | `00_issues/.99_faded/`  |

## ファイル内部構造

WIP に紐づく作業ログとして、以下の 4 セクションで構成する:

- 💧 進行中: いま考えていること、迷っていること、判断
- 🌂 中断点: 次にやること / 再開点（戻ってきた時の行動指示）
- ☔ TODO: タスク分解したチェックリスト（完了したら `[x]`）
- 🪣 経緯: 過去の 💧/🌂 と会話文脈を合わせた経過記録

💧/🌂 は常に最新状態を上書きし、旧内容は 🪣 経緯に降ろす。
🪣 経緯は初回更新時に自動追加される（起票時点では無くてよい）。
複雑なタスクは追加セクション（背景・選択肢・着地イメージ等）を足してよい。
末尾には `## 関連` を置いてよい（関連 issue / wiki page への `[[link]]`）。

<!-- セクション詳細は定義順（☔ → 🪣）に並べる。🪣 の規定は「🪣 経緯の書き方」に集約する -->

☔ TODO を書く時は `00_issues/.guide/` を確認し、タスク種別に該当する guide があればその行をコピーして使う（各 guide の冒頭 `## 対象タスク` が使う / 使わないを宣言している）。

中断後に ☔ TODO を再開する時は、リストの消化に入る前に前提（環境仕様・設計判断・着手順の妥当性）がまだ有効か確認する。
該当する guide が起票後に新設・改訂されていることがあるので、その突き合わせも確認に含める。

### 進捗の台帳は 1 箇所に決める

チェックボックスを 2 箇所以上に置かない。
同じ作業が複数箇所で追跡されると、片方だけ更新して他方が古くなる。

台帳を分けるなら責務で切り、重ならないようにする。
例: 進捗は ☔ TODO のチェックで表し、実行順や参照用のリストはチェックボックスを持たない。

### 🪣 経緯の書き方

フォーマット:

- 位置: ☔ TODO の直後（`## 関連` があればその前）
- エントリ形式: `### YYYY/MM/DD (曜) HH:MM` + 空行 + 本文（複数行 OK）。`###` の下の空行は markdownlint MD022 対策で必須
- 順序: 新しいエントリが上（戻ってきた時に最新の経緯が最初に目に入る）
- 更新ポリシー: append 基調だが更新 OK（typo 直し・表現整理・補足追記は自由）。`log.md` の append-only とは別物

見る範囲は旧 💧/🌂 に限らず会話全体（議論・決定・調査したこと）。
そこから何を書くかの判定の軸は「新しい context window でこの issue を読んだ人が再開できるか」。

書く:

- 判断・決定・方針転換
- 測って分かった事実（「調べたが該当なし」のような否定的結果を含む）
- 採らなかった選択肢のうち、実物に痕跡が残らないもの
- 同じ実装で再び誤りやすい箇所

書かない:

- 作業の実況（何をどう直したか、件数、ファイル名）。`log.md` と `git log` と実物が持つ
- 振り返り・反省。retro と知見の書き戻しが持つ（セッションを切る前に済ませる前提。retro を回さないなら知見側に先に書く）

判別文（迷ったときはこれを通す）: その事実を知る手段が再実行・再測定しかないなら残す。他の正本から復元できるなら参照に落とす。

決定は、理由が示されていなければ決定だけ書き、理由を補わない。
理由を書くときは帰属を付ける（ユーザーが決めた / lead が推した / advisor が指摘した）。理由と決定を同じ文に書くと、理由を否定するのに決定ごと覆すことになる。
採らなかった案は「却下」でなく「今回は採らなかった」と書く。経緯は決定の履歴であって、決定を縛る契約ではない。

🪣 を更新するたびに新しいエントリを立てる。既存エントリの本文に書き足さない。
同一セッション内で 2 回以上更新しても同じで、見出しがその時刻を持つ形にする。

#### 二重記帳をやめる

他の正本が持つ内容を 🪣 に写さない。まず同じ issue の他セクションを疑う。
扱いは参照先の性質で分かれる。

- repo に残り、移動時に参照が追われる正本（設計書の節 / 知見 / `git` 履歴 / 閉じた issue）→ 1 行の参照
- 開いている別 issue（WIP / TODO / ICEBOX）→ issue 単位の `[[link]]` まで。相手の 🪣 も改訂される側なので、セクション名やエントリの日付を指さない
- 更新後の 💧 / 🌂 が持つ現在状態 → 🪣 に先回りして書かない。次回の更新で降りてくる
- ☔ の項目 → 書かない。チェックが台帳になる
- 外部の揮発先（`/tmp/lw-review/` 等）→ 参照でなく結論そのものを 1-2 行

参照を書いたら実在を確認する（`[[link]]` は `find`、セクション名は `grep`）。

## 完了 / 廃棄時の規律

issue を閉じる前に、内容を 3 種類に仕分ける:

- 永続的な指針・知識・決定 → 関連 wiki page に書き戻す（必須）
- issue としての作業ログ（判断過程・選択肢比較・着手順・採用判断）→ `.90_fixed/` に mv して保持
- 一時的な作業計画・進捗・中断点メモ → 上 2 つの過程で取り上げ済みなので、issue 本体は通常通り保持

書き戻し先の wiki page が決まらない場合は issue を残したまま、書き戻し作業を別 issue に切り出すか wiki に新規 page を作る。

## ユーザー確認

Claude は自発的に issue を FIXED / FADED にしない。
完了したと判断したら「内容は X に書き戻した、FIXED にしてよいか？」とユーザーに確認してから mv する。
ユーザーが明示指示（「FIXED で」「閉じて」等）を出した場合のみ確認なしで mv して OK。

## 派生作業の記録先

本題の作業中に出た派生を記録する時の優先順位。

既存 issue への 1 行 append が第一候補。次点が親 issue の 1 行。
新規 issue は明示の判断があるときだけ作る。
`0_icebox.md` は使わない（着手時期が決まっていない issue の置き場で、出たばかりの派生とは扱いが違う）。

append した時はユーザーに報告する。
黙って別 issue の中身が増えると、ユーザーが認識しないまま作業範囲が広がる。

## 作成

- ファイル名: `<プロジェクト>-<サブプロジェクト>-<動詞>-<対象>`、kebab-case、日付プレフィックスなし
  - プロジェクト: ワークスペース名 / 案件名。どちらにも当てはまらない場合は `_` prefix を付けた bare-name（例: `_research-thinking-style-profile.md`）
  - サブプロジェクト / 動詞: 既存 issue で使われている語彙を探し、合うものがあればそれを使う。なければ新しく作る
  - 対象: 具体物
- 命名前に `ls 00_issues/` と `find 00_issues/ -name "*.md"` で既存の名前パターンを確認する
- frontmatter は issue 固有スキーマ（`related` / `source` / `created` / `tags`）

`related` は配列で、要素は次のいずれか。

- `"[[page-title]]"` — issue / wiki page への wikilink。YAML で `[[` は配列開始と衝突するため引用符必須。issue は状態ディレクトリ移動でパスが変わるので、issue 間参照は wikilink にする
- `<path>` — 非 wiki ファイルへのパス（`.claude/rules/issue.md` / `README.md` / `lefthook.yml` 等、wikilink で解決できないもの）
- `<directory>/` — ディレクトリ参照（`10_raw/<案件>/` / `90_reports/weekly/` 等、末尾 `/`）

`wiki.md` の `sources` と使い分ける。
`sources` は出典（raw パス / URL / `conversation`）、`related` は作業上の関連物（他の issue / 設計書 / 設定ファイル）。
